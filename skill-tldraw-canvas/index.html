The board is somebody's live workspace

Drawing on a tldraw board from an agent has two failure modes and they pull in opposite directions. Write the records yourself and you are hand-authoring an undocumented schema — a geo shape's props, a ProseMirror label, an arrow that needs two separate binding records to stick to the shapes it connects. Drive the UI instead and you are clicking, slowly, through a canvas you can't measure.

And underneath both: a board is not a file. It is a live, shared surface, often with people watching it right now, containing work that was there before you arrived. An agent that writes into it without reading it first, or that "cleans up" by clearing the page, deletes somebody's afternoon.

So the skill is two transports with one discipline on top: read before you write, prefix everything you create, plan the geometry before you place a shape, and verify with the right oracle for the right question.

Pick the transport before anything else

Two ways to reach a board, and the choice comes first because the two differ in what you write and what you can do, not just in how you send it. Direct HTTP is preferred: faster, works on boards nobody has open, and it hands back an authoritative read to verify against.

The trigger is anything shaped like drawing — "draw X on tldraw", "add a box labeled Y", "tldraw this out", "re-colour those", "clean up". Homophones teal draw, tealdraw, tl draw, td draw all mean the same thing.

Other people are looking at this board

  • Never delete a shape whose id doesn't start with shape:ai- without explicit confirmation. That's the user's work, and someone may be watching it live.
  • Check who's watching before a bulk edit, where the transport can tell you. Humans see every intermediate state.
  • Deleting shapes this session created needs no confirmation — that's correcting your own output.
  • Don't navigate away from a board with unsaved user intent — selected shapes, half-typed text — without asking.

Same reason a build gets split into a few logical batches when people are watching: it animates in front of them instead of appearing all at once.

Beyond safety, the standing ceilings: no text measurement over HTTP, so sizing is heuristic and anything text-heavy needs a picture; no viewers count in the browser, so you cannot tell who is watching on that transport; no writing to a board nobody has open in the browser at all; and no aesthetic judgement anywhere — the skill checks that boxes don't overlap, not that the diagram is good.

Where it lives

Integratestldraw — a sync server's agent API over HTTP, and tldraw.com boards — and Chrome, as the fallback transport via Chrome MCP. Those two, and nothing else.
RequiresThe manifest lists no hard requirement, and that is accurate: the HTTP transport needs only curl, and the browser transport needs Chrome MCP if you end up on it. Neither is a prerequisite for the other.
ConfigurationTLDRAW_SYNC_URL — the sync server base URL, read from the environment. The skill does not store it; if it isn't set it asks, and suggests you persist it in your shell profile or the project's CLAUDE.md.
The injected halfscripts/bootstrap.js defines window.__td in the page, per tab, and is idempotent. It lives in the browser tab's memory and dies with the tab. Nothing is installed.
Its stateNone. The manifest says state: false and the skill keeps nothing between runs — no board registry, no remembered room id, no cached record schema, nothing under ~/.agents/. Every run re-probes the transport and re-reads the board, which is why "don't reuse a URL from a previous session" is a rule it can actually keep.
Where things persistOn the board, which belongs to the user and their sync server. That is the point of the skill and the reason for every safety rule above: the only durable thing it touches is somebody else's document.
Safe to deleteLocally, there is nothing to delete. On the board, shape:ai- shapes are — that prefix exists so cleanup can be exact. Everything else is the user's.
A roomId is a secretAuth is typically none: the roomId is the capability, because joining the sync websocket already grants full write. Treat one like a password — never in a commit, an issue, or anything public.
Referencesreferences/ carries the detail the main file doesn't: transport-http.md, transport-browser.md, records.md (templates per shape type), shape-schemas.md (every prop with valid enums), rich-text.md (the ProseMirror label format), td-api.md (the full window.__td surface).

Six moves, and the two that go wrong

One request — "draw this out" — from an unknown transport to a verified board.

← → arrow keys

0 — probing a transport, and the trap in the probe

The HTTP check asks for a room that cannot exist and reads the status code:

curl -s -o /dev/null -w '%{http_code}' "$BASE/agent/room/probe-does-not-exist"
# 404 with a JSON body  → the handler answered: the API is there
# HTML error page / 405 / connection failure → it isn't
HTML back does not mean "no API" — it usually means "wrong host". The web app and $BASE are frequently different hosts, and the web app is an SPA that answers 200 + index.html for any path. Probe the sync host before concluding this transport is unavailable. Separately, a deployment that scales to zero answers /health non-200 while parked; waking it is usually triggered by someone loading the web app, so ask the user to open the board and poll /health until 200 — typically 30–90 seconds. Building against a parked server fails every write.

1 — pick the board, and read it before you write

A URL or room id from the user is used as given; "a new board" creates one and hands the link back; anything else is a question, because guessing means writing into someone's real work. Then read it. Over HTTP, GET $BASE/agent/room/$ROOM returns {roomId, viewers, pages, shapes, bindings} with richText flattened to props.text and coordinates rounded, so it is cheap to read; ?full=1 gives raw records when you need to copy an existing shape's exact prop shape. In the browser it is window.__td.probe() then readCanvas(). Either way the question is the same: are there shapes here that this skill didn't create? If so, say what's in the board and confirm before adding.

The page id matters and is easy to miss: .pages[0].id is the parentId every top-level shape needs.

2 — plan the layout before placing a single shape

Anything over ~5 shapes gets a plan written out in the response first: grid coordinates for every shape, arrow routes as source/target pairs with one question each — does this path cross another shape's bounding box? — and a whitespace budget where shapes don't touch, arrow lanes get a shape-width of clearance, and children stay inside their frame's bounds.

Sizing is a heuristic, not a measurement: a 2-line rectangle wants 260×110, a diamond with 2+ lines 320×200, an arrow carrying a 2-word label needs ≥300px of free path. On HTTP that is the only sizing you get; in the browser autoSize measures the real rendered text and does better.

The failure mode isn't forgetting the check — it's writing it out and not applying it. The skill says so in as many words, then tells you to actually run the arithmetic against your own numbers.

Background furniture — gridlines, bands, axis rules, backdrops — is bounded by the content region it annotates, never by the layout's total extent. It underlaps content by design, so the overlap check above reads clean and tells you nothing about it. Get it wrong and a chart's deadline line runs straight down through the legend prose sitting below the chart.

3 — every id it writes starts with shape:ai-

That prefix is the safety boundary: cleanup targets only the skill's own work, never the user's. And where you control the ids, they are derived deterministically — from position, or from the source record they represent — rather than from a counter that restarts each run.

Which buys re-rendering. A board generated by a script can be re-run as an overwrite in place, and the delete sweep fires only on shapes that genuinely went away — so a rebuild that shifts every shape on the page still comes back put 409, delete 0.

That determinism is yours to supply, not the helper's. bootstrap.js's newId() is 'shape:ai-' + Date.now().toString(36) + '-' + Math.random()… — unique, prefixed, and different every run. The prefix guarantee holds on both transports; the re-render-in-place guarantee only holds when you write the ids yourself, which in practice means the HTTP transport.

4 — build, and the arrow that needs two bindings

The record shapes are identical on both transports; what differs is how much of each record you write. Over HTTP records are complete — every envelope field and every prop, because there is no Editor to fill in defaults. A malformed one comes back 400 carrying the schema's own message, which enumerates the valid values rather than just rejecting you:

At shape(type = geo).props.color:
  Expected "black" or "grey" or … got chartreuse

An arrow is the one worth reading twice: it is three records — the arrow shape, plus one binding per end, each carrying terminal: "start"|"end" and a normalizedAnchor. In the browser, __td.createArrow({from, to}) builds them for you: it resolves each endpoint through editor.getShapePageBounds() for initial placement, then calls editor.createBindings() — inside a try, best-effort. Which is precisely why the next step asserts the count rather than trusting it.

Deleting is symmetrical and has a sharp edge: deleting a shape leaves its bindings orphaned. Delete the bindings too, or delete the arrow, which takes its bindings with it.

5 — two oracles, and the arithmetic nobody else will do

Verification is three claims: every shape you meant to create exists, every arrow has two bindings, and no two bounding boxes overlap. That last one is arithmetic on the coordinates — do it explicitly, because nothing else will catch it.

Then the split: records are the oracle for what exists, pixels are the oracle for how it lays out, and the two don't collapse into one. A browser tab is never the presence oracle — hidden, it defers applying incoming sync messages and reports a shape missing long after every visible viewer already has it. An authoritative read is never the layout oracle — it echoes your own numbers back, so a label that overflowed its box and collided with the shape below reads perfectly clean.

So anything text-heavy gets a screenshot too, including over HTTP, where nothing measured the text in the first place. Borrow a tab purely to look — no bootstrap needed, window.editor is already on the page — and point the camera at coordinates you already know, because you computed them when you built it: window.editor.zoomToBounds({x, y, w, h}, {inset: 20}). zoomToFit() on a board thousands of units tall renders every chart too small to judge.

6 — then it hands the board back

The report is the link, what got made, and the shape count — plus the note that saying "clean up" removes the shape:ai- shapes. Or you can just hit undo.
