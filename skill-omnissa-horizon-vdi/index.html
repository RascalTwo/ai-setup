↓  WHY IT EXISTS

The Mac screen is the user's

Driving a GUI with computer-use normally means taking the screen. Windows get raised, focus is stolen, the pointer moves under your hands — fine for a thirty-second task, unusable for an agent working a ticket queue or a mailbox inside a corporate VDI for twenty minutes. The user is sitting right there, wanting to keep typing.

And a VDI is the least forgiving place to do it. Horizon Client is a macOS window containing a picture of a Windows desktop, so the accessibility tree stops at the wrapper: there are no buttons to query, no labels to match, no element tree to walk. Everything inside is pixels, and every click is a coordinate.

DeskPad is the move that makes both problems tractable at once. It presents a virtual display that macOS treats as real, so Horizon can be parked somewhere that isn't the user's screen — and once it is parked there, the agent can click into it all day without ever touching what the human is looking at.

Preferred display setup

The skill carries disable-model-invocation: true, so it doesn't fire on its own. Ask for it: "operate the VDI", "check my mail on the remote desktop", "open Horizon and find the ticket" — anything naming a VDI, a remote or virtual desktop, Omnissa or Horizon, or an app that lives inside one.

Standing it up is four moves, in this order:

  1. Launch DeskPad if it isn't running.
  2. Confirm macOS actually sees it — system_profiler SPDisplaysDataType | sed -n '1,260p' should list DeskPad Display.
  3. Put Horizon in windowed mode if it's fullscreen.
  4. Window > Move to DeskPad Display, and leave it windowed there.

Step 4's menu item is only enabled when Horizon is in a normal windowed state. Greyed out means exit fullscreen or restore the window first — the menu isn't broken, the precondition is unmet.

Windowed, not fullscreen, and not Window > Fill. Both were measurably less reliable for input after a focus change. This is an empirical finding rather than a preference, and it is the single setting most likely to be "improved" back into a broken state.

What it will not do

Reading the VDI is allowed when the user asks. Acting in it is not, by default. No sending messages, joining meetings, submitting forms, changing tickets, deleting data, or transmitting anything sensitive — unless the user explicitly asks and the computer-use confirmation policy allows that action. Two gates, not one.

Stop and ask on any login, MFA, password or permission prompt. Those require a human. The skill does not attempt them, work around them, or wait them out.
  • It cannot read the Windows UI structurally. Horizon's accessibility tree exposes the Mac wrapper, not the app inside, so there is no element to assert on — only pixels, and only from a fresh screenshot.
  • It won't trust a stale coordinate. Every batch re-derives from the current screenshot, because the Horizon window can move or resize between actions.
  • It avoids global keyboard shortcuts, Ctrl+Esc especially — it sometimes fails after a focus change even when concrete clicks still work. Visible controls beat shortcuts every time here.
  • It won't leave litter on someone's desktop. Probes are task-shaped by design; an arbitrary typed probe string is a last resort and gets cleared immediately.
  • It won't quietly mark your mail read. Opening a conversation to check unread state changes that state, so the evidence is captured from the app's own unread filter or counter first.
  • macOS only. DeskPad, system_profiler and the Horizon menu structure are all Mac-specific.

The known good state, and the probe that proves it

One task, from a cold Mac to a verified click inside Windows — and the four ways input stops landing.

← → arrow keys

Target Horizon, never the mirror

There are two windows showing the same thing and only one of them works. DeskPad's mirror window displays the virtual display faithfully — and input clicked into it did not reliably pass through to the remote desktop. Every sky call names the client directly, by app name:

await sky.click({ app: 'Omnissa Horizon Client', x: 760, y: 430 });

App-name targeting is preferred over the macOS app path, which is the fallback for when name targeting fails. Naming the app on every call, rather than setting a target once, is what keeps a focus change from silently redirecting a click at the wrong surface.

Two clicks, because the first one is not for you

The known good state has a specific shape and the click order is part of it: the first click lands well inside the remote Windows content — away from the macOS titlebar and away from Horizon's own toolbar — and only then does a second click take a concrete Windows control. The first click is buying input capture; the second is doing the work.

The probe is the same two clicks with a verification bolted on, run before real work and again after the user alt-tabs or changes display settings:

await sky.get_app_state({ app: 'Finder', disableDiff: true });
await new Promise(r => setTimeout(r, 500));
await sky.click({ app: 'Omnissa Horizon Client', x: 760, y: 430 });   // into the content
await new Promise(r => setTimeout(r, 500));
await sky.click({ app: 'Omnissa Horizon Client', x: 450, y: 750 });   // a real control
await sky.press_key({ app: 'Omnissa Horizon Client', key: 'Escape' });

Those coordinates are an example, not a constant — they depend on where the Horizon window currently is, and the skill says so explicitly: use the latest screenshot, never a stale number. The 500 ms pauses are there because focus takes real time to settle; without them the second click lands before the first has taken effect.

The probe is quiet on purpose

This is somebody's work machine, so the probe is chosen to leave nothing behind, in this preference order: click the Windows Start button, confirm Start opens, press Escape; or click a navigation control that was already part of the task and confirm the expected pane appears; or, if you were about to launch an app anyway, click the taskbar Search box and type only the real app name you were going to type.

An arbitrary typed probe string is the last resort, and it gets cleared immediately. The design goal is that a colleague looking over the user's shoulder afterwards finds no evidence a robot was there — no stray "test123" in a search box, no half-composed message.

Click, screenshot, re-derive. Every batch.

Because the accessibility tree exposes only the Mac wrapper, there is nothing to query about the Windows app — so the loop is deliberately short and deliberately slow: one small batch of click/type, then a screenshot, then re-derive the coordinates from that screenshot. Never a long unverified sequence, because there is no error to catch: a click that lands on nothing succeeds exactly as loudly as one that lands on a button.

Two standing preferences fall out of the same constraint. Visible controls over global shortcuts — Ctrl+Esc sometimes fails after a focus change even when concrete clicks still work. And click into a known control, then type, rather than typing and hoping focus was where you left it. For launching an app inside Windows: click the taskbar Search box, type the name, and press Return only once the result is visible or strongly implied.

Reading the screen without spending vision tokens

Screenshots go to read-image-locally first, with a specific extraction prompt — exact fields, titles, counts, table rows, error text — and cropped first when the target region is known. Native image reading is the documented fallback, for three named cases: local vision returns nothing but the screenshot visibly contains small or dense UI text; the task needs layout judgement; or calendar cards, dense tables and message lists are too small or clipped to resolve.

magick '<screenshot>' -crop WxH+X+Y /tmp/vdi-crop.png
Prefer an app's own filter over a badge. When checking read/unread state, use the chat client's Unread view or the mail client's unread folder — not a visual interpretation of a badge. And capture that evidence before opening anything, because opening a conversation may mark it read. You can destroy the thing you were sent to measure.

When input stops landing

It will. The recovery ladder is ordered, and the point of the order is that each rung is cheaper than the next:

  1. Re-query Horizon state.
  2. Click inside the remote Windows content.
  3. Run the quiet Start-menu probe, or click a task-relevant visible control.
  4. If text input specifically must be verified, type only task-relevant text into the target control.
  5. Still failing — restore the window with Window > Move & Resize > Return to Previous Size.
  6. And avoid true fullscreen and Fill while using DeskPad unless a fresh probe passes.

One specific culprit is worth recognising on sight: the Windows snap-layout popup. It appears near the top-right maximize button when the pointer rests there, and it intercepts input — clicks that should reach the app land on the popup instead. The fix is the same first move as everything else: click well inside the content area, then retry the concrete control.
