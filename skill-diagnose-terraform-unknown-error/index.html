↓  WHY IT EXISTS

"Unknown error" is a printing problem

A Terraform provider that reports unknown error has usually made a perfectly ordinary HTTP call and got a perfectly ordinary HTTP failure back — it just had nowhere to map that response, so it shrugged. The status line, the headers and the response body all exist. They're one log level away. This skill's entire job is to go get them, once, and then put the log level back.

Three things you hand it

Everything else it derives:

  • The workflow file to modify — e.g. deploy.yml.
  • The name of the failing step — e.g. Terraform Apply. It matches on the step's name:, so that string has to be exact.
  • That step's working directory — e.g. ci/terraform, because the rewritten step reproduces the original working-directory: rather than inferring it.

It is invoked when a run has already failed with an opaque provider error. There is nothing to diagnose on a green pipeline: the whole method depends on reproducing a failure you've already seen.

It only owns the middle

The skill is deliberately narrow: it edits the workflow, reads the logs and interprets the exchange. The CI mechanics belong to neighbours — trigger-github-deploy kicks off the run, wait-for-github-workflow blocks until it finishes. One diagnosis, one round trip, and the repo is left exactly as clean as it started.

  • One round trip is the design, not a budget. It captures everything with tee precisely so a second debug run is never needed — and because every debug run costs a commit, a push and a full pipeline.
  • It only reaches errors the provider actually made an HTTP call for. A crash before the request, or a failure inside Terraform's own graph, leaves nothing for the greps to find.
  • The response filter is tuned, not general. grep -v "azure\|microsoft\|storage" strips the platform's own 4xx chatter, and will also strip a real failure whose text happens to contain one of those words.
  • The fix rides with the revert. Once it has named the missing scope or the null field, the fix lands in the same commit that reverts the debug flag — never on its own, never after.

Where it lives

IntegratesGitHub Actions — it edits a workflow file, pushes it, and pulls the run's logs through gh — and Terraform's own TF_LOG=DEBUG output, which is the only place the raw HTTP exchange is ever printed.
Requiresgh, authenticated and able to push. Plus unzip, grep and head. It does not run Terraform locally and does not need the provider installed.
What it changesYour repository. This is the one skill in the group that writes: one commit adding TF_LOG: DEBUG and a tee, and a second commit reverting it alongside the real fix. Both land on the branch you're on.
Its stateNone. It keeps nothing between runs — no local config, no cache, nothing under ~/.agents/state/. The two files it touches, /tmp/tf-debug.log (written inside the runner, which is destroyed with it) and /tmp/run-logs.zip (overwritten next time), are scratch.
Where the risk sitsIn the build log, not on your disk. A DEBUG-level Terraform run prints credentials into a log that outlives the run — which is why reverting is part of the method rather than a follow-up.

The pipe that eats your exit code

Step one edits the failing step to capture output. The shape matters more than it looks:

- name: <step-name>
  working-directory: <working-dir>
  env:
    TF_LOG: DEBUG
  run: |
    <original-command> 2>&1 | tee /tmp/tf-debug.log; RESULT=${PIPESTATUS[0]}
    exit $RESULT

tee plus ${PIPESTATUS[0]} exists because a pipeline's exit status is the last command's. Pipe a failing terraform apply into anything and the step reports the exit code of the thing on the right — which succeeded. Your broken apply turns green and CI carries on. 2>&1 is equally load-bearing: TF_LOG output goes to stderr, so without the redirect the tee captures a tidy plan summary and none of the HTTP traffic you added the flag for.

Never pipe through grep at apply time. It's the tempting version — filter the noise as it streams — and it's exactly the thing that masks the failure. Capture everything with tee, filter later, when the run is over and the exit code is already banked.

Getting the exchange back out

Logs come down as a zip and get read without unpacking. Two greps: one for what you sent, one for what came back.

gh api repos/<owner>/<repo>/actions/runs/<run-id>/logs > /tmp/run-logs.zip

# the request body sent to the failing endpoint
unzip -p /tmp/run-logs.zip | grep -a -A 40 "performing request.*<endpoint>" | head -60

# the response — 4xx/5xx only, minus the platform's own chatter
unzip -p /tmp/run-logs.zip | grep -a -A 15 "HTTP/[0-9]\.[0-9] [4-5][0-9][0-9]" \
  | grep -v "azure\|microsoft\|storage" | head -40

performing request is the Terraform SDK's own log line for an outbound call, which is why the endpoint is matched as a suffix of it rather than searched for on its own. -A 40 and -A 15 are the request body and the response headers respectively — the match is the status line, the payload is what follows it. grep -a is not decoration either: it forces grep to treat the stream as text, because a log full of control bytes will otherwise get written off as binary and matched silently.

Reading the answer

  • 403 — read the Www-Authenticate header. It names the scope the token is missing. That's the fix, spelled out, in a header nobody looks at.
  • 500 — read the response body for an error code; if there isn't one, read the request body instead for the field that's missing or null. A 500 is often the API's reaction to something you didn't send — which is why the request grep runs even when the response looks like the interesting half.

Cleanup isn't a tidy-up step

Once the cause is known, the TF_LOG=DEBUG change is reverted and the actual fix applied in the same commit — then pushed and run again to verify. Not a follow-up PR, not a TODO.

Never leave TF_LOG=DEBUG in the workflow. At DEBUG, Terraform prints the API keys, tokens and client secrets in its outbound requests in plain text — into a build log that outlives the run and is readable by anyone with access to it. The debug flag is a liability with a fuse, and closing the loop is the only thing that puts it out.
