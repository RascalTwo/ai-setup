Nothing in a config ever goes red

A setup like this has no build. A symlink whose target got renamed keeps resolving as a dead file. A third-party skill drifts three versions behind upstream without a single warning. An MCP server stops being called and goes on loading its tool schemas into every session. A published poster keeps confidently selling a skill that was deleted in March. None of it fails anything, because there is nothing to fail.

It's also spread too thin to notice by eye: one public repo plus private overlays, symlinked into ~/.claude/, ~/.codex/ and ~/.agents/, driving two different agents that each expose a different slice of the truth. No single place shows you the whole thing, which is exactly why the drift survives.

You run it. Weekly, and on purpose.

Say "run the weekly audit", "audit my setup", "clean up my agent config", or name the symptom — a stale skill, an unused MCP server, an orphaned directory, drift in external-skills.json. The manifest carries disable-model-invocation: true, so an agent never starts a ten-phase sweep of your home directory on its own initiative.

It is interactive from the first phase, not the last. Phase 1 inventories everything read-only, hands you the list, and asks which phases you actually want to run — so a "just the skills, skip memory" audit is a normal outcome rather than an interruption. Every phase after that ends by asking, and so does the run.

All ten phases are independent enough to skip. The usage snapshot in Phase 0 is worth having regardless: it is the only number in the audit that comes from evidence rather than inspection.

Nothing ships without you

The golden rule is stated before the first phase: never auto-apply changes. Every recommendation is presented individually, with the reasoning — not "remove this" but why it's a candidate for removal.

Because every live entry is already a pointer into a repo, the edits made during the audit are the repo — Phase 9 has nothing to cp back, and copying over a symlink would replace it with a regular file and silently break the setup. What's left is re-running the idempotent installer, recompiling subagents, and offering a commit on private/trunk — never on the squashed public snapshot.

  • Half the red lines aren't defects. SYMLINK is a healthy state, and REAL_DIR usually is — a legitimate third-party install. Saying which is which is the actual work, and a run that reports one broken link and nine fine ones has done its job.
  • "0 calls" is not proof of death. Usage comes from Claude Code's transcripts; Codex exposes no equivalent, so quiet means unused by Claude. Confirm before treating it as a removal signal.
  • A skill with no poster is not a finding. Posters are opt-in and most skills will never have one. Reading that list out as a backlog is the meta-tooling trap, and the skill says so.
  • It cannot see the private overlays from here. Their paths are machine-local, kept in ~/.agents/overlays.json rather than in the public file, so the audit discovers them at run time or not at all.
  • Publishing has a hard gate. The public core is only pushed after a mandatory secrets scan — org identifiers, account numbers, hardcoded home paths, AWS keys, GitHub tokens — because company and client material belongs in the private overlays only.

One setup, two agents, zero copies

The thing being audited is a public core (RascalTwo/ai-setup) plus private overlays, installed by symlink into the paths Claude Code and OpenAI Codex both read. AGENTS.md is canonical and CLAUDE.md is a symlink to it, so both agents read the same bytes. The canonical skills dir is ~/.agents/skills; ~/.claude/skills is a whole-dir symlink to it. Subagents are authored once and compiled by Ruler into a Claude .md and a Codex .toml.

That model decides what counts as a finding. A healthy entry is a pointer into a git repo, so there is nothing to copy back, no snapshot to reconcile, and no token doubling to "fix". The audit's first move is a classification sweep — SYMLINK, BROKEN, REAL_DIR, ABSENT — and only SYMLINK is unconditionally fine.

The one invariant it runs every time

Everything in ~/.agents/skills is either a symlink into one of the repos (owned) or named in external-skills.json (third-party). A real directory that the manifest doesn't name is an orphan. The manifest is hand-maintained on purpose: the npx lock file on disk silently fails to update, so it isn't trusted for provenance.

# a real dir whose name isn't explicitly in the manifest
for d in ~/.agents/skills/*; do
  [ -L "$d" ] && continue    # symlink into a repo = owned, fine
  # $DOC = the public manifest merged with every overlay's
  jq -e --arg n "$(basename "$d")" '[.repos[][]] | index($n)' "$DOC" \
    >/dev/null || echo "UNACCOUNTED: $d"
done

Freshness is a separate question, answered by content hash: a third-party skill is current when its installed SKILL.md matches some blob in its source repo's tree. Hashing sidesteps mapping local names onto upstream paths — upstream reorganises (mattpocock moved every skill into category dirs without renaming one) and a path-based check would break. The same pass reports skills upstream has added, and a NEW you pass on is deliberately recorded nowhere — there is no declined-list, so it is offered again next audit. A stale no is worse than a repeat ask.

The signals that lie, and it names them

  • ls -ld ~/.agents/skills/foo/ prints d even when foo is a symlink — the trailing slash makes ls follow the link. Test with [ -L ], never infer a real dir from ls. stat follows links too.
  • An entire repo's skills reporting GONE on one line isn't a finding, it's a shell bug: IFS=$'\t' read leaks past the read and the whole list arrives as one variable.
  • Usage counts are Claude-only. They come from ~/.claude/projects/**/*.jsonl, which Claude Code writes unconditionally. Codex exposes no equivalent, so "0 calls" means unused by Claude. A reviewer subagent can also be quiet simply because the r2-sdlc pipeline was idle.
  • /doctor runs first and is folded in — then set aside. It is one probe of one agent, blind to Codex, the overlays, the symlink model and memory. Green /doctor never means the setup is healthy.

The usage report replaced a Prometheus/Loki/Tempo/OTEL Docker stack that only had data while it was up, needed babysitting, and was down at audit time. The transcripts had more than it would have provided. Decommissioned 2026-07-11 — and the audit still checks that OTEL_* isn't exporting to the dead endpoint.

It audits its own advertising

Phase 8 turns the audit on the published explorables — the setup tour and these posters. They're hand-authored HTML that nothing regenerates, so they drift every time a skill changes, and this audit is the only cadence that catches it. Each poster stamps its subject as data-atom="<skill>" so the check is a one-second grep rather than a slow semantic judgment about whether a pitch still lands.

The two lists it produces are read differently, and that asymmetry is the point. A poster whose atom no longer exists is the worst kind of defect — a public, listed page confidently selling something that's gone. A skill with no poster is not a defect at all; posters are opt-in, most skills will never have one, and reading that list out as a to-do is the meta-tooling trap.

Two traps learned the hard way: viz verify is not parallel-safe — it writes one shared latest.png, so concurrent runs clobber each other and you confirm a layout you never looked at. And a poster's og.auto.png never regenerates itself: edit a card without --og and the page updates while every chat unfurl keeps previewing the old pitch. It's git-ignored, so a fresh clone has no OG images at all.

Phase 9 closes the loop the same way it opened: the explorables deploy separately, off disk, so the OG images have to be regenerated before the deploy rather than before the commit. Then it asks what you want to revisit.
