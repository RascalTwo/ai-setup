↓  WHY IT EXISTS

Things randomly happen

A browser renders the result of a click and never the click itself. Record an agent driving a UI and you get a video in which menus open, panels swap and rows appear with nothing visible causing any of it. The viewer's experience is not "I see how to do that"; it is "things randomly happen" — and that is the failure this skill names.

The obvious fixes all fall over. A GIF recorder that stamps a click marker gives you a slideshow. Editing arrows on afterwards means re-editing every time the flow changes. Screen-recording the real OS pointer captures a cursor that teleports, because an automation tool moves the mouse by assignment, not by motion.

So: draw the cursor in the page, move it with an easing curve, frame the target before touching it, and flash a ring where the click lands. Then a recording explains itself, and the same choreography works live in front of a human with nothing recording at all.

Inject it, then drive it

It is one file and it defines window.__narrate. It does nothing on its own.

// Chrome MCP — a page you are already driving
javascript_tool: <paste the contents of ui-narration.js>

// Puppeteer / Playwright
await page.evaluate(fs.readFileSync(
  `${'$'}{process.env.HOME}/.agents/skills/ui-narration/ui-narration.js`, 'utf8'));

// or by hand: paste it into a DevTools console

Then call it. The one you want ninety percent of the time takes two arguments, and the split matters more than it sounds: frame one element, click another — you often want the whole card outlined while the click lands on its title, because the card's centre sits over an avatar or a menu.

focusAndClick(hlEl, clickEl?)frame, glide, hold, pulse, click, wait. The main verb.
highlight(el) / hideBox()frame an element / drop the frame
moveTo(x, y, dur) / clickPulse(x, y)glide to a point / ring at a point, without clicking
realClick(el)framework-safe click at the centre, via elementFromPoint
waitFor(fn, timeout?) / sleep(ms)poll until truthy / pause
smoothScrollTo(y, dur?)eased scroll — what a GIF recorder can never capture
typeInto(el, text, per?)type character by character, through the right prototype setter
drag(el, dx, dy, opts?)drag with intermediate moves, so a framework sees a real gesture
say(text, {at, hold}) / captions(bool)caption · show or hide the band (cues keep logging while hidden)
captionsT0(ms?) / vtt() / cueszero the caption clock · emit WebVTT · the raw log
clap() / ready(timeout?) / CFGtwo sync frames · wait for the overlay · the timings

browser-capture injects this for its recorded walkthroughs. You can equally drive it live, through Chrome MCP, while a human watches — the same choreography, no file at the end.

What it refuses to be

  • It is a toolbox, not a pipeline. There is no run(steps), no DSL, no config file. An agent composes calls; the skill supplies verbs. That is deliberate and it is why a caption is an independent primitive rather than an argument to focusAndClick.
  • It does not record anything. No video, no frames, no files. clap() is the only recorder-aware call in it and it is meaningless outside one.
  • It does not survive navigation on its own. A fresh document has no __narrate — re-inject, or use Puppeteer's evaluateOnNewDocument.
  • It moves a drawn cursor, not your mouse. The real OS pointer is untouched, which is exactly why a screen recording of the desktop still shows the system cursor sitting wherever it was left.
  • Spoken narration is not built yet. The name is aspirational on purpose and currently half-earned: spatial narration works, textual narration works, audio is the roadmap — driven off the same cue log, so the .vtt becomes the script rather than a second source of truth.
Assert on geometry, never on "the call returned". A drag or resize that does nothing is indistinguishable from one that works: the handle is there, waitFor resolves, nothing throws, and the element's rect comes back byte-identical. Measure before and after, or you will ship a take of an interaction that never happened.

Where it lives

The whole skillskills/ui-narration/ui-narration.js, plus SKILL.md. One file, one IIFE, one global. No build step, no bundle, no npm package, no import.
IntegratesChrome — as an injected page overlay, through Chrome MCP's javascript_tool or Puppeteer's page.evaluate. That is the entire integration list, and it is one-way: the skill never calls out to anything.
RequiresThe manifest lists no hard requirement, and that is accurate — it is plain DOM against standard APIs. Anything that can run a script in a page can run this, including a DevTools console you paste it into by hand.
Depended on bybrowser-capture, as a hard dependency: record-flow.js injects it unless you pass --no-kit, and exits with the paths it tried rather than recording a silent, unannotated take.

The beat, in milliseconds

One focusAndClick, from the call to the app responding — and the six places where the obvious implementation is wrong.

← → arrow keys

The overlay is built lazily, and that is load-bearing

Injecting the file costs nothing until you call something: ensureOverlay() creates the cursor and the box on first use. The reason is not frugality. The recorder injects this kit with Puppeteer's evaluateOnNewDocument so it survives cross-document navigation — and that runs at document-start, when document.body is still null. Touching body at top level would throw there, and window.__narrate would never get defined at all, on any page. So ensureOverlay() returns false when there is no body yet and ready() polls every 30 ms until there is.

Two nodes, both pointer-events: none — the cursor at z-index: 2147483647, the box one below it: the cursor is an inline <svg> arrow with a drop shadow so it survives a light page and a dark one, and the box is a 3px #ff7a00 frame with a glow. After a navigation the cursor is restored to (cx, cy) — the coordinates it left off at — so a glide reads as continuous across pages instead of teleporting back to a corner.

Motion: setTimeout, not requestAnimationFrame

moveTo() tweens with setTimeout(step, 16) and an ease-in-out curve, t < .5 ? 2t² : 1 − (−2t+2)²/2. Two deliberate rejections sit behind that one line. rAF is throttled or paused in headless and background tabs, so an rAF tween silently stalls exactly where you least want it. And a CSS transition lags behind what it is chasing, which shows up as the cursor and its pulse ring visibly drifting apart.

The highlight box reads the target's computed borderTopLeftRadius and matches it, so the frame follows a pill button's corners rather than sitting around it as a rectangle — the detail nobody gets right first try. It pads by 8px and falls back to 12 when the element has no radius.

The order inside focusAndClick, which is the whole product

highlight(hlEl)                 // frame goes on first — the viewer knows what's next
await moveTo(x, y, CFG.glide)   // 950ms, eased, to clickEl's centre
await sleep(CFG.hold)           // 550ms of nothing: let the eye arrive
hideBox()                       // INSTANT, and BEFORE the click
clickPulse(x, y); cursorPress() // 420ms ring to r=44 · cursor dips to 0.7×
realClick(clickEl)
await sleep(CFG.afterClick)     // 1300ms: let the app answer, visibly

hideBox() sets opacity to 0 with no transition, and before the click rather than after. With a fade, the frame survives into the next page for a frame or two and reads as a rendering bug. cursorPress() scales the arrow to 0.7 from transform-origin: 4px 2px — near the tip, so it dips where it points instead of shrinking toward its own middle.

And 950 / 550 / 1300 are not arbitrary. Faster and the eye cannot track the cursor to its target; slower and the capture drags. They are the product, which is why they are exposed as CFG for a run rather than hidden as constants.

realClick — dispatching at a point, not at an element

A bare el.click() on the element you matched frequently does nothing, because component libraries (Joy, Material UI, Radix) nest the real interactive node inside the wrapper you selected — and because a framework may have re-rendered your element into a detached node between the query and the click. So realClick() takes the element's centre, resolves document.elementFromPoint(x, y), and dispatches the full sequence on whatever is actually topmost there:

pointerover → pointerenter → pointerdown → mousedown
           → pointerup → mouseup → click        // each bubbles, cancelable, with clientX/Y

That is a click where a user would have made one, which is the only definition that survives a component library.

typeInto and the prototype that has to match

Setting el.value on a React-controlled input does not fire React's onChange, so the standard workaround is to take the native setter off the prototype and call it, then dispatch a bubbling input event. The trap is which prototype:

const proto = el instanceof HTMLTextAreaElement
  ? HTMLTextAreaElement : HTMLInputElement;
const set = Object.getOwnPropertyDescriptor(proto.prototype, 'value').set;
An <input> setter applied to a <textarea> is silently ignored. No exception, no warning, no console message. The characters appear, the text snaps back on the next render, and there is nothing anywhere to tell you why. It types character by character at 45 ms each, clearing first, so the value builds visibly rather than materialising in one frame.

drag rides the element, and aims along the element's own axis

Two corrections, both from real failures. First, the cursor follows the dragged element's live bounding rect each step, not the straight line between start and end — because a rotate handle travels an arc, and interpolating along the chord leaves the cursor visibly detached from the thing it is supposed to be holding (chord-versus-arc error is about 0.29 × radius). If the element goes away mid-gesture, it falls back to the interpolated point.

Second, pointerdown goes on the element but pointermove and pointerup go on window, because that is where drag implementations listen once a gesture has started. Thirty steps at 24 ms, then a 600 ms settle.

Aim along handleCentre − elementCentre, not along the screen. A handle labelled "right edge" is named in its element's frame. Rotate that element 90° and its right edge sits at the bottom of the screen — so a screen-right drag slides along the edge and resizes by exactly zero pixels, with every call returning successfully.
const v = {x: hx-cx, y: hy-cy}, L = Math.hypot(v.x, v.y) || 1;
await drag(handle, v.x/L*D, v.y/L*D);

Captions: one run, two deliverables

say() is non-blocking by default, so it layers over the 950/550/1300 pacing instead of fighting it; pass hold when the caption is the beat, and {at: el} to anchor it above an element instead of in the subtitle band. Every call pushes {t, text} onto cues, timed from capT0 — which captionsT0() zeroes when recording starts.

Cues are logged even when the band is hidden, and that is the entire point: one take ships burned-in captions or a clean capture plus a complete .vtt sidecar. vtt() emits the file, and its timing rule was learned the hard way — a cue runs until the next cue starts, capped at 6 s, and the 900 ms minimum applies only to the last cue:

const end = next ? Math.min(next.t, c.t + 6000)
                 : c.t + Math.max(900, Math.min(6000, 60 * text.length));

Clamping every cue to a 900 ms minimum made cues overlap whenever two say() calls landed close together. The last cue has no successor to bound it, so it gets a length from its own text instead.

clap(), and why it is not a trim marker on its own

Two white frames: a full-viewport #fff div for 90 ms, removed, then 120 ms of quiet. Fire one immediately before the choreography and one immediately after, and ffmpeg can find both ends of the action afterwards. The caveat is written into the source: on a white-background app the flash barely differs from the page, so pair it with the recorder's own clock (__cap.t0) and use freezedetect only to cross-check.
