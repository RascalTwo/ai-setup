↓  WHY IT EXISTS

A percentage with nobody's name on it

Claude Code's statusline payload carries rate_limits.five_hour.used_percentage and its seven-day twin. Those are account-wide. They will tell you the five-hour window is 43% gone and they will never, under any circumstance, tell you which of your six open sessions did it — so the number is alarming and unactionable at the same time. You cannot close the expensive pane if you cannot find it.

The second thing missing is pace. 43% one hour into a five-hour window is a comfortable afternoon. 43% twenty minutes in means you are done before lunch. A raw percentage cannot distinguish those, and the distinction is the entire decision you are trying to make.

There was an obvious way to get the first number — read the OAuth token and call the usage API, which is what the tools in this space tend to do. That was refused. rate_limits is the supported statusline interface: it arrives on stdin, it costs nothing, and using it carries no ToS risk. Everything here is built on what Claude Code already hands over.

There is nothing to run

The trigger is every render. Claude Code's settings.json points its status line at ccstatusline, and refreshInterval is set to 30:

"statusLine": {
  "type": "command",
  "command": "ccstatusline",
  "padding": 0,
  "refreshInterval": 30
}
Absent does not mean "default". With no refreshInterval there is no periodic refresh at all — the line redraws only on an event. Every clock-driven widget here (the cache countdown, both reset timers, the duration) would sit visibly frozen between turns. The 30 is load-bearing.

ccstatusline reads its own config from its own default path, ~/.config/ccstatusline/settings.json, which install.ts symlinks to tools/statusline/ccstatusline.json — so the tracked config names no path at all and needs no --config. The widget scripts are never linked individually: the config addresses them through $HOME/.agents/ai-setup/tools/statusline/, and they find each other with dirname "$0". They only have to stay in one directory together.

Every widget is a custom-command entry with preserveColors: true, which is what stops ccstatusline applying its own foreground over the ANSI the scripts emit.

It only sees this machine, and it never throttles anything

  • Other clients are invisible. claude.ai, mobile, and any other machine burn the same account window and leave no transcript in ~/.claude/projects. That shrinks the denominator, which inflates every local session's share. The headline account percentage stays exactly right; only the attribution skews.
  • Cost is a proxy, not the meter. Nobody outside Anthropic knows what the rate limiter actually weighs. A share computed from list-price cost is immune to any constant rescaling of that weight, and skews only between sessions with very different model and cache mixes.
  • The window's size is inferred, so it is suppressed when it would lie. The cache widget derives dollars-per-point as local burn ÷ account percentage — and that percentage arrives quantized to about a whole point. Below 3% the rounding alone can move the answer several fold, so the 5h: and wk: figures simply do not print for the first slice of every window rather than printing something confidently threefold wrong.
  • It reports. It never intervenes. No throttling, no blocking, no model switching. ⚠out~44m is information; what you do with it is yours.
  • A widget with no data prints nothing at all — not a zero, not a dash. An empty segment is the honest rendering of "this field was absent from stdin".

Cracking it open

One render, from Claude Code invoking ccstatusline to 3.3/7% appearing on the line. The hard constraint shapes everything: a status line is redrawn constantly, so nothing in this path may block, and the number that takes 1.2 seconds to compute has to arrive on some later render than the one that asked for it.

Two tiers of widget, and only one of them shares anything

Four widgets are standalone: statusline-cost.sh, statusline-duration.sh, statusline-cache.sh and statusline-ttyimgspool.sh each read their fields straight off stdin and exit. They source nothing, so a bug in the shared library cannot take them down. Only the two windowed widgets — statusline-5h.sh and statusline-wk.sh — source statusline-lib.sh, for verdict(), hms(), refresh_share() and share().

verdict() is four lines of awk and it is the pacing number: project current utilisation forward over the window (proj = util / (elapsed/window)), and if the projection exceeds 100 print how long until you hit the cap at this pace, otherwise print the headroom left. The unit adapts — minutes under 90, then hours, then days — because ⚠out~2.1d and ⚠out~44m want completely different reactions from you.

Only the 5h widget kicks off the scan. statusline-wk.sh deliberately does not call refresh_share — one scan serves both windows, and a second caller would only lose the mkdir race a few milliseconds later. Adding the call would look symmetrical and buy nothing.

mkdir is the lock, because macOS has no flock

Several sessions render their status lines at once. Without a lock, every stale moment spawns one scan per live session — six pythons walking the same 500MB of transcripts to compute the same answer. mkdir is the portable atomic test: it succeeds for exactly one caller and fails for everyone else, and the winner rmdirs it when its subshell exits.

A lock can still be orphaned by a kill or a reboot, and a stuck lock would freeze the share number forever — a silent, permanent failure. So a lock directory whose mtime is more than 300 seconds old is treated as abandoned and removed before the race is run. Age comes from stat -c %Y falling back to stat -f %m, GNU then BSD, which is the same two-spelling dance every mtime read in this tool does.

refresh_share() returns immediately in all three outcomes — cache fresh, lock lost, or scan launched. The scan itself is backgrounded and disowned. A cold scan is ~1.2s and a status line that stalled for 1.2s on every render would be worse than having no share number at all.

Fractions, not percentages, are what gets cached

This is the decision that makes a 60-second TTL acceptable. usage-share.json stores each session's fraction of local burn, never a percentage:

{"five_hour": {"total": 41.2207,
               "shares": {"a1b2…": 0.4713, "c3d4…": 0.2088, …}}}

The live account percentage arrives fresh on every render, so only the split needs caching. share() multiplies one by the other at render time, which means a minute-old cache blurs the attribution and never the headline: the 7% is always current, and only the 3.3 in front of it is slightly behind.

Its decimals are adaptive for a reason a fixed format cannot handle: a session is a meaningful slice of five hours and a rounding error against a week. share() starts at one decimal place and keeps adding places until a significant digit appears, up to four — so the weekly widget shows .02/ rather than a permanent, useless 0.0. The leading zero is then stripped to buy back a column on an already crowded line.

Dedupe by message id, or overcount by 1.8×

statusline-usage-scan.py prices each assistant message from its own usage block — plain input, plus cache_read at 0.10×, ephemeral_5m at 1.25× and ephemeral_1h at 2.00× the input rate, plus output. The unknown-model fallback is deliberately the Opus tier: guessing cheap would silently understate whoever ran it.

The load-bearing detail is the dedupe. A transcript writes the same message several times as it streams, so summing rows instead of messages overcounts by roughly 1.8×. scan_file() keeps a seen set of message.id and skips repeats. It also only parses lines that contain the literal string "usage", which is a cheap prefilter over a very large file.

There is deliberately no long-context premium above 200k tokens, and that absence was measured rather than assumed. On a 1M-context setup about 88% of input tokens sit above that threshold, so a premium would dominate the entire calculation. Fitted against four live sessions' own cost.total_cost_usd, the flat rates predict a 301-message session to within 1.6%; an input premium would have put the estimate near half the reported cost. Flat is the measured answer.

The memo, and why the scan stays cheap

Costs land in 300-second buckets keyed by timestamp — fine enough to place a message on either side of a window edge, small enough on disk to keep. Transcripts are append-only, so an unchanged (mtime, size) pair means unchanged cost: usage-scan-memo.json carries both, and a file that matches is reused without being reopened. Anything whose mtime predates the widest window is skipped outright.

Summing a window is then just a floor comparison on bucket keys, which is why one scan serves both the five-hour and the seven-day windows for free. Both output files are written through a tmp + os.replace() pair, so a render that reads the cache mid-write gets the old file rather than half a JSON document.

The cache file carries no scanned_at field and no window-start fields, on purpose: statusline-lib.sh checks the file's own mtime for staleness, and nothing reads the rest. A timestamp inside a file whose mtime already says the same thing is a second copy waiting to disagree with the first.

Two smaller widgets that are not what they look like

The cache countdown uses the transcript file's mtime as the cache age against a 60-minute TTL, and once that lapses it goes negative — 🧊 -3m means the cache expired three minutes ago — rather than resetting. It only jumps back to ~60 on genuine new activity, which is the thing that actually mints a fresh cache. Red starts at 0, not at five minutes, because zero is where the meaning changes: above it the next message is cheap, at or below it the whole context gets rewritten.

The image count resolves its session id from herdr's agent_session for the pane, not from the session_id on stdin. Claude Code's own id differs when a session runs as a background job, and using it would point the widget at the wrong spool folder — so it matches how ttyimgspool's hook and viewer resolve it, and only falls back to stdin when there is no herdr pane.
