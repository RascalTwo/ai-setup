↓  WHY IT EXISTS

A screenshot per read, a live message box per write

Slack is a web page, so an agent that needs to read it has one obvious move: look at the page, click, look again. Every read costs a screenshot round-trip. Every write is worse, because the thing the agent is typing into is the live message box. The skill's own last gotcha is that this happens: a stray keystroke lands in the composer, and the fix is to click the box, select all, delete, and confirm the placeholder is back before doing anything else.

slack-in-browser starts from a plainer fact: that page is only a client. Whatever it shows, it got from Slack's web API, called with a token and a cookie it already holds. The tab is therefore a ready-made, authenticated API client, and an agent that can run JavaScript in it needs no UI at all. The skill's own count: two fetch calls do the work a screenshot-and-click loop does, and the result can be checked by reading it back.

When no Slack tool is connected

The skill's description gives the occasions: watch a channel for a message, read recent messages or bot and email alerts, add a reaction, or reply, when no Slack tool is connected. If a proper Slack connector exists, the skill says to use that instead. It needs one capability: a browser tool that runs JavaScript in the page and returns the value (a javascript_tool, for example), and a tab where the user is signed in.

Three Slack methods are the whole vocabulary:

conversations.history Read recent messages. channel, limit.
conversations.replies Read a thread. channel, ts.
reactions.add React. channel, timestamp (the message's ts), name.

A message has no other handle: it is identified by its ts. Posting a reply (chat.postMessage) is also on the menu, but behind a gate, below.

Reads are free. Posts are never silent.

Everything it does is as the user, and the skill grades its actions by how far they reach:

READalways yours
conversations.history, conversations.replies. No ask needed.
REACTif they asked
reactions.add, only when the user asked for the reaction. It shows as their reaction.
POSTshow, then yes
chat.postMessage sends content as the user. Show the draft, wait for a clear yes, each time.
  • It cannot sign in. A tab showing the Slack client is signed in; a login page means the user signs in, because the skill cannot.
  • It returns results, not credentials. The token is read and used inside the page. The skill says to return only results, and that a token in the result is a leaked credential.
  • It does not trust the open tab's view. The tab can show a new message minutes late; the API is current. The tab is the stale one.
  • It does not fight a broken method. This is Slack's undocumented web API and the user's own token, and it can change without notice. A failure means "this method no longer works", not a reason to retry harder.
  • It does not claim a write it did not see. Every write is verified by reading it back, and the skill says what it saw.

One file, one integration, nothing kept

The skill skills/slack-in-browser/SKILL.md: a single file, 54 lines. No scripts or hooks; the code is an example snippet inside the prose that the model adapts.
Declared kind: skill, state: false, and one integrates entry: chrome (browser automation). requires.manual: [Chrome, claude-in-chrome]; no deletion-policy.
Its state None. The token is read from the page's own storage at call time and never written anywhere by the skill: no cache, no config, no log of what was read.
Integrates with Chrome, through whichever browser tool can run JavaScript in a tab and return the value. That tool, and a tab where the user is signed in, are the whole dependency.
Called from Nothing in this repo. It fires from the situation its description names: Slack work with no Slack connector.

The credential never leaves the tab

The architecture is a boundary, and the order of steps is the order in which the agent crosses it. Outside is the agent. Inside is the page, which holds a token in localStorage and a session cookie. The only thing that crosses is one JavaScript expression in, and a short result out. Step through the real sequence; the line numbers are skills/slack-in-browser/SKILL.md:

← → arrow keys

The expression, line by line

22 const token = JSON.parse(localStorage.getItem('localConfig_v2')).teams['<TEAM>'].token;
23 const slack = async (method, params) =>
24   (await fetch('/api/' + method, { method: 'POST', body: new URLSearchParams({ token, ...params }), credentials: 'include' })).json();
25 const h = await slack('conversations.history', { channel: '<CHANNEL>', limit: '5' });
26 JSON.stringify(h.messages.map(m => ({ ts: m.ts, reactions: (m.reactions || []).map(r => r.name + ':' + r.count) })));
  • L22 reads the token from localStorage.localConfig_v2, the entry for one workspace's T… id. It is a local variable of the expression; nothing prints it.
  • L24 posts to /api/<method>, a relative URL. The page's origin serves it, and credentials: 'include' sends the session cookie too, so the request is authenticated the way the page's own calls are.
  • L26 is the last expression, so it is the return value, and it is a projection: ts and name:count per reaction, not the message objects and never the token. The same snippet is also the read-back check for a write: run reactions.add, then this, and the new reaction shows up in the list.

Where it goes wrong, and what the file says

  • Wrong door (L17). https://<workspace>.slack.com/archives/<channel> redirects to a "launching the desktop app" page. The skill opens app.slack.com/client/<TEAM>/<CHANNEL> instead, or follows the "open this link in your browser" link, and takes <TEAM> from the T… id in that URL.
  • Wrong evaluator (L29). Tools differ in how they evaluate scripts. Where top-level await works, use the bare form above; an async IIFE "may return {} instead of its result".
  • Empty message (L44). An email integration's alert has an empty text; the words live in files or attachments. So search JSON.stringify(message) for the phrase, and poll the API, not the tab.
Why this shape. Clicking through a UI makes the agent a second pair of hands on the user's screen. Calling the API from inside the tab makes it a client with the user's credentials and none of the user's screen: it cannot mistype into a composer, because it never touches one. The cost is that every guardrail has to be written down (identity, post-gate, read-back), because the API cannot tell a careful agent from a careless one.
