The failure it prevents

An agent asked to hit the PingOne Management API will, left alone, write the obvious thing: a curl with a client ID and secret pasted straight into the command. That command is now in the transcript, in the tool-call log, in the scrollback, and in whatever session archive comes later. The credential is a permanent artifact of a one-off question.

So the skill has exactly one rule at the top of it — always use scripts/ping-api.sh, never inline credentials in a curl command. The script reads ~/.ping/ping.yaml itself, so the secret goes from disk to an HTTP Basic header without passing through a shell argument on the way.

Two base paths, and you pick

The path you type is a suffix, not a URL — and there are two things it can be a suffix of. Default mode is relative to your environment. --raw drops the environment segment and makes it relative to /v1, which is where org-level things live.

# default — relative to /v1/environments/{environmentId}
ping-api.sh GET /users
ping-api.sh GET /signOnPolicies
ping-api.sh POST /users '{"email":"…","username":"jdoe","population":{"id":"…"}}'
ping-api.sh DELETE /users/abc-123-def

# --raw — relative to /v1, no environment prefix
ping-api.sh --raw GET /organizations
ping-api.sh --raw GET /environments

The script does not validate the path or guess the mode for you. Ask for /environments without --raw and you have politely requested the environments inside an environment. The skill's endpoint table — /users, /populations, /applications, /groups, /resources, /signOnPolicies, /identityProviders, /schemas, /brandingThemes, /certificates, /keys, and the per-user /grants and /roleAssignments — is a memory aid, not an allowlist.

Discovery is grep, and it says so

scripts/ping-lookup.sh is not a documentation browser. It downloads the PingOne Platform OpenAPI spec to ~/.ping/spec-cache/pingone-platform.yaml, re-fetching only when the file is missing or older than seven days, and then runs grep -n over it. What comes back is line numbers.

That's the intended shape: grep to find where a resource is defined, then open the spec at that offset with a normal file read to get the request body and response schema. The skill spells out that second step, because half a tool is only useful if you know which half you're holding.

The spec has a fallback source. If the official pingidentity/pingone-api-specs file can't be fetched, the script tries a community Go-SDK OpenAPI file instead, and only then gives up — telling you that you can drop a spec at that path by hand. Two upstreams, one cache, no silent empty results.

Two caches, both boring on purpose

  • The token. One client_credentials grant, cached at ~/.ping/token-cache.json with its own expiry timestamp minus a 60-second buffer. Every later call reuses it until that passes — typically an hour. There is no refresh command; you delete the file.
  • The spec. Seven days, as above. Also no refresh command; the age check is the whole mechanism.

Neither cache is invalidated by anything except time and rm. That is a limitation and it is also why there is nothing to debug.

What it deliberately does not do

  • It does not paginate. PingOne returns _links.next; the script does not follow it. You pass limit and cursor yourself — GET '/users?limit=100' — and page by hand if you need more.
  • It does not shape output. Raw response body to stdout. Every example in the skill ends in | jq for a reason.
  • It does not create credentials. You make the Worker app in the PingOne admin console, grant it the admin roles the calls need, and write the four values into ping.yaml yourself. The skill points at setup.md and stops.
  • It has no per-resource commands. No ping-api users list. Method plus path plus optional JSON body, for every resource PingOne has — including the ones added after this skill was written.

Region is one line of config

PingOne is regional and the domain changes with it. region: in ping.yaml takes NA (the default), EU, CA, AP or AU, and the script maps that to the matching pingone.com / .eu / .ca / .asia / .com.au pair for both the token endpoint and the API. Get it wrong and you get an auth failure against a tenant that doesn't hold your environment — which is exactly why it lives in the config file and not in the command.
