↓  WHY IT EXISTS

A mesh can't take "move the buttons to the top"

You want a lifelike 3D model of a real device at its real size. The quick route, an AI mesh generator, hands back a lumpy surface you can only regenerate: the first fix request is a new roll of the dice. The model-real-things-3d skill exists because the 2026-10-16 bakeoff for a NAS case settled it. Code-built models took a change request in about 8 minutes; the generated mesh (Hunyuan3D-2mv, 56.8 minutes, mostly a 4.9 GB checkpoint download) could not take one at all and was dropped before round 2.

When to fire it

Say "make a 3D model of my X", "model this device", "lifelike model", or "fix the model". It also fires for any job that needs Blender driven from an agent: a PC case, a router, a UPS, furniture.

  • You give it a size in mm with a source, and reference photos. Your own photos win over product photos.
  • It asks what photos can't show: which way it faces, where the buttons really are, what comes off.
  • Later fixes are plain requests; they edit the same build.py.

What it doesn't do

  • It does not trust its own scorer. In the bakeoff every model passed and still had the front buttons wrong; the owner's eye is the real check.
  • It does not generate meshes. No photo-to-3D; the model is geometry written in code, with fine detail (grilles, perforation) as alpha textures.
  • It does not sandbox Blender. The MCP runs agent-written Python with no sandbox; keep sensitive data off the machine.
  • Only one Blender MCP at a time. Blender Lab MCP and blender-mcp both use port 9876.
  • The default is not headless. It needs a Blender window; with none (CI, remote, overnight) it falls back to build123d + trimesh.

Where it lives

The skill skills/model-real-things-3d/: SKILL.md, setup.md, and two scripts, scripts/render.py and scripts/score.py.
Declared kind: skill, state: false. integrates blender and build123d.
Requires uv, plus three manual installs: Blender (brew install --cask blender, 5.1+), the official Blender Lab MCP add-on, and build123d + trimesh for the fallback. The full steps and gotchas are in setup.md.
Its state None. The skill keeps nothing. The model's state lives with the model: the owner's build.py, the GLB it writes, and a NOTES.md of each change's what and why, in the owner's project.
Evidence The 2026-10-16 bakeoff (NAS case, private notes).

Pin, script, score, hand over, edit

The model is a re-runnable build script, not a mesh. build.py runs inside Blender through the Blender Lab MCP's code tool and exports <name>.glb in glTF conventions: Y up, metres, front facing +Z, centred on the origin. Anything that will move (a side panel, a door, a lid) is its own named node with its origin at its own centre.

The judge is shared and scripted

Step 3 uses the same two files in every run. scripts/render.py runs under Blender --background --factory-startup --python scripts/render.py -- <glb> <png> with one camera and one set of lights (the MCP's live scene has no lights, so its viewport screenshots come out black). scripts/score.py loads the GLB with trimesh and prints JSON: per-axis size error, triangles, file size, watertight, and any required node names that are missing. Done means within_1pct is true, missing_nodes is empty, and it is under the default budget of 50k triangles and 5 MB.

Setup gotchas: the Blender Lab MCP server only starts when Blender runs with --online-mode (open -a Blender --args --online-mode), and its first launch spends about 70 seconds installing dependencies, past the client's 30 second timeout. Run uv sync in the unzipped bundle once first.
