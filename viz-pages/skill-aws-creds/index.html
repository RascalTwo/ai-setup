↓  WHY IT EXISTS

Three commands deep, and the credential quietly expired

You're mid-task and an aws call comes back ExpiredToken. The work is fine; a short-lived credential ran out. Now the task is on hold while you find a browser tab, sign in to the portal, expand an account tile, click copy and paste. The interruption costs more than the credentials ever did.

Every quick fix leaves the secret somewhere it shouldn't be

Three shortcuts get you unstuck faster: paste the three export lines into the chat, have the agent scrape them off the portal page with JavaScript, or run aws configure export-credentials. Each one works. Each one also leaves live credentials in a transcript, a scrollback or a file you didn't plan for. The skill is shaped around refusing all three, and it says so out loud: the export command is called out by name (SKILL.md line 83) as "the very credentials this path exists to avoid".

One skill, every portal, no one's company in it

A skill that hardcoded one organisation's start URL and account IDs would be wrong for the next account and unpublishable. So aws-creds keeps every portal-specific fact outside SKILL.md: a per-org wrapper skill hands them down, or portals.md holds them. The public copy of portals.md ships as a template with one fake example-org, and the rule is written into both files: never commit a real org to it.

Ask for credentials, or just let the call fail

The skill's own description names two ways in. Either you ask for AWS credentials or access, or an aws call fails with one of:

  • ExpiredToken
  • InvalidClientTokenId
  • Unable to locate credentials

"Get me AWS creds for dev", "log into AWS", or nothing at all, because the failed call is the invocation. The skill maps whatever you said, an org name, an account name, a bare "dev", onto a portal and an account. If that is ambiguous, or names an account that isn't listed, it asks instead of guessing which account to touch.

What comes back depends on the route, and the two are deliberately different. A profile run returns a profile name and a verified account ID; callers use aws --profile <name> … or AWS_PROFILE=<name>. A portal run returns a file path, the account ID, and the expiry, never the secrets. Consuming that file is one line, because the Bash tool doesn't persist env between calls: 

set -a && source ~/.agents/state/aws-creds/<portal>-<account>.env && set +a && aws sts get-caller-identity

What it refuses, and what it can't do

  • Never types a password. An IdP redirect is fine to complete; a password prompt means the browser session died, and the user signs in. Same rule on both routes.
  • Never guesses an account. Ambiguous or unlisted means it asks. After the fact it also checks sts get-caller-identity against the expected ID rather than trusting the tile it clicked.
  • Never pastes credentials into chat unless you explicitly ask, prints raw export lines only on request, and never commits the .env files.
  • Read-only by default. These credentials often carry write permissions; it won't run a mutating aws command unless that specific change was the ask.
  • Won't resurrect a dead session. Tab died or the portal shows signed out: restart from step 1. There is no reconnect path.
  • Short-lived by construction. The file is good for about an hour; later ExpiredToken or UnrecognizedClientException just means run it again. The fallback also writes AWS_REGION=us-east-1 into every file, and the template warns that a portal's SSO region and your workload region may differ. If yours does, say so.
  • Doesn't set up SSO for you. It reads ~/.aws/config to find a profile and never writes to it. No profile means the browser route, not a new profile.

Where it lives

Integrates AWS IAM Identity Center, as a browser-driven portal, and Chrome automation through the claude-in-chrome tools. The profile route talks to the same portal through the AWS CLI instead.
Requires aws (the profile route and the final identity check), chrome and claude-in-chrome (the portal route and the device-code approval). Nothing is installed or configured on your behalf.
Portal facts skills/aws-creds/portals.md, a template (start URL, IdP, SSO region, cache prefix, an alias to account-ID table), or a private per-org <org>-aws wrapper skill that pins one portal and hands the facts down. Account IDs are stored so a run can verify where it landed; an unconfirmed one is written ?, never a guess.
Its state Yes, on the portal route only. ~/.agents/state/aws-creds/, mode 700, holding one <portal>-<account>.env per account at mode 600. The profile route writes no file at all.
Safe to delete? Yes: deletion-policy: delete. Every file in there is a credential that expires in about an hour regardless. Deleting the directory costs one re-run; no history, config or cache goes with it.
Not its state ~/.aws/config is read to find a profile, never written. The aws CLI's own login handling belongs to the CLI, not to this skill.

Two routes, tried in order of how little they leak

aws-creds is one file of instructions (skills/aws-creds/SKILL.md, plus the portals.md template) and no code, so its architecture is the order of its attempts. The profile route comes first because it materializes nothing. The browser route is the fallback and does the heavy lifting, but every step in it is shaped to keep the secret out of the transcript.

← → arrow keys

The profile is tried first because it leaves nothing behind

SKILL.md line 63 is headed "Profile path: try this first". Find an SSO profile in ~/.aws/config by its sso_session or sso_start_url plus sso_account_id and sso_role_name, then prove it works with one call: 

aws sts get-caller-identity --profile <p> --query Account --output text

If the printed ID matches the expected account, the run is over. The CLI resolves the credentials itself on every later call, so nothing is materialized into a file or the transcript. That is the whole reason the route exists, and why aws configure export-credentials is forbidden on it.

Re-login by device code, so the agent never holds a password

When the profile fails with an SSO-token error, it runs aws sso login --sso-session <session> --use-device-code --no-browser in the background with output redirected to a file. The login prints a URL and a code; the skill opens the URL in Chrome and checks that the page's code matches the printed one. Redirecting to a file instead of piping to head is deliberate: a reader that closes early kills the producer with SIGPIPE. It then clicks Confirm and continue and Allow access (the botocore-client-<session> grant) and re-runs the identity test. A password prompt anywhere in that flow stops the run.

When there is no profile, the portal is a website and gets driven as one

Step 0 loads six Chrome tools in one batched ToolSearch: tabs_context_mcp, tabs_create_mcp, navigate, javascript_tool, find, computer. Then it navigates to the portal's start URL and takes a screenshot to see where it landed. An IdP page such as login.microsoftonline.com or Okta is an SSO redirect, so completing it is in scope: find the user's account row and click it. A password field is not: the browser session expired, and the skill hands it back.

The modal check is a regex, and the regex has a scar

Account rows are collapsed and the expand chevron is a small target, so it clicks the account name, then finds the Access keys link in that row. Before copying anything, javascript_tool walks every [role="dialog"] and reads the account out of the modal's own text (lines 108 to 137): 

d.textContent.match(/Create access for the account\s+(.+?)\s*\((\d+)\)/)

(.+?) was once \S+?, a single non-space token. Account names contain spaces, so the old pattern silently failed on every multi-word account and reported NO_CRED_DIALOG against a valid modal. The code comment records this, and so does the rule next to it:

NO_CRED_DIALOG means "no modal found", not "wrong account", and it is never a pass. If it comes back while a credentials modal is plainly open, the selector or regex has drifted from the portal's markup. Confirm the account from a screenshot before copying anything, and fix the snippet. Portals render several modals, so a stale one can still be in the DOM.

Copy, don't read

It finds the copy button for Option 1: Set AWS environment variables and clicks it. The three export lines go to the system clipboard and from there straight to disk. Reading the values out with javascript_tool and pasting them into a bash command would route live credentials through chat, which Step 3 forbids.

The write carries two scars, both real

# 1. the portal's code block is CRLF; a stray \r corrupts the
#    Authorization header -> "Invalid header value"
# 2. the block has NO trailing newline, so AWS_REGION lands on the
#    end of AWS_SESSION_TOKEN -> InvalidClientTokenId
mkdir -p ~/.agents/state/aws-creds && chmod 700 ~/.agents/state/aws-creds
umask 077
{ pbpaste | tr -d '\r' | sed -E 's/^export //; s/"//g'; echo; echo "AWS_REGION=us-east-1"; } > "$OUT"
chmod 600 "$OUT"

The bare echo is the whole fix for bug 2. The sed strips export and the quotes so the file is a plain dotenv that set -a; source turns into environment variables. On Linux, pbpaste becomes xclip -o -selection clipboard or wl-paste.

Debug by length, never by value

awk -F= 'NF{printf "%s len=%d\n", $1, length($0)-length($1)-1}' "$OUT"
# expect: AWS_ACCESS_KEY_ID len=20, AWS_SECRET_ACCESS_KEY len=40,
#         AWS_SESSION_TOKEN len~1000, AWS_REGION len=9

A session token ending in -east-1 means bug 2 bit. The last thing the run does before reporting success is source the file and compare sts get-caller-identity with the account ID from portals.md (or the wrapper skill). A mismatch prints WRONG ACCOUNT and exits 1, because the tile it clicked is a guess and the caller identity is not.

The troubleshooting table, as the skill keeps it

Invalid header value … \r CRLF in the pasted block. tr -d '\r'.
InvalidClientTokenId, right after writing Missing trailing newline merged AWS_REGION into the session token.
ExpiredToken / UnrecognizedClientException, later The roughly one hour lifetime. Re-run the skill.
Different account from get-caller-identity Wrong tile, or a stale modal still in the DOM. Re-check with the Step 2 snippet.
