OWNED SKILL · R2-SDLC-TESTING-PARADIGM

Mocks are the
last resort.

Tests sit on a spectrum from most real to most isolated. This chapter of r2-sdlc says: start at the most-real end the project can support, and step down only when forced. A fake has working logic that matches the real contract; a mock returns Y and asserts it was called. Fakes let you write behavior tests — mocks force structure tests.

It does not ban unit tests.
On date math and parsers, don't apologize for them.

This is a chapter, not a command. It's the testing taste that r2-sdlc loads before writing any test, and loads again when tests get reviewed. Writers follow these rules; the test-reviewer enforces them. Same document, both jobs — which is why a reviewer can never object to something a writer was never told.

Test as if you don't know how it works

The core stance is black box: you are a user of the thing under test, and "user" is context-dependent. For a UI, a human clicking around. For an HTTP API, a consumer making requests. For a library function, a caller. For a CLI, a shell invocation. Exercise the code the way that user would and assert on observable outcomes — never on internal structure.

Which makes one anti-pattern a naming problem rather than a style problem: the wrong layer of "user" — a test that claims to be behavior-level but is really poking a private helper.

Rung 4 is a sidestep, not a demotion

The hierarchy descends by realness, but unit tests get an explicit carve-out. Date math with timezones and DST, parsers and tokenizers, pricing and scoring, any function with N×M input combinations where each one matters — for those, a behavior test would have to synthesize dozens of scenarios through the full stack. Unit-test the function directly, exhaustively.

They're still GWT-formatted and still assert observable output. They just target a narrower user: the function's caller.

A test that cannot fail is a useless test

If you can delete the implementation and the test still passes, it isn't testing anything. Red-green-refactor prevents this by construction — you have to watch it fail for the right reason first — but the skill states it standalone anyway, because it's the single most common way tests become theater.

  • Tautologies — expect(x).toBe(x).
  • Missing or trivial assertions: the body runs code and never asserts anything meaningful.
  • Stubs that always return the expected value, then assertions against that value.
  • Tests that pass whether or not the code under test is invoked.
If the red phase never fails for the right reason, the test has a bug — and you fix the test, before writing any implementation.

Vertical, not horizontal — and this one has an override

Default mode: write one test, make it pass, write the next. AI agents have a strong pull toward the other shape because bulk-generating tests feels productive, and it produces the worst kind of tests — tests of imagined behavior. With no implementation to look at, they assert on the shape of things (data structures, signatures), so they pass when behavior breaks and fail when behavior is fine. The moment you learn something mid-build, every test ahead of you needs revising.

WRONG (horizontal):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

RIGHT (vertical):
  RED → GREEN: test1 → impl1
  RED → GREEN: test2 → impl2

The override is explicit: if you ask for horizontal — "draft all the test cases so I can review them", "scaffold the tests before any impl" — it does horizontal. Your call wins. It just never chooses it on its own.

Repeat the verb. Never write AND.

Every behavior test is Given/When/Then, verbs in ALL CAPS, and multiple clauses each get their own line rather than being joined:

GIVEN a user with no session
WHEN they request the dashboard
THEN they are redirected to /login
THEN a login-required event is logged   ← not "...to /login AND a login-required..."

In code there are two forms. Gherkin-style given()/when()/then() helpers are preferred where the stack already has them — and rare, because most projects don't emulate Gherkin. The skill's guard rail: don't invent machinery just to get this form. Otherwise use section-marker comments, where the comment must carry the clause, not just the verb — // GIVEN a user with no session, never a bare // GIVEN.

Even the title has a rule, and it's grammatical: it(...) reads as "it should …", so the string continues that sentence; test(...) takes a declarative. Match the caller the file already uses; don't mix them.

What a reviewer actually asks

Three questions per test, then findings as a prioritized list — severity (blocking / nit), location, suggested fix:

  • Who's the user, and what behavior is this exercising? If you can't answer in one sentence, the test is muddled.
  • Would this test catch the bug it was written to prevent? If not, it's theater.
  • Is there a simpler version using fewer mocks? If yes, propose it.

The flag list is concrete: mocks where a fake would work, expect(repo.save).toHaveBeenCalledWith(...) with no behavioral outcome behind it, malformed or missing GWT, behavior tests reaching into internals, bulk-written batches, and over-mocking — when 80% of a test is setup and 20% is assertion, the assertion is usually on the mocks.

When in doubt, it resolves the same way every time: default to the highest-realness tier the project can support. One high-signal behavior test beats five implementation-asserting mocks.
