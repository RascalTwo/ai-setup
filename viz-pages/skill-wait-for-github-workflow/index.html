OWNED SKILL · WAIT-FOR-GITHUB-WORKFLOW

Waiting is
one Bash call.

Hand it a run ID — or just latest — and it polls every 20 seconds until the run is done, then prints the conclusion and the URL. Add --job and it comes back the moment that one job lands, without waiting for the rest of the run.

It never reads the logs.
On a failure it hands you to /analyze-github-workflow-failure.

↓  WHY IT EXISTS

An agent is a terrible egg timer

Left to wait on its own, a model does one of two bad things. It re-invokes gh run view once per turn — every poll costing a tool call, an approval and a round trip through the model — or it guesses a sleep, comes back too early, and starts the guessing again. Both turn a nine-minute deploy into a conversation about a nine-minute deploy.

Putting the loop in bash makes the whole wait one tool call. The model is suspended for the duration and wakes up holding a conclusion, not a status.

The whole skill is one blocking call

The skill's Steps section is a single instruction: run the script, in one Bash call, with the timeout set to 600000 ms. Everything else — resolving latest, the polling, reporting the final result — happens inside that one call.

.claude/skills/wait-for-github-workflow/scripts/wait-for-github-workflow.sh \
    <run-id-or-latest> [workflow-file] [--job <job-name>]

# 22379581209                      an explicit run
# latest deploy_bravo.yml          newest run of that workflow
# latest deploy_bravo.yml --job ldap   leave as soon as that job lands

Two ways to name the run

Either the run ID, or the word latest. With latest plus a workflow filename it resolves the newest run of that workflow; with latest and nothing else it takes the newest run in the repo, whatever workflow that happens to be. Either way it echoes the run ID it settled on before it starts waiting — so a wrong guess is visible in the first line, not in the last.

Argument parsing is positional-then-flag: the first argument is always the run, and anything after it that isn't --job is taken as the workflow file. There is no --run flag and no way to pass a workflow without also passing a run.

Where it stops, and who it hands to

It waits and it reports. It does not fetch logs, diagnose, or fix. When the run or the job failed, both the script and the skill say the same thing: go run /analyze-github-workflow-failure <run-id>. One skill owns the waiting, a different one owns the reading.

  • The loop is unbounded. There is no internal deadline. The 600000 ms on the Bash call is the only wall, which is why the skill specifies it rather than leaving it to the default.
  • 20 seconds is not configurable. No flag, no env var. A run that finishes in three seconds still costs you up to twenty.
  • One run at a time. No fan-out across several runs, and --job takes one name, not a list.
  • It never cancels anything. Killing the wait does not touch the run; the run outlives the waiter.

The tick

Every 20 seconds it asks gh for the run's status and conclusion, glued into one string, and prints a timestamped line:

STATUS=$(gh run view "$RUN_ID" --json status,conclusion \
           -q '.status + ":" + (.conclusion // "")')
[[ "$STATUS" == completed:* ]] && break
sleep 20

Two fields in one string is what lets a single prefix test end the loop: completed: is the exit condition, and ${STATUS#completed:} is then the conclusion, with no second API call. The // "" matters because conclusion is null while a run is in flight, and null would have printed as the word null on every line.

The transcript of a wait is just that line repeating until it isn't in_progress any more — then the conclusion and the run URL. A non-success conclusion is a non-zero exit, not a note in the output. The wait doesn't just observe the failure, it inherits it.

--job: don't wait for the parts you don't care about

A deploy workflow with six jobs makes you wait for all six even when you only care about one. --job cuts that: the script watches for a matching job and returns as soon as that job completes — success or failure — without waiting for the full run.

# first pass: suffix match, case-insensitive
gh run view "$RUN_ID" --json jobs \
  -q "[.jobs[] | select(.name | ascii_downcase | endswith(\"$LOWER_TARGET\"))] | first // empty"

# nothing? second pass: substring
  … | select(.name | ascii_downcase | contains(\"$LOWER_TARGET\")) … | first // empty

Suffix first, substring second, first either way. That ordering is why --job ldap lands on Deploy LDAP (bravo) rather than on whichever job merely mentions LDAP somewhere in its name — and why, when several still match, you get the first one rather than an error.

The one that bites: a job that hasn't started yet and a job whose name you got wrong look identical — both print job '<name>' not started yet, once every 20 seconds. The script only tells them apart at the end: if the run completes and the job was never found, it errors, lists every job name in the run, and exits 1.
