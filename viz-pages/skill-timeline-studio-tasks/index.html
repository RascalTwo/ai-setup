↓  WHY IT EXISTS

You said it, and nothing wrote it down

A task list has one weakness no app fixes: it contains only what somebody typed into it. Work that comes up mid-conversation ("oh, and I owe someone those numbers, later this week") lives in a chat transcript, and a transcript is not a plan. When the session ends, the promise ends with it.

The second failure is quieter and worse. An agent starts a long job, the terminal closes or the context runs out, and nothing anywhere says the job ever began. The next session opens blank. There is no unfinished work to resume because, as far as every record is concerned, there was never any work.

That is the whole reason this skill is mostly policy and very little mechanism. Its own text says it holds "only what the served documentation cannot": where the plan is on this machine, and the rules for touching it.

It fires on a sentence, and once on its own

Nothing to invoke. The skill loads when you state something to do, defer it ("later", "remind me", "waiting on"), ask what is next, ready, blocked or due, or finish or abandon work. The agent also uses it on itself: anything it works on gets started before the work and finished after.

YOUAlso, I still owe somebody the budget numbers. Sometime this week.
AGENTAdded to your plan: "send budget numbers" (unrefined). Carrying on with the migration.

That reply is the standard: a few words of confirmation, no questions, no batching to the end of the session. The one thing that fires without any sentence is the hook. On SessionStart (matcher startup|resume) it checks the plan for agent work that was started and never finished, and says nothing at all if there is none.

What it will not do to your plan

  • It never certifies its own work. The skill never sends setRefined. refinedAt means you read this and agreed, and the plan's /api/ready gates on it, so an agent that refined its own tasks could declare its own work ready.
  • It never edits a refined task's label, description or duration. Each of those silently clears your sign-off, with no event and no log line. If an edit of its does drop one, it says so; it does not quietly put it back.
  • It does not decompose work that finishes in one session. Start and finish on one task, nothing else. Its own wording: eight sequential rows is "a list drawn in a graph tool", and the graph is what the plan is for.
  • It does not take in-flight work. A task that started and has not finished may belong to a session still running. Resuming one is deliberate, and said out loud.
  • It does not carry the API manual. It reads <base>/api/openapi.json before writing, because the schema is held to the code by tests and a copy in a skill is not.
  • It does not leak the credential. The token goes in an x-timeline-token header and nowhere else: not a URL, not a log, not a commit. The config that holds it sits outside this repository on purpose.
  • The hook never lists your backlog, never claims anything is dead, and never speaks to a subagent. Its normal output is nothing; a hook whose normal output is a list gets tuned out within a week.

What it plugs into, and what is safe to delete

The skill skills/timeline-studio-tasks/SKILL.md: location, capture policy, rules for recording its own work. hooks/inflight.py: the session-start reader.
Declared kind: skill, state: false, integrates timeline-studio and claude-code, requires: [timeline-studio].
Integrates Timeline Studio, over its HTTP API, with the token header. And Claude Code, through a SessionStart hook registered by the snippet in SKILL.md.
Requires A reachable Timeline Studio and a share link: the token is the part after the #. Nothing is installed; the hook is plain Python with the standard library.
Its state None of its own. The plan lives in the service, not on this machine. The one local file, ~/.config/timeline-studio/config.json (base, page, token), is Timeline Studio's credential, kept out of the repo so it cannot be committed.
Safe to delete? Nothing to retain, so there is no deletion policy. Remove the config and the skill goes blind until you hand it the share link again; the hook fails open and stays silent, so sessions are unaffected.

Writing is a policy. Reading is a hook.

The two halves are built differently on purpose, and the hook's own header says why. Writing has a natural trigger: an agent doing work records it. Reading has none: nothing about opening a session reminds anybody that the last one died partway, which is the exact case the arrangement exists for. "A good intention is the wrong mechanism for a thing that must not be forgotten", so reading is a hook.

The thing both halves agree on is one marker. An agent task is born shape: "ai" with noQueue: true (it is flagged as machine-made, and its days stay out of your capacity). Start puts a first session on it; finish sets done. In between is the window the hook watches.

Amber is the branch nobody used to see. Everything the hook does is a search for tasks sitting in that box.

Two schema versions, one test of "finished"

The plan changed shape underneath the hook: older plans carry actualStart and actualEnd on a task, newer ones carry a sessions list and a done flag. began() and ended() (lines 79 to 84) read both, so the hook works on either side of the upgrade. In the newer shape a task counts as ended only if done is set; a recorded session alone is not a finish, which is what lets an interrupted run show up at all.

The clock wording is the whole liveness protocol

The hook cannot know a session is dead, because another one may be running right now. So it never says "dead". It says when the task started, and picks the wording from humanise() (lines 33 to 50) so that live and abandoned read differently at a glance. Pick an age to see the real output:

Liveness comes from the whole channel, not from one row. An agent partway through a decomposed job is finishing siblings; the task still in flight can sit untouched for an hour while its pieces move. So the "last agent activity" line takes the freshest stamp across every shape: "ai" task (line 94), which is the real answer to "is anyone still working".

One honest ceiling: it reads the plan once, with a 2 second timeout, and the plan store being down is a thing that actually happens. In that case you get silence, not a hung session. That is deliberate and checked, not assumed: with the plan stubbed to return one open task, a main session got the report; a subagent session and an unreachable plan both got nothing and exited 0.
