↓  WHY IT EXISTS

You said it, and nothing wrote it down

A task list has one weakness no app fixes: it contains only what somebody typed into it. Work that comes up mid-conversation ("oh, and I owe someone those numbers, later this week") lives in a chat transcript, and a transcript is not a plan. When the session ends, the promise ends with it.

The second failure is quieter and worse. An agent starts a long job, the terminal closes or the context runs out, and nothing anywhere says the job ever began. Ask the plan afterwards and there is no unfinished work to find because, as far as every record is concerned, there was never any work.

BEFORE · 1
The aside Said once, in passing, never filed. The plan is only as complete as the last thing someone had the energy to type.
Now: it is added when said, even vague. A bad label is cheap to fix.
BEFORE · 2
The dead session Half a job done, no record it began. Asking the plan afterwards shows nothing, so nobody knows there was anything to resume.
Now: start before the work, finish after. A start with no finish is a trail.
BEFORE · 3
The second copy How to drive the plan, pasted into the skill, drifted from the real API without anyone noticing.
Now: the skill keeps only location and policy. The plan serves its own manual.

That is the whole reason this skill is mostly policy and very little mechanism. Its own text says it holds "only what the served documentation cannot": where the plan is on this machine, and the rules for touching it.

It fires on a sentence

Nothing to invoke. The skill loads when you state something to do, defer it ("later", "remind me", "waiting on"), ask what is next, ready, blocked or due, or finish or abandon work. The agent also uses it on itself: anything it works on gets started before the work and finished after.

YOUAlso, I still owe somebody the budget numbers. Sometime this week.
AGENTAdded to your plan: "send budget numbers" (unrefined). Carrying on with the migration.

That reply is the standard: a few words of confirmation, no questions, no batching to the end of the session. Reading it back is the same: ask what is next, ready, blocked or due, and the skill reads the plan then. Nothing runs at session start.

What it will not do to your plan

  • It never certifies its own work. The skill never sends setRefined. refinedAt means you read this and agreed, and the plan's /api/ready gates on it, so an agent that refined its own tasks could declare its own work ready.
  • It never edits a refined task's label, description or duration. Each of those silently clears your sign-off, with no event and no log line. If an edit of its does drop one, it says so; it does not quietly put it back.
  • It does not decompose work that finishes in one session. Start and finish on one task, nothing else. Its own wording: eight sequential rows is "a list drawn in a graph tool", and the graph is what the plan is for.
  • It does not take in-flight work. A task that started and has not finished may belong to a session still running. Resuming one is deliberate, and said out loud.
  • It does not carry the API manual. It reads <base>/api/openapi.json before writing, because the schema is held to the code by tests and a copy in a skill is not.
  • It does not leak the credential. The token goes in an x-timeline-token header and nowhere else: not a URL, not a log, not a commit. The config that holds it sits outside this repository on purpose.

What it plugs into, and what is safe to delete

The skill skills/timeline-studio-tasks/SKILL.md: location, capture policy, rules for recording its own work.
Declared kind: skill, state: false, integrates timeline-studio, requires.manual: [timeline-studio].
Integrates Timeline Studio, over its HTTP API, with the token header.
Requires A reachable Timeline Studio and a share link: the token is the part after the #. Nothing else is installed; the skill is a single SKILL.md.
Its state None of its own. The plan lives in the service, not on this machine. The one local file, ~/.config/timeline-studio/config.json (base, page, token), is Timeline Studio's credential, kept out of the repo so it cannot be committed.
Safe to delete? Nothing to retain, so there is no deletion policy. Remove the config and the skill goes blind until you hand it the share link again.

One marker: an agent task is born flagged, started, then finished

The skill records its own work with one convention. An agent task is born shape: "ai" with noQueue: true (it is flagged as machine-made, and its days stay out of your capacity). Start puts a first session on it, before the work; finish sets done, after. A task started and never finished is how a dead session leaves a trail instead of a silence.

Amber is the branch nobody used to see. It stays in the plan until a session, yours or a later one, reads it and decides, deliberately, what to do.

Estimate agent work in gate runs, not keystrokes

A pilot task was estimated at 60 minutes the way a person would be: 25 for the change, 15 for harness checks, the rest for gate runs and a re-read. It took about 16 minutes to the review request. The edit took minutes; the time went on about five suite runs and one unexpected interaction with an existing check.

60 min
actual, to the review request
~16

So the skill's rule: keep edit time small, add about 90 s per full gate run (plan on 3 to 5, including a mutation run to prove each new check can fail), and about 5 minutes for one unexpected interaction. The human's own steps (a browser demo, the review round) go on top; they are theirs, not the agent's. The actual time is recorded in the task's final comment.
