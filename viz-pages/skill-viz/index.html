Name the form, then write

The failure mode this skill is built against is an agent asked to “visualize” something and returning styled text — a page of colored boxes with words in them. So Step 2 is a hard sequence: name the spatial form, announce the choice in one sentence, then open the editor. Not a question — a checkpoint you can interrupt. “Rendering this as a force-directed graph, edges weighted by call count.”

The fallback ladder on the card is deliberately generous at the bottom: a styled page is allowed, and beats text in a terminal. But if the content has magnitudes, relationships, sequences, hierarchy or topology, there is a real form for it, and that's what you go find. One exception — if you asked for a UI to be designed, the UI is the artifact.

Five scaffolds, so the chrome isn't rebuilt each time

viz create <slug> [--local [dir]] [--deck|--poster|--poster-dive|--exchange|--hero]
viz verify <url|id> [--og] [--size WxH] [--interactions <file>] [--commit <msg>]
viz ls · search · history · rollback · publish · server   # viz <verb> --help

A blank page is the default. When the viz has a known shape, a scaffold replaces it — each one stamps viz:scaffold so the page states what generated it, and each carries its authoring guide inline.

  • --deck — an arrow-key presentation: scale-to-fit 16:9, fullscreen, progress bar, reversible per-slide fragments.
  • --poster — a page that is its own 1200×630 share card, clipped straight to og.auto.png.
  • --poster-dive — that card as the top of a scrollable page, with the deep dive below it. This page is one.
  • --exchange — an animated diagram of something passed or proven between parties: actors in phase bands, packets on declared wires, stepped narration.
  • --hero — not a scaffold but an add-on: a share card for a viz that stays an ordinary page.

Three things it is not, and one it refuses to claim

  • Not a static SVG that fits inline. If the answer is six boxes and four arrows in a chat reply, drawing it inline is cheaper than a page, a server and a verify run.
  • Not a freeform canvas. Dragging shapes around a board is tldraw's job. A viz is authored, versioned and reloaded from a file, not manipulated by hand.
  • Not your real production UI. Nothing here is a component library. It stamps a page with a kit of tokens and gets out of the way.
  • The layout report is not taste. ⚠ 0 layout finding(s) means “nothing is broken”, not “it looks good”. Whether the thing reads is a human or an agent looking at the PNG, which the skill requires at least once before finishing.

And without a shell it drops to lite mode and writes one self-contained HTML file: no server, no hot reload, no api.ts, no verify run. That is the honest ceiling in a chat-app sandbox, not a degraded bug.

Safe to delete?No — deletion-policy: retain. That directory is git init-ed on first create and every viz is committed into it. It holds authored work, not a cache: deleting it is data loss, and nothing regenerates it.

Boxes and arrows, without the rework

Hand-drawn SVG diagrams are where past vizzes bled the most iteration: labels overflowing, arrows pointing at empty space, whole layouts redone late. Always the same root cause — coordinates typed as independent literals, then guessed wrong. The fix is structural.

  • Define each node once as {x, y, w, h}; derive every arrow endpoint and label from that geometry with connect(a, b) / side(node, "right"). Now moving a box can't strand its arrows.
  • labelBox() for anything multi-word — a <foreignObject>, so the browser wraps and text cannot spill. Raw <text> has no overflow protection.
  • Past ~5 nodes with crossing edges, stop hand-placing: hand nodes and edges to elkjs, get coordinates back, and still draw the SVG yourself. (Not dagre — unmaintained, last release 2019.)
The silent one: {x, y, w, h} is the node shape, not the SVG attribute set. <rect w= h=> is not an error — SVG ignores unknown attributes, so the box renders at zero size: invisible, clean console, nothing to debug. It's width/height. The tell is verify's census saying rendered: 0 rect when you drew twelve.

Done means rendered, and something else checks

A viz isn't finished when the code is written — it's finished when it renders. verify.ts hands off to lib/verify/verifyViz(), which drives headless Chrome once through puppeteer-core (your installed Chrome, no Chromium download) and writes a screenshot, console, network log and final DOM into .verify/. Every run also prints a layout report, no opt-in:

✓ 0 error(s) — .verify/{console.txt, latest.png, network.txt, dom.html}
⚠ 3 layout finding(s) · rendered: 17 rect, 11 path, 40 text
  text-overflow: text.nsub "Claude Haiku 4.5 · cloud twin" spills 37px past its box
  clipped: div.vsvg-label "build/dependency-graph-data.json…" is cut off by 87px
  og-card-overflow: 1 element(s) escape the card frame — div.stat-row

It checks what eyes are bad at: text past its own box, content silently clipped by an overflow:hidden ancestor, anything wider than the viewport, content escaping a 1200×630 card, a blank render. The mark census separates rendered nothing from rendered wrong instantly.

A plain run only ever sees state 1 — which is how nearly every interactive viz in the corpus shipped unlooked-at past its opening frame. Drop a disposable verify.interactions.ts beside the page to click through steps, tabs and drawers and snap your own extra PNGs. And --commit commits only on a clean run, so a broken render can't quietly reach the history.

A kit, so nobody re-derives the palette again

Every color is a token — --accent, --good, --warn, --danger, --c1…--c8 — and var() works in SVG presentation attributes, so fill="var(--accent)" follows a re-theme. Want a different palette? Override the :root block in six lines and keep every component; don't rebuild.

The discipline that goes with it: override the property, don't restate the rule. Re-declaring a whole kit block is how a component silently becomes a fork — its values get retyped, then stop tracking the kit when it improves. Measured across the corpus, more than half of all kit-component overrides restate six or more properties to change one. New helpers get jotted in CANDIDATES.md and only promoted once a pattern has actually recurred (~3+ vizzes).

One server, many roots, and posture is never inherited

A single Bun server on 127.0.0.1:5180 (PORT, overridable with $VIZ_PORT) serves from many roots: the central library plus any viz-pages/ folder inside your own repos. allContainers() unions the central dir, the skill's own bundled pages and the registry; buildSlugMap() turns that into routes. A viz's identity is idFor(dir, $HOME) — its path relative to home, which is also its URL — so two repos can both have a dashboard viz and never collide. A repo-local viz is registered on creation with addContainer(), so the central server serves it immediately; --runtime additionally vendors a self-contained server into the repo, so a cloner can run it with no skill installed.

That vendoring is deliberately opt-in, and it used to be automatic. Until 2026-08-17 every --local run committed the whole serve runtime into the host repo; an audit found two repos where the standalone property was actually used and eight carrying tracked files nothing read, quietly drifting from canonical. Ask for it only when a cloner really will run the vizzes without the skill.

Every page is stamped viz:posture / viz:listed as <meta> tags — there are no CLI flags for them, and an undeclared posture makes the whole build refuse. New pages start local + unlisted; forking a page copies everything but always resets to local/unlisted, because posture is a trust decision and is never inherited. build.ts writes artifacts and never deploys — that stays a separate, human-confirmed step.

The comment layer has a rule about who deletes

Every live viz injects a review layer through commentOverlay(id): Alt-click any element to pin a comment that anchors to it and follows it through animation. It's how located visual feedback gets handed back to the agent. The division of labour is fixed — you resolve; you never delete. The user deletes; the user never resolves. Comments live beside the page in comments.json, git-ignored, never committed.
