The double trigger

Deploy workflows usually list branches under on.push.branches. If yours does and you still have commits sitting locally, then git push starts the run all by itself — and a gh workflow run on top of it starts a second one. The skill marks that check REQUIRED and gives the reason in the step title: prevents double triggers. It is the only step written that way.

So the order matters. Read the workflow file first, decide second, run one command third. Not: dispatch and hope.

The one thing it will ask you

The workflow to trigger. If which one isn't clear from context, it lists .github/workflows/ and asks rather than guessing — picking the wrong file here means deploying the wrong thing. Everything after that it works out from the repo: the branch from git, the trigger route from the YAML, the run ID from the API.

There is no branch argument. It deploys the branch you are standing on, always, which is why the skill is named for the current branch rather than for an environment.

Where it hands off

  • It does not watch the run. It reports a run ID and stops; wait-for-github-workflow owns the waiting, so the watching half stays reusable against any run ID you already have.
  • It does not pass workflow inputs. gh workflow run <file> --ref <branch>, no -f. A workflow with required inputs is outside what this does.
  • It checks for a push trigger, not for a workflow_dispatch one. Nothing inspects whether manual dispatch is even enabled — a workflow without on: workflow_dispatch makes gh workflow run fail, and you find that out from gh, not from the skill.
  • It never force-pushes, amends or rebases. The only write it performs is a plain git push of commits you already made.

Where it lives

IntegratesGitHub Actions workflow dispatch, via the gh CLI — gh workflow run to start one, gh run list to find the run it started. Everything else is local git and a grep over a YAML file.

The whole skill is a decision with two possible actions, and the decision is made from files rather than from memory.

Matching the branch is three rules, not one

Having a push trigger isn't enough — the trigger has to cover this branch. The skill pulls the branch list out of the YAML and compares against the current branch three ways.

# the current branch — never an argument you pass in
git branch --show-current

# pull on.push.branches out of the workflow file
grep -A 20 '^on:' .github/workflows/<file> \
  | sed -n '/push:/,/^  [a-z]/p' | grep '^\s*-' | sed 's/.*- //'

A branch matches if it appears literally (main, fix-bravo), if it matches a glob (feature/* covers feature/foo), or if the list contains '**' — every branch. Miss the glob case and you'd dispatch a workflow the push was already going to run.

That extraction is line-shaped, and lines lie. -A 20 reads twenty lines after on: and the sed range ends at the next two-space key, so an on: block longer than twenty lines, or the inline on: [push] form, yields an empty list. An empty list reads as "no push trigger", which routes to manual dispatch — safe in the moment, but it means the check is a heuristic over text, not a YAML parse, and it fails toward dispatching.

The no-op nobody expects

A push trigger does not mean pushing is the route. If the branch is already up to date with the remote there is nothing to push, so the push trigger won't fire — and the skill says so explicitly, then falls through to manual dispatch. That fall-through is why two of the three exits land in the same box: one branch never had a push trigger, the other had one that couldn't fire.

The test is git log @{u}.. --oneline 2>/dev/null, and the redirect is doing something: on a branch with no upstream at all, @{u} is an error, the output is empty, and empty means "nothing to push" — so a brand-new local branch takes the manual-dispatch route too. Right answer, arrived at by accident.

The inverse is the rule that saves you the duplicate run: when there are unpushed commits, git push is the whole action. The skill's words are "do NOT also run gh workflow run."

Then it stops watching

Once something has been started, the skill sleeps 15 seconds and asks GitHub for the newest run of that workflow, by ID:

sleep 15 && gh run list --limit 1 --workflow <file> \
  --json databaseId -q '.[0].databaseId'

The sleep is there because a run is not queryable the instant it is created, and --limit 1 is an optimistic bet that the newest run of that workflow is yours — true in the ordinary case, wrong if a teammate pushed in the same fifteen seconds. It reports that run ID and hands the run off to wait-for-github-workflow. Triggering and watching are two skills, not one.
