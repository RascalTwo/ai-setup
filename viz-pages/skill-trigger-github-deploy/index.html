The double trigger

Deploy workflows usually list branches under on.push.branches. If yours does and you still have commits sitting locally, then git push starts the run all by itself — and a gh workflow run on top of it starts a second one. The skill marks that check REQUIRED and gives the reason in the step title: prevents double triggers. It is the only step written that way.

So the order matters. Read the workflow file first, decide second, run one command third. Not: dispatch and hope.

Matching the branch is three rules, not one

Having a push trigger isn't enough — the trigger has to cover this branch. The skill pulls the branch list out of the YAML and compares against the current branch three ways.

# the current branch — never an argument you pass in
git branch --show-current

# pull on.push.branches out of the workflow file
grep -A 20 '^on:' .github/workflows/<file> \
  | sed -n '/push:/,/^  [a-z]/p' | grep '^\s*-' | sed 's/.*- //'

A branch matches if it appears literally (main, fix-bravo), if it matches a glob (feature/* covers feature/foo), or if the list contains '**' — every branch. Miss the glob case and you'd dispatch a workflow the push was already going to run.

The no-op nobody expects

A push trigger does not mean pushing is the route. If the branch is already up to date with the remote there is nothing to push, so the push trigger won't fire — and the skill says so explicitly, then falls through to manual dispatch. That fall-through is why two of the three exits above land in the same box: one branch never had a push trigger, the other had one that couldn't fire.

The inverse is the rule that saves you the duplicate run: when there are unpushed commits, git push is the whole action. The skill's words are "do NOT also run gh workflow run."

Then it stops watching

Once something has been started, the skill sleeps 15 seconds and asks GitHub for the newest run of that workflow, by ID:

sleep 15 && gh run list --limit 1 --workflow <file> \
  --json databaseId -q '.[0].databaseId'

It reports that run ID — and hands the run off to /wait-for-github-workflow to monitor. Triggering and watching are two skills, not one, so the watching half is reusable against any run ID you already have.

The one thing it will ask you

The workflow to trigger. If which one isn't clear from context, it lists .github/workflows/ and asks rather than guessing — picking the wrong file here means deploying the wrong thing. Everything after that it works out from the repo: the branch from git, the trigger route from the YAML, the run ID from the API.
