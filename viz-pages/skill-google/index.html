↓  WHY IT EXISTS

One Claude account, one Google account

The claude.ai Gmail, Calendar and Drive connectors each bind exactly one Google account per Claude account (open feature request anthropics/claude-code#100407). If you have a work account and a personal one, half your inbox and calendar is invisible to the assistant, and "did I get that email?" has the wrong answer half the time.

The obvious fix, gws --account, is gone: gws 0.22 removed its own multi-account support (changelog commit e1505af). What is left is the mechanism this skill uses, one config directory per account.

When it fires

Any email, calendar or Drive task: "my inbox", "check my personal email", "what's on my calendar", or whenever an account is named. Which account it uses is decided by one rule:

  • Named (alias, email, or any spoken name for it) → that account.
  • Unnamed read (search, "did I get…", agenda) → every account, each result labeled with its alias.
  • Unnamed write (send, reply, create, edit, delete, accept) → it asks which account first.

What it doesn't do

  • No multi-account in one process. Each gws call sees exactly one account; cross-account reads are separate calls.
  • Each account needs an OAuth client whose Google Cloud project allows it. An org-internal project rejects outside accounts with org_internal.
  • Testing-mode projects expire refresh tokens every 7 days. You re-run login weekly unless the project is in production.
  • It doesn't replace claude.ai's web or cloud features. Anything that needs the hosted connectors still uses them.
  • It never guesses on writes. No account named means a question, not a coin flip.

How it's wired in

The skill skills/google/SKILL.md, plus the account map accounts.json.
Declared kind: skill, state: false.
Integrates google: the Gmail, Calendar, Drive, Docs and Sheets APIs, reached through the gws CLI.
Requires The gws command (Homebrew googleworkspace-cli, v0.22.5), and one manual step: a Desktop-app OAuth client per Google Cloud project your accounts can use.
Its state None kept by the skill. Credentials live in each account's own ~/.config/gws-<alias> directory, owned by gws. Deleting one just means logging that account in again.
Account map accounts.json (alias, email, spoken names, notes) is gitignored. accounts.example.json is the committed template.

One call, one account

Every call carries two environment variables. GOOGLE_WORKSPACE_CLI_CONFIG_DIR selects the account's config dir. GOOGLE_APPLICATION_CREDENTIALS=/dev/null/none stops gws borrowing a quota project from gcloud's ADC file, which otherwise 403s for accounts outside that project. 

# every call, both vars
GOOGLE_APPLICATION_CREDENTIALS=/dev/null/none \
GOOGLE_WORKSPACE_CLI_CONFIG_DIR=~/.config/gws-<alias> \
  gws gmail +triage

Adding or repairing an account

mkdir -m 700 ~/.config/gws-<alias>, drop a Desktop-app client_secret.json in it, enable the five APIs in that project, then run gws auth login with full-URL scopes (bare names like gmail are rejected). Verify with gws gmail users getProfile, then add the alias to accounts.json. On invalid_grant or a 401, run the same login again.

Docs online are stale: they still show --account, auth list and GOOGLE_WORKSPACE_CLI_ACCOUNT. gws 0.22 removed all three. If the account isn't a member of the OAuth client's project, delete project_id from that client_secret.json or calls 403 on quota.
