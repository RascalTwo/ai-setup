↓  WHY IT EXISTS

Nobody grades a screen but the one who made it

Code has tests. A page, a demo or a 3D render has none: the builder looks at its own work, says it looks right, and stops. It built the thing, so it also fills in what it meant to show, and misses the label that is cut off or the grey text nobody can read.

The obvious fix is a second AI to critique the first. The risk is that a critic which invents problems, scores the same screen differently each time, or disagrees with a real person steers the builder towards its own noise, and every round still looks like progress. So this skill's critic was tested before the loop existed, with every result shown next to what a critic with no judgement would score.

Before visual work is handed over

The agent runs it on its own before handing over visual work it built or changed: a UI, a viz page, a demo, a 3D render, an animation frame. A tweak too small to change how a screen reads skips it. You can also ask for a critic loop, a visual critic or an art-director pass. The agent then goes round like this:

  1. Writes a brief: one paragraph on what the screens are for and every choice that looks like a bug but is not. Plus up to five task checks, such as "the before and after sit side by side".
  2. Takes screenshots, at 1280 and 390 px wide for a web page.
  3. Asks the critic, which scores them and lists issues, worst first, each with a box on the screenshot.
  4. Fixes the blockers and majors, then takes new screenshots and asks again.
  5. Stops when the stop rule fires and hands over the score trend and anything still open. 
# one round, from the skill's folder
node shoot.ts <url> $RUN/shots-1
node round.ts $RUN --brief brief.md --checks checks.md $RUN/shots-1
# prints the trend, ranked issues and boxes, then CONTINUE or STOP

What is not proved, and what it will not do

The loop is tested on 10 one-page tasks, not beyond. An Opus builder made each page alone, then the same build went through the loop. On 3 tasks the critic found nothing serious, so the loop changed nothing. On the other 7, a person picked blind and preferred the loop's build on 6 and could not tell on 1 (p = 0.016); an Opus judge, sides swapped, preferred it on all 7. It cost about $1 more per task. Not tested: a builder that checks its own screenshots without a critic, or work bigger than one page.
  • It will invent problems if you skip the brief. On clean screens it raised 0.7 blocker or major issues each, and a person judged all 7 sampled to be made up. With a brief that fell to 0.3, and fault detection did not drop.
  • It is stricter than a person about small grey text, and on one page it caught a slight misalignment or a half-clipped label in only 2 or 3 of 5 runs.
  • It has not been shown to judge subtle differences. The pairs a person could decide mostly had an obvious gap, such as one side empty or still loading. Eight of the ten fault pages were skill posters in one house style.
  • It cannot say "good enough" for you. It scores and ranks; it does not know where your bar sits. Only a run that ends STOP clean means nothing serious is left by its reading. After a plateau or cap the agent lists every serious item still open.
  • It writes no code and checks no behaviour. It sees pictures, so a button that looks right and does nothing passes. It takes PNG screenshots only.
  • It is a different critic after any edit. Changing the prompt, schema, model, effort or the brief wording sends it back to be re-proved before it is trusted again.

What it needs, and what it keeps

The skill skills/visual-critic-loop/: SKILL.md, critic.ts, round.ts, shoot.ts, prompt.md, schema.json, and proof/ (the test harness and PROOF.md).
Declared kind: skill, state: true, deletion-policy: retain. No integrates.
Requires node and claude on the PATH, and Chrome: shoot.ts drives it headless through the viz skill's installed puppeteer-core. Nothing else; there is no server and no daemon.
Its state ~/.agents/state/visual-critic-loop/. runs/<slug>-<date>/ holds one run: the frozen brief and checks, each round's screenshots and round-N.json. Safe to delete once a run is handed over. proof/ holds the planted-fault pages, the before/after pairs and the person's blind picks; delete it and the proof cannot be re-checked, which is why the policy is retain.
Called from Nothing calls it. A person asks for it, and the agent follows SKILL.md. The decision to prove the critic first is docs/adr/2026-11-15-prove-the-visual-critic-before-the-loop-trusts-it.md.

One round, from screenshot to verdict

The critic is one script, critic.ts, that both the proof harness and the loop call, so the critic that was tested is the one that runs. It is a separate claude -p process started with no tools, no settings, no CLAUDE.md, no skills and no MCP, in an empty temporary folder. It gets the PNGs, the brief and the checks, and nothing else.

The stop rule

decide() in round.ts checks these in order, after every round. Its numbers come from the proof, not from a demo: the critic's own wobble on a repeated screen is about 0.2 points, so a rise under 0.5 is noise.

  • clean: no blocker or major issue left, and every task check passes.
  • plateau: from round 3, the better of the last two scores is less than 0.5 above the score before them.
  • cap: 4 rounds done.

The critic, tested before the loop was built

Three questions, each answered beside a critic with no judgement, so a result reads against chance rather than against a bar picked after the fact. No pass mark was fixed in advance: the person who owns this setup judged the results. The 90% is with a brief, which is how the loop runs it; the full table is in skills/visual-critic-loop/proof/PROOF.md.
