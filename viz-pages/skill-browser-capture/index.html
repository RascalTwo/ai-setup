Pick the route before you touch anything

Turning a browser flow into files you can embed has three routes, and they are in strict order of preference. The reason the skill opens with the choice rather than a procedure: every obvious shortcut here fails silently, which is how this costs hours instead of minutes.

  • Route 1 — MCP capture, the user's own Chrome. The default; prefer always. Real login/SSO, real data, real device pixel ratio. About a second of human-visible disruption and zero clicks from them. Nothing else can do that.
  • Route 2 — a spawned browser (record-flow.js). No session at all, but it never touches the screen. For when Route 1 is impossible: no GUI, CI or background, the screen must not be disturbed, or the choreography has to be deterministic and scripted.
  • Route 3 — the GIF recorder (gif_creator). Only when a click-annotated how-to GIF is specifically what's wanted and smooth motion isn't needed.

You can always convert a Route 1 or Route 2 video to GIF with ffmpeg — which usually looks better than the GIF recorder anyway. Dependencies: ffmpeg on PATH; Route 2 also wants puppeteer-core, and record-flow.js finds the one the viz skill already ships.

The GIF trap. gif_creator yields a slideshow, always — one frame per action, and extra screenshot calls add zero frames. If a GIF looks janky or choppy, that is not a quality bug to iterate on; it is Route 3 working exactly as designed. Switch routes, don't try harder.

The error is a sentence, not a mystery

InvalidStateError: Invalid state means one thing: the tab wasn't visible. macOS marks a Chrome page hidden when its window is occluded by another app — so an editor sitting on top is enough, even though the tab is selected and the page is "open". Re-raise, re-screenshot, re-click.

The flip side is the useful half. Once capture is live, Chrome pins the tab visible and the whole constraint evaporates — proven, not assumed. The one thing that is not proven is switching to a different Chrome tab mid-capture: occlusion is verified safe, tab-switching is probably fine and has simply never been tested. Until it is, the skill says to tell the user not to do it.

Say something before the screen goes red

Arming the click target throws a red overlay across the user's entire screen, and then a script yanks Chrome in front of whatever they were doing. You click that overlay — the MCP's clicks are trusted, so the human never has to touch it. They don't know that.

"I had no idea I, as a human, was supposed to click that."

That is a verbatim user report, and it is why step 0 of the procedure is one line in chat before anything happens. Same reason the overlay's default label is worded at the person — "Claude is starting a screen recording / No action needed" — rather than as the imperative "CLICK TO START RECORDING". Override the label if you like; keep that property.

Where it actually goes wrong: the click

Screenshot dimensions change between calls — 1456×840 then 1502×818 were observed for the same 1728px viewport — so any scale factor computed earlier silently misses. Always screenshot immediately before clicking and use that image's coordinates. The target covers the whole viewport for exactly this reason.

If a click seems to do nothing, find out whether events are landing at all before changing any JS:

window.__clicks = [];
document.addEventListener('click', e => window.__clicks.push(
  [e.clientX, e.clientY, e.isTrusted]), true);
// state stays 'idle' + __clicks empty  → the click isn't reaching the page. Re-screenshot, re-click.
// state stays 'idle' + a TRUSTED click on some OTHER element → top-layer.

That second case is the sneaky one. An open <dialog> — or anything via showModal() / popover — paints above every z-index, so a target appended to <body> sits underneath it and the click hits the dialog. Seen on a session-detail modal, where the click logged cleanly as [864, 471, true, "SPAN"] while the recorder never left idle. The fix is in the skill: the arm helper now hosts inside dialog[open] / [role="dialog"] when one is present, and returns the host so you can confirm.

Then prove the file is real

ffprobe -v error -count_frames -select_streams v:0 \
  -show_entries stream=nb_read_frames,width,height -of default=nw=1 capture.webm
ffmpeg -y -loglevel error -i capture.webm -movflags faststart -pix_fmt yuv420p \
  -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2" capture.mp4

Hundreds of frames = real video. yuv420p and even dimensions aren't polish — without them QuickTime and Slack won't play the file at all. And MediaRecorder webm is variable-frame-rate, so frame-index extraction (-vf select='eq(n,N)') is unreliable: seek by time instead (-ss 7, -sseof -2.5).

The hard line

Route 1 wins because the MCP is the user's real browser, so their sessions are already there — a protected app typically shows an account picker with accounts already marked "Signed in", one click and you're in, no password. Never type the user's credentials. If a real password field appears, stop and hand back to the human. The skill calls that a hard line, not a difficulty.

The cursor is the narration

A recording has no click annotations of its own, so the injected walkthrough kit's fake cursor, highlight box and click pulse are the explanation. It works with Route 1 and Route 2 alike. Three of its rules break a take rather than merely annoy:

  • Wait for everything. An early click is the most common way a take breaks.
  • Frame one element, click another when a card's centre sits over some other control.
  • Assert on geometry, never on "the call returned". A drag or resize that does nothing is indistinguishable from one that works — the handle is there, the wait resolves, nothing throws, and the rect comes back byte-identical. Measure before and after.

Everything situational lives beside the skill rather than in it: long takes (gating the choreography, parking the OS pointer out of frame, clapping and trimming both ends, polling under CDP's 45s limit), the other two routes, sanitized stills for documents that show real account IDs — and a file of verified dead ends, so nobody re-derives them.
