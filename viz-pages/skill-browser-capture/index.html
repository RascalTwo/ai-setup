↓  WHY IT EXISTS

A slideshow, or no session

Putting a browser flow into a doc, a PR or a walkthrough has two obvious routes and both fail in a way you only notice at the end. The GIF recorder produces a slideshow, always: one frame per action, so the "choppy GIF" you keep re-recording is the tool working as designed. And a spawned headless browser records beautifully but arrives at the login page with no session, which for anything behind SSO is the end of the exercise.

What was missing was the third thing: capturing the browser the user is already signed into, at a real frame rate, without a red overlay across their screen, without Chrome pulled to the front, and without asking them to click anything or hand over a password. The previous design did it with a screen-share handshake that was fragile for one instant; OpenCode Browse records the session's own tab over CDP, so that instant is gone.

Pick the capture before you touch anything

Turning a browser flow into files you can embed is one question: still, video or GIF. The skill opens with the choice rather than a procedure because every obvious shortcut here fails silently, which is how this costs hours instead of minutes.

  • Still (viewport, full page, one element): page.screenshot inside a browse execute script.
  • Video: browse recording start / stop, an MP4 in ~/.agents/state/browser/<task>/.
  • GIF: record the video, then scripts/to-gif.sh. It usually looks better than the GIF recorder anyway.
  • Spawned browser (record-flow.js, agent-browser record) when no login is needed and Chrome must stay untouched, and the gif_creator fallback when a slideshow GIF (one frame per action) is what's wanted.

The skill fires on "add screenshots of the steps", "show how to do X in the UI", "record a walkthrough", "make a video of this", and especially on "this GIF came out choppy". Tool choice itself (browse, agent-browser, claude-in-chrome) belongs to the browser skill, not here.

What it will not do

Browse drives the user's own Chrome, so their sessions are already there: a protected app typically shows an account picker with accounts marked "Signed in", one click and you're in, no password. Never type the user's credentials. For a password, 2FA or payment the script calls handoff() and the user finishes in the tab. The skill calls that a hard line, not a difficulty.

The GIF trap. gif_creator yields a slideshow, always: one frame per action, and extra screenshots add zero frames. A GIF cut from a browse recording carries the video's motion. If a GIF looks janky, switch the capture path; do not tune the slideshow.
  • No slideshow GIF. gif_creator in claude-in-chrome makes one frame per action. Click annotations are not the gap: the ui-narration overlay draws the cursor, click pulse and captions in the page, so browse recording captures them.
  • Smoothness follows repaints. A CSS animation recorded at about 60 source frames per second; keystrokes through browse about 10 distinct frames per second, so a typing-heavy take looks stepped.
  • tab-capture mode needs a human. It fails until the user clicks the browse toolbar icon on the tab, and writes WebM only. The default CDP mode never asks.
  • The spawned browser has no session and cannot get one. Copying cookies won't ride an SSO session; that dead end is written down so nobody re-derives it.
  • It records; it does not edit. Trimming and captions are ffmpeg afterwards, not features here.

Where it lives

The kit scripts/to-gif.sh (video to GIF, two-pass palette) and scripts/record-flow.js (a puppeteer take in its own headless Chrome). The capture itself is the browse CLI; there is nothing to inject.
Integrates Chrome, through OpenCode Browse: screenshots and browse recording in the user's own tabs, with a spawned headless Chrome for scripted takes. claude-in-chrome survives only as the gif_creator fallback for slideshow GIFs.
Requires The browser skill (tool choice and the browse session recipe), ffmpeg (convert and verify), node for record-flow.js, and Chrome with the OpenCode Browse extension paired.
Hard dependency ui-narration. record-flow.js injects it unless you pass --no-kit, and exits with the paths it tried if the skill isn't installed rather than recording a silent, unannotated take. For a browse recording it supplies the highlight box, click pulse and eased scroll.
Its state None. The manifest says state: false and the skill keeps nothing between runs: no recording index, no settings file, no remembered tab or URL. A browse session lives only for one take and is deleted at the end.
What it writes Files you asked for, in ~/.agents/state/browser/<task>/ (the browser skill's artifact folder): screenshots, an MP4 with a .json sidecar of quality stats, and any GIF. Nothing is hidden and nothing is written to ~/Downloads.
Safe to delete Everything it produced. Re-running re-records. There is no local state that a deletion could corrupt.

What actually records

No injected recorder and no screen share. browse recording start -s <name> <path> asks the browse relay to record the session's tab. In --mode auto that is CDP for a tab the relay owns, which is every tab a browse session opens, so the output can be H.264 MP4 and the frame rate target is 60. start returns startedAt (epoch ms), mode, artifactType and frameRate; stop writes the file and a <file>.json sidecar with quality stats (achievedSourceFrameRate, droppedFrameCount, screenshotFallback).

--cursor draws browse's ghost cursor into the recording; without it only the page is recorded. --max-duration-ms (default 15 minutes) is the guard against a forgotten recording. The alternative, --mode tab-capture, uses Chrome's own tab capture, writes WebM only, and refuses until a human clicks the browse toolbar icon on the tab (the activeTab permission).

Why frames are not free

A CDP screencast delivers a frame when the page repaints. Measured on the same session: a CSS animation gave 201 source frames in 3.2 seconds, while a todo-list flow typed through pressSequentially gave about 10 per second, with the encoder repeating frames to fill the nominal 60. So the choreography decides smoothness: pace it (delay: 40, waitForTimeout(500) between beats) and lead with motion such as smooth scroll when the clip must feel like video. browse flight-recorder is the same capture as a rolling buffer (start, do the thing, save-last) for something you did not plan to record, and it drops idle stretches because only repaints are buffered.

Stills, and the pixel arithmetic

page.screenshot({ path: files.path("x.png") }) inside browse execute writes to browse's private temp folder, so the script returns the path and the agent cps it into the artifact folder. Output is CSS pixels times the device pixel ratio: a 1672×947 viewport saved as 3344×1894, and fullPage: true on a 7607 px page saved 15214 px tall. locator.screenshot crops to one element. page.setViewportSize pins the frame for a set of shots and read back as 1280×800. The page is rendered without the OS pointer, so there is nothing to park.

Then prove the file is real

ffprobe -v error -count_frames -select_streams v:0 \
  -show_entries stream=codec_name,pix_fmt,width,height,nb_read_frames:format=duration \
  -of default=nw=1 flow.mp4
ffmpeg -y -i flow.mp4 -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2:out_range=tv,format=yuv420p" \
  -color_range tv -movflags +faststart flow-share.mp4

Hundreds of frames is a real video. The recorder writes yuvj420p (full range), which some players mishandle; the second command gives QuickTime, Slack and Confluence the yuv420p tv-range file they expect.

GIF from the MP4

scripts/to-gif.sh in.mp4 out.gif [width] [fps] [colors] runs one ffmpeg call with fps, scale, then split into palettegen=stats_mode=diff and paletteuse with Bayer dither: a palette built for this clip rather than the 256-color global default. It prints the frame count, dimensions and bytes, so "more than one frame" is checked rather than assumed. The 4.7 s test take became 71 frames at 800×453 in 54 KB. Destination budgets (a Slack emoji is 128×128 under 3 s; a PR or Confluence GIF up to 480 wide under 10 s) and the rule that dropping frames beats dropping dimensions live in SKILL.md.

The cursor is the narration

A recording has no click annotations of its own, so a cursor and highlight are the explanation. Browse's --cursor is the cheap version; ui-narration adds a highlight box, click pulse and eased scroll, injected with page.evaluate and lost on every navigation, so re-inject after each page.goto. Pick one cursor, not both. Wait for everything: an early click is the most common way a take breaks, and a drag that does nothing is indistinguishable from one that works until you measure the element's box before and after.

Long takes trim from the recording's own clock: stamp Date.now() in the script at the first beat, subtract startedAt, and cut with ffmpeg -ss. On a 3.9 s take the stamp said 2.2 s and the first changed frame was at 2.25 s.
