The problem

You want a screenshot at the top of a PR. Every path that looks like it should work fails — and most of them fail silently, so you only find out when a reviewer sees a broken image icon.

Why the obvious paths fail

  • There is no attachment API. GitHub's only uploader is a browser drag-drop onto a classic Markdown editor. gh can't do it.
  • raw.githubusercontent.com from a private repo → does not render. GitHub proxies images through camo, and camo can't authenticate. Dead end.
  • The file_upload MCP tool → currently rejects host paths (regressed). Don't rely on it.
  • Synthetic cmd+v paste → unreliable; the key event never delivers image bytes to GitHub's paste handler.

The receipt

Clipboard → drop → URL → body. Four moves:

# 1. image onto the clipboard as base64 text (macOS; note the -i)
base64 -i /path/to/image.png | tr -d '\n' | pbcopy

# 2. open a CLASSIC editor and prove it is one — both must be true
#    https://github.com/<owner>/<repo>/wiki/_new
({ hasFileAttachment: !!document.querySelector('file-attachment'),
   hasBody: !!document.querySelector('#gollum-editor-body') })

# 3. click the body for OS focus, then run scripts/drop-and-harvest.js
#    → { url, imgTag }

# 4. spend the URL
gh pr edit <N> --body-file body.md   # <img width="1200" src="$URL" />

Linux swaps step 1 for base64 -w0 image.png | xclip -selection clipboard. Everything after that is identical, because the mechanism is the browser's, not the shell's.

When not to

  • The image already has a public, renderable URL — just paste it.
  • The repo is public and the file is committed — raw.githubusercontent.com is fine there.
  • Chrome MCP isn't available. The whole mechanism is a real browser driving a real uploader.
  • You want many images. One per run is simplest; multiples mean looping steps 1 and 4, since each drop appends a fresh URL to the same body.
  • You want the upload deleted later. It doesn't do that — the asset is permanent and there is no API to remove it, which is the flip side of it being permanent enough to leave the wiki unsaved.
Scope is the gotcha: a user-attachments asset is only visible to people who can see the repo it was uploaded through. Upload via the same repo as the PR — or one your audience can also see. Then navigate to the PR and actually look at it. A broken image means wrong repo scope or a bad URL; that eyeball check is the whole point.

The turn

Stop trying to host the image. Make GitHub's real uploader run. One PNG, from the clipboard to a URL in a PR body.

← → arrow keys

The bytes travel as text, on purpose

base64 -i image.png | tr -d '\n' | pbcopy puts the image on the OS clipboard as a single line of text. Two things fall out of that. The obvious one: the bytes never enter the agent's context — a 400 KB screenshot costs nothing to move. The less obvious one: text is what navigator.clipboard.readText() can reach from inside a page, and an image on the clipboard is not, which is the same reason synthetic cmd+v was a dead end.

The snippet validates before it decodes — /^[A-Za-z0-9+/=]+$/ over the trimmed clipboard — so a stale clipboard fails with "clipboard is not base64 text — re-run the pbcopy step" instead of producing a corrupt File that GitHub accepts and renders as garbage.

The classic editor is the whole constraint

GitHub's uploader is bound to a <file-attachment> custom element, and that element exists only on the classic Markdown editors — not the React /issues/new page. The reliable instance is any repo's wiki new-page, https://github.com/<owner>/<repo>/wiki/_new, used purely as an uploader. The precondition is checked rather than assumed, and both halves must be true:

({ hasFileAttachment: !!document.querySelector('file-attachment'),
   hasBody: !!document.querySelector('#gollum-editor-body') })

A wiki that is disabled redirects /wiki/_new to the repo home, where both come back false. The snippet refuses with a message that names the fix rather than dropping into a page with no uploader on it.

Reconstructing a File nobody dragged

Then the actual trick, five lines of it. Decode with Uint8Array.from(atob(b64), c => c.charCodeAt(0)), build a DataTransfer, add new File([u8], "image.png", { type: "image/png" }), and dispatch three events at the <file-attachment> — dragenter, dragover, then drop — each a real DragEvent with bubbles, cancelable and that dataTransfer attached. The first two are not ceremony: GitHub's handler establishes drop state on the enter/over pair, and a bare drop arrives at an element that was never told a drag was in progress.

From GitHub's side this is indistinguishable from a human dragging a file in, which is exactly why it works where every synthetic shortcut failed. Its own uploader runs, with its own auth, its own scoping, its own CDN.

Harvesting, because the upload is asynchronous

The drop returns immediately; the URL does not. So the snippet polls the editor body — 30 attempts, 500 ms apart, fifteen seconds in total — for /https:\/\/github\.com\/user-attachments\/assets\/[0-9a-f-]+/, and returns { url, imgTag } the moment it matches. A timeout returns { error, body } with the body included, so you can see what GitHub actually inserted rather than guessing.

Pass the snippet as-is. Do not wrap it in an async IIFE. javascript_tool returns the last expression's value and supports top-level await — but it does not await a Promise you hand back, so (async () => {…})() serializes to {}. The file's last expression is the bare out for exactly this reason. If you do get {}, the drop still ran; read the URL back out of the body:
document.querySelector('#gollum-editor-body').value.match(/user-attachments\/assets\/[0-9a-f-]+/)?.[0]

Spend it, then walk away without saving

The URL is plain text in a plain Markdown body, so gh takes it from there — gh pr edit, gh issue edit, gh project item-edit --body. Build the body in a file and pass --body-file to avoid escaping pain. <img width="1200" height="630" src="…"> pins a stable render size for an OG card; ![alt](url) is fine otherwise.

Then the cleanup, which has an ordering requirement: clear the body, fire a bubbling input event so the editor notices, null out window.onbeforeunload, then navigate. Navigate first and Chrome throws a "Leave site?" dialog that blocks the tab.

const b = document.querySelector('#gollum-editor-body');
b.value = ''; b.dispatchEvent(new Event('input', {bubbles:true}));
window.onbeforeunload = null; true;

The wiki page is never saved and nothing is committed. The asset outlives the editor it was uploaded through — which is the property the whole approach rests on. Last step, always: open the PR and look at it.
