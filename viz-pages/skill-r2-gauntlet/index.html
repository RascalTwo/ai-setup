↓  WHY IT EXISTS

Sixteen reviewers, sixteen reports

Once you've collected a shelf of review skills, using them is the problem. Run them one at a time and you read the same finding five times in five different voices, with no idea which of the five you should actually believe. Run only your favourite and you've thrown away the other fifteen opinions. The gauntlet's answer isn't a better reviewer — it's one pass, one report.

The one thing it refuses to do

Guess what to review. /r2-gauntlet <scope> blocks until you've named a scope, and if the invocation didn't carry one it asks rather than defaulting — reviewing the wrong thing burns about sixteen agents. There are exactly four:

repo         the whole tracked tree      → git ls-files
unstaged     working-tree changes        → git diff
staged       what's staged for commit    → git diff --cached
since <ref>   everything since a commit   → git diff <ref>...HEAD

The resolved diff is written to the scratchpad once and the same artifact is handed to every reviewer. Reviewers are not allowed to recompute scope for themselves — if they each resolved it, they'd diverge, and the dedup would be comparing apples to oranges.

repo changes who is in their element: the diff-native reviewers (code-reviewer, test-reviewer, ponytail-review) are reviewing the whole tree and the report says so, while the auditor family (ln-53, ln-56, ln-57) is in its native habitat. It is also the only scope that dispatches ln-55-test-suite-auditor, because a flake matrix cannot run on a diff.

It reports. It never fixes.

Reviewers are read-only truth-tellers; the gauntlet edits no code, regardless of who invoked it. It ranks the findings, saves the report next to the diff, and hands the decisions back. When r2-sdlc calls it as its Tier-2 quality wave it can pass --quality-only to skip the correctness pair the pipeline already gated, or a --only/--skip subset — but the fix-and-re-run loop belongs to the caller either way.

  • It will not interview you. The conditional lenses are probed, not asked about. Turning the probe into a Q&A is listed in the skill as an anti-pattern — look, decide, note, move on.
  • It will not prune the roster to reduce duplicates. That is the one optimization that destroys the product.
  • It cannot review what no lens covers. A tool that isn't installed, a PR that doesn't exist, a design doc nobody wrote — each becomes a named skip, not a silent gap.
  • For one targeted review it is the wrong tool. Sixteen agents to answer "is this function right" is absurd; that is /code-review.

Where it lives

Integrates withClaude Code — the r2-sdlc reviewer subagents, the ln-* auditor skills, and the built-in /review and /security-review. git and gh for scope and PR detection.
RequiresNothing it installs. The deterministic floor uses jscpd, madge and eslint-plugin-jsx-a11y if present, and names the sub-check as skipped if not.
Its stateIt has no directory of its own. The manifest declares state-owner: r2-sdlc, and a run writes into ~/.agents/state/r2-sdlc/<repo-id>/gauntlet-<YYYYMMDD-HHMMSS>/ — gauntlet-scope.diff and gauntlet-report.md.
Why share a storeOn purpose. r2-sdlc invokes the gauntlet as its Tier-2 quality wave, and the gauntlet reads r2-sdlc's design.md files when probing fidelity-reviewer. Two directories for one repo's review history would mean the probe has two places to look and the reports have two homes. <repo-id> is derived exactly as r2-sdlc derives it — the git remote's path, github.com/user/repo → user--repo, falling back to a sanitized directory basename — because a different derivation would silently split the store in half.
Its own cornerA gauntlet run is not a pipeline run, so it gets a timestamped sibling directory rather than writing into a pipeline's <slug>/. Shared store, separate rooms.
Safe to delete?deletion-policy: retain, and the policy belongs to r2-sdlc, not here. Past reports are the evidence trail for what was already reviewed and decided.

Cracking it open

One run, from a word you typed to a ranked report. Four steps, and only the last one is the product.

Three dispatch mechanisms, one message

The roster is not written in this skill. It lives in one shared registry that both the gauntlet and repo-issue-scanner read, and the gauntlet selects every lens whose change-review projection is ✓, plus the ✓* conditionals that passed the probe. The registry's Invoke via column then decides how each one is spawned, and all of them go out in a single message so they run concurrently:

  • A — reviewer subagents. code-reviewer, test-reviewer, docs-currency-reviewer, reuse-reviewer, security-reviewer spawn straight through the Agent tool by subagent_type. The conditional pair, fidelity-reviewer and qa-validator, join them if the probe found their oracle.
  • B — skill wrappers. ln-52, ln-53, ln-56, ln-57, ponytail-review and code-review are Skill-tool skills, not subagents, so each is wrapped in a general-purpose subagent whose entire job is: invoke that skill against the scope artifact, return findings in the canonical schema, nothing else.
  • C — built-ins. security-review always, wrapped the same way. review is the GitHub-PR reviewer and runs only if gh pr view --json number succeeds; on a local-only diff it is skipped with a note.

Three lenses were cut on 2026-08-30, each disqualified by its own description. ln-54-codebase-auditor ("use when no specialist audit is primary" — never true here, every specialist always runs) and ponytail-audit ("ponytail-review, repo-wide" — nothing unique, and it was being handed a diff while instructed to scan a tree) were deleted. ln-55-test-suite-auditor was kept but not dispatched on a diff: its flake matrix is the one thing test-reviewer cannot do, and a diff is exactly where it cannot run.

Every reviewer returns the same eight fields

Dedup is only mechanical if the inputs line up, so every subagent is told to return a flat list in one shape — source, file, line, severity, category, title, detail, fix. Reviewers natively speak different severity words (blocker/suggestion/fyi, critical/high/med/low); they are told to map onto the five-level scale and synthesis normalizes the stragglers. Each one also gets the scope artifact path, the changed-file list and the schema up front, because a subagent cannot ask mid-run.

The overlap is a feature

The roster is deliberately redundant, and the skill forbids pruning it to "reduce duplicates." The duplicates are the signal. Synthesis merges findings that name the same problem in the same place — judged by meaning, not string match, so ponytail-review's "premature BaseProcessor abstraction" and code-reviewer's "single-impl interface, inline it" collapse into one entry — then keeps the set of sources that raised it. That count is the confidence score, and it's what does the ranking after severity.

The report is explicit about the shrinkage: raw findings n → after dedup m, with a consensus highlights section for anything three or more independent reviewers flagged. The skill's own closing instruction is that a flat undeduped digest "is just the old chaos with one keystroke — the ranking is the deliverable."

Probe the conditionals. Never interview.

Two lenses need an oracle a diff can't supply. fidelity-reviewer asks "does this match the design?" and needs a design.md; qa-validator asks "does this solve the user's problem?" and needs the original ask. The gauntlet looks in the known locations — any .scratch/*/design.md in the repo first, then the most recent ~/.agents/state/r2-sdlc/<repo-id>/*/design.md — includes the reviewer if it finds exactly one obvious candidate, and otherwise skips it with the reason printed in the report: "no design doc found, pass one to enable". Turning that probe into a Q&A is listed as an anti-pattern: look, decide, note, move on.

Skips are output, not silence. Every lens that didn't run — no design doc, no open PR, a scanner binary that isn't installed — lands in a Skipped reviewers section of the report. You always know what didn't get looked at.

The floor nobody else covers

One conditional subagent runs the mechanical checks that no judgement-based reviewer owns, and only the sub-checks the diff actually triggers: a changed dependency manifest enables the dep audit, changed JSX/TSX enables the a11y pass, and any code diff gets copy-paste detection via jscpd (10+ duplicated lines, not 3), madge --circular for new import cycles, and an async-correctness sweep — forEach(async) with no error handling, a missing await, fire-and-forget with no logging, Promise.all with no failure strategy. Tool not installed → that sub-check is skipped and named.

The dependency check reuses repo-issue-scanner's existing dependency-audit skill rather than reimplementing it. Same reason the roster itself isn't written here: it lives in one shared registry that both the gauntlet and the scanner read, so adding a lens in one place can't leave the other stale. The scanner is a sibling that shares that registry — the two deliberately don't call each other.
