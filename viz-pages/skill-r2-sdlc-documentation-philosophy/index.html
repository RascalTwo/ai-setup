Too little and too much
are the same bug.

A doc earns its keep only by adding signal a reader can't get from the code. Below that bar it's a trap; above it, it's a line someone now has to keep true. So the reviewers are aimed at both failure modes — noise gets flagged exactly as hard as a gap.

A layer, not the whole rulebook

This isn't something you run, and it isn't the general documentation rules either — those belong to documandments, which owns the gate (should this doc exist at all?), the ladder (fix it with a name, a type, a test, a comment — prose last), what survives in the prose, and the duty to update or delete prose in the same change as the code. This file is the thin layer r2-sdlc adds on top: the bar for exported APIs, and the checklists the code-reviewer and docs-currency-reviewer run.

It used to restate documandments — about 51 lines of Goldilocks, inline-comment rules and README currency, in a second vocabulary. documandments is vendored from documandments.com and expected to change when the site does, and nothing checks that copy for drift, so the duplicate was guaranteed to disagree eventually. Trimmed to 88 lines in the 2026-08-30 audit: one home per fact, which is documandments' own rule.

The export bar is the part that's ours

documandments has no notion of an exported API — it reasons about docs, not call sites. So this is the one rule with nowhere else to live: if other code imports it, treat it as a library. A one-line purpose (not mechanism), the non-obvious parameters, the return contract including error/null/empty behavior, what it throws, and usage constraints. Not the implementation details — callers don't care how.

# the split that does the work
exported  → the library bar: contract, errors, constraints
internal  → the comment bar: only a non-obvious WHY
never     → a doc string that restates the type signature

The last line is the one reviewers flag most: /** @param id The id */ above id: UserId is a line someone now has to keep true, in exchange for nothing.

The worst thing is a doc that's now wrong

Outdated documentation is ranked the number-one worst outcome here: wrong docs are worse than no docs, because they actively mislead. documandments states the duty (prose describing changed code is updated or deleted in the same change); what this layer adds is the docs-currency-reviewer's two questions.

  • Are any existing docs now wrong? Did you rename a file, module, command, config key or endpoint? Change setup steps, env vars, defaults? Change a public API or an output format? Every doc and every example that references the old thing has to move.
  • Does anything you added need new documentation? A new public command or endpoint, a new config option, a gotcha that isn't self-evident, a new architectural concept. Written when the answer is yes — not "just in case."
The reviewer stops at the finding. docs-currency-reviewer reports a file path, a line, and the specific change needed — and does not rewrite docs unprompted. It surfaces the gap and lets the main agent decide whether to fix it in this run or spin it off.

When in doubt

One question settles it: would a reader reasonably need this to understand or safely use the code? Yes → write it, concisely, focused on the WHY and the contract. No → write nothing. And if you genuinely can't tell, the tie-breaker isn't neutral — lean toward not writing. It's easier to add a doc when a reader later asks "why?" than to delete stale noise that has already calcified into the codebase.
