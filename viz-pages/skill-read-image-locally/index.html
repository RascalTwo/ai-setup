The cost you don't see

Images are not like text. A native image Read adds roughly 1–2k vision tokens to the context — and unlike a one-off tool result you can forget about, it stays there and accumulates every turn for the rest of the session. Five screenshots into a debugging loop, a meaningful slice of the window is spent on pictures you already extracted two numbers from.

Using it

Always pass the specific extraction intent — never a generic “describe this image”. Pass --json when you expect a structured shape and the engine validates the output is real JSON.

# Read HUD values out of a screenshot
python3 vision_judge.py /tmp/frame.png --prompt "Extract the SCORE and LIVES values."

# Force a structured shape
python3 vision_judge.py /tmp/dash.png --json \
  --prompt 'Return {"cpu_pct":int,"mem_pct":int} from this dashboard.'

# on success, a header line then the answer
[read-image-locally OK] model=… <latency>

Models are tried in tier order, cheap and fast first — default gemma4:e4b, then gemma4:12b. It needs Ollama reachable at http://localhost:11434 with those models pulled.

The decision boundary

Image reading is intent-dependent, so the routing is too. The same PNG belongs on either side depending on what you actually want out of it — and the prompt you pass carries that intent. A local model is only ever as good as the extraction instruction you hand it.

  • Structured / known extraction → this skill. HUD and dashboard values, table contents, log or screenshot text, error messages, specific labeled fields, “what does this text say”.
  • Holistic visual judgment → the native Read tool. Layout and aesthetics, “does this look right”, subtle or ambiguous scenes, dense unfamiliar UIs, “why does this look off”. A small local model answers those with a generic caption that silently misses exactly what you were looking for.

Two more ceilings worth knowing before you rely on it. It reads one still image — a video is read-video-locally, which has its own frame-selection problem to solve. And it makes one request per model tier with no retry inside a tier: a model that answers wrongly but confidently is accepted, because the only thing the engine can check is that a reply arrived and, under --json, that it parses.

It is an optimization, never a hard dependency. If every local tier fails — Ollama down, model missing, empty or invalid output — the engine prints LOCAL_VISION_FAILED and exits non-zero. That is the signal to read the image natively with the Read tool. Native Claude is simply the last tier of the same ladder, not an error path.

Where it lives

The engineskills/read-image-locally/vision_judge.py — about seventy lines, standard library only. base64, json, urllib.request; no Ollama SDK, no HTTP client dependency.
IntegratesOllama, and nothing else. One POST to http://localhost:11434/api/generate. There is no client library to keep in step and no daemon of its own — if Ollama is running, this works.
Requiresollama reachable on localhost:11434 with the tier models pulled (ollama pull gemma4:e4b). Confirm with curl -s localhost:11434/api/tags.
The routing ruleNot in this skill. AGENTS.md §9 holds the local-vision-first policy, because it has to reach an agent before it reflexively reaches for a native Read. Both Claude Code and Codex read that file, so the guidance travels by prompting with no hook to install.
Its stateNone. The manifest says state: false and there is nothing to qualify: no cache, no index, no run history, nothing under ~/.agents/. The image is read, base64'd in memory, POSTed, and the answer goes to stdout. Two runs on the same file share nothing.
Safe to deleteThere is nothing to delete. The one thing that persists is Ollama's own model store, which belongs to Ollama and is shared with everything else using it.
Teststests/run-tests.sh covers the success and failure paths, with assets/hud.png as the fixture. The failure path is the one that matters — it is what keeps this an optimization rather than a single point of failure.

How it's wired in

One PNG, from open() to either an answer on stdout or exit code 3.

← → arrow keys

The whole file, base64, in the body

There is no upload endpoint and no multipart form. Ollama's generate API takes images inline, so the engine does base64.b64encode(open(image,"rb").read()).decode() and drops the string into an images array. The consequence is worth knowing: the image is held in memory twice — raw bytes and a base64 string a third larger — and travels as one JSON POST. For screenshots that is nothing. A 40 MP photo is a different conversation.

A file that cannot be opened is the one failure handled separately: it prints LOCAL_VISION_FAILED: cannot read image and exits 2, distinct from exit 3 for "the models were tried and none worked".

The request body, and why each field is set

{"model": model, "prompt": prompt, "images": [b64],
 "stream": false,            # one JSON reply, not an SSE stream to reassemble
 "keep_alive": "30m",        # the model stays resident between images
 "options": {"temperature": 0}}   # extraction, not composition

keep_alive: "30m" is the one that changes how the skill feels. Loading a vision model is the expensive part; holding it resident for half an hour means the second, third and tenth screenshot in a debugging loop answer immediately. temperature: 0 is because this reads values off a dashboard — sampling variety is not a feature here.

With --json, "format": "json" is added and the reply is passed through json.loads() before it is accepted. That validation is deliberately the only check: the engine asserts a shape, never a fact.

The qwen branch, which exists because of a real trap

Reasoning models hide their answer somewhere else. Under format:json, a Qwen3 model puts its output in the response's thinking field and leaves response empty — so a run "succeeds" and yields nothing. The engine detects "qwen" in model.lower(), sets "think": false and removes format from the body, which puts the answer back where the rest of the code expects it. Belt and braces, the reader also falls back: txt = response or thinking, and an empty result raises ValueError("empty response") rather than printing a blank answer.

The ladder, and what it catches

The tier loop is four lines and catches bare Exception — on purpose. A tier can fail as a connection refusal, an HTTP 404 for an unpulled model, a timeout at 300 s, an empty string, or invalid JSON, and from the caller's position those are one event: that tier did not produce an answer, try the next. Each failure prints [read-image-locally tier failed] model=… : … to stderr, so the diagnosis survives without polluting the answer on stdout.

Exhausting the list prints LOCAL_VISION_FAILED: all local tiers failed — fall back to native image reading and exits 3. Native Claude is the last rung, reached by an agent reading that line — which is why the policy lives in AGENTS.md:
