The one failure it prevents

An agent that knows curl and knows your Okta token will, sooner or later, write the obvious thing: curl -H "Authorization: SSWS ...". That command is now permanent. It's in the transcript, in the approval prompt you clicked through, in shell history, in whatever the harness logs. Rotating the token is the only fix, and you have to notice first.

So the skill's rule is blunt: always use scripts/okta-api.sh — never inline the token in a curl command. The script takes three positional arguments, pulls orgUrl and token out of ~/.okta/okta.yaml, and assembles the header itself. The secret exists in a file and in a subprocess's argument array. It never exists in a string anyone reads back.

It is a passthrough, not a client

There are no verbs to learn. There's one script, and the path you give it is appended to <orgUrl>/api/v1:

scripts/okta-api.sh <METHOD> <API_PATH> [JSON_BODY] | jq '.'

scripts/okta-api.sh GET /users/me | jq '.'
scripts/okta-api.sh DELETE /idps/0oa123abc
scripts/okta-api.sh POST /groups '{"profile":{"name":"My Group","description":""}}'
scripts/okta-api.sh PUT /idps/0oa123abc "$(cat body.json)"

Identity providers, users, groups, apps, policies — whatever the REST API exposes, this reaches, because it doesn't model any of them. The cost of that is that you have to know the path.

The 80,000-line problem

Okta publishes an official OpenAPI spec (okta/okta-management-openapi-spec), and it is roughly 80k lines. Reading it to answer "what shape is an IdP body" would eat the context window that was supposed to hold the actual work.

So the second script never loads it. okta-lookup.sh caches the spec at ~/.okta/spec-cache/management-minimal.yaml and greps it, returning line numbers:

scripts/okta-lookup.sh "/api/v1/idps"     # paths
scripts/okta-lookup.sh "IdentityProvider" # schemas
# then Read the cache file at that offset for full context

Grep for the hit, then read a window around it. The cache auto-refreshes when it's older than 7 days — which is also the size of the staleness window you're accepting.

What it doesn't do

Okta paginates large result sets through Link response headers. The wrapper prints the response body only — so those headers never reach you, and there is no cursor to follow. The skill's answer isn't auto-pagination; it's ask for a bigger page:

scripts/okta-api.sh GET /users?limit=200 | jq '.[].profile.login'

Honest framing: for an org that overflows one page, this skill gets you the first page. Walking the rest is on you.

The config is parsed by grep, not by a YAML parser. orgUrl and token are pulled with grep | awk '{print $2}'. Exactly one line of each — a second token: anywhere in the file, even commented differently than expected, concatenates into a credential that can't work. It's a two-key convention wearing a .yaml extension.

Setup is deliberately manual

Nothing here mints credentials. You either write ~/.okta/okta.yaml by hand with an admin-console token (Security → API → Tokens → Create Token), or run okta login if the Okta CLI happens to be installed. If the file is missing, the script exits with an error pointing at setup.md rather than guessing.
