The one failure it prevents

An agent that knows curl and knows your Okta token will, sooner or later, write the obvious thing: curl -H "Authorization: SSWS ...". That command is now permanent. It's in the transcript, in the approval prompt you clicked through, in shell history, in whatever the harness logs. Rotating the token is the only fix, and you have to notice first.

So the skill's rule is blunt: always use scripts/okta-api.sh — never inline the token in a curl command. The script takes three positional arguments, pulls orgUrl and token out of ~/.okta/okta.yaml, and assembles the header itself. The secret exists in a file and in a subprocess's argument array. It never exists in a string anyone reads back.

It is a passthrough, not a client

There are no verbs to learn. There's one script, and the path you give it is appended to <orgUrl>/api/v1:

scripts/okta-api.sh <METHOD> <API_PATH> [JSON_BODY] | jq '.'

scripts/okta-api.sh GET /users/me | jq '.'
scripts/okta-api.sh DELETE /idps/0oa123abc
scripts/okta-api.sh POST /groups '{"profile":{"name":"My Group","description":""}}'
scripts/okta-api.sh PUT /idps/0oa123abc "$(cat body.json)"

Identity providers, users, groups, apps, policies — whatever the REST API exposes, this reaches, because it doesn't model any of them. The cost of that is that you have to know the path, which is what the second script is for.

What it doesn't do

Okta paginates large result sets through Link response headers. The wrapper prints the response body only — so those headers never reach you, and there is no cursor to follow. The skill's answer isn't auto-pagination; it's ask for a bigger page:

scripts/okta-api.sh GET /users?limit=200 | jq '.[].profile.login'

Honest framing: for an org that overflows one page, this skill gets you the first page. Walking the rest is on you.

  • It does not mint credentials. No login flow, no device code, no token creation. You bring a token or there is no skill.
  • It does not shape output. Raw body to stdout — which is why every example ends in | jq.
  • It does not check the status code. curl -s with no -f: an Okta error object is printed exactly like a success, and it is on the reader to notice errorCode.
  • It has no per-resource commands. No okta-api users list. Method, path, optional body — including for endpoints added after this skill was written.

The 80,000-line problem

Okta publishes an official OpenAPI spec (okta/okta-management-openapi-spec), and it is roughly 80k lines. Reading it to answer "what shape is an IdP body" would eat the context window that was supposed to hold the actual work.

So the second script never loads it. okta-lookup.sh caches dist/current/management-minimal.yaml from the repo's master branch at ~/.agents/state/okta-api/spec-cache/management-minimal.yaml and greps it, returning line numbers:

CACHE_DIR="${HOME}/.agents/state/okta-api/spec-cache"
# refresh if missing or older than 7 days
if [ ! -f "$SPEC_FILE" ] || find "$SPEC_FILE" -mtime +7 | grep -q .; then
  curl -sf "$SPEC_URL" -o "$SPEC_FILE"
fi
grep -n "$KEYWORD" "$SPEC_FILE"

Grep for the hit, then read a window around it with an offset read. The staleness window is that -mtime +7 and nothing else — there is no ETag check and no force-refresh flag, so a spec that changed on day two is a spec you see on day eight. rm is the refresh command.

The wrapper, argument by argument

Three positionals — method, path, optional body — and a fixed header set. The body argument is the only conditional in the script:

CURL_ARGS=( -s -X "$METHOD"
  -H "Authorization: SSWS $TOKEN"
  -H "Accept: application/json"
  -H "Content-Type: application/json" )
[ -n "$BODY" ] && CURL_ARGS+=(-d "$BODY")
curl "${CURL_ARGS[@]}" "${ORG_URL}/api/v1${API_PATH}"

That last line is the whole security argument. $TOKEN is expanded inside the script, into the argument array of a curl the agent never composed. What the agent wrote — and what the approval prompt, the transcript and the scrollback keep forever — is scripts/okta-api.sh POST /idps '{…}': a method and a path.

The script runs under set -euo pipefail and refuses to start without the config, exiting 1 with a message that names the missing file and points at setup.md. It does not fall back to an environment variable, and it does not prompt.

The config is parsed by grep, not by a YAML parser

Two keys wearing a .yaml extension. orgUrl and token are pulled with grep '<key>:' | awk '{print $2}' | tr -d '"'. That takes the second whitespace-separated field of every matching line — so a second token: anywhere in the file, including one you thought was commented out differently, concatenates into a credential that cannot work. The nesting under okta.client in setup.md is decoration; the parser never sees it.
