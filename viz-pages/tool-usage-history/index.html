The number is destroyed on a timer

A rate-limit window is a cumulative counter that zeroes when it resets. Claude Code reads it, renders it, and keeps nothing. /usage shows the current window. The claude.ai usage page shows the current window. The Admin API's usage and cost reports have real history — for API organisations, which a Max subscription is not.

So the counter is not merely unsampled between renders. At the boundary it is gone rather than deferred: whatever accrued after the last observation is not carried into the next window, and no later reading can recover it.

Which makes an ordinary question unanswerable. You end a week at 61%. Was the other 39% capacity you were physically throttled out of using, or capacity that sat there while you rationed yourself? Those call for opposite corrections, and after the reset there is nothing left to tell them apart.

Codex, meanwhile, writes rate_limits into every session rollout and always has. The asymmetry is the whole design: usage-history records for Claude Code and only scrapes for Codex.

You do not use it. That is the point.

There is no command. Once installed it is three things that run on their own:

  • Every statusline render — statusline-capture.sh sits at statusLine.command, appends if the value changed, and pipes the payload through to ccstatusline untouched.
  • Every 5 minutes — a launchd agent wakes usage-poll.py, which does nothing unless the last API snapshot is over 15 minutes old or a window resets within 6.
  • Hourly — codex-usage-scrape.py re-reads ~/.codex/sessions and merges by union.

What you do is read it, later, with whatever you like — it is one JSON object per line:

{"t":"2026-09-20T09:52:03-05:00", "src":"api", "usage":{ "five_hour":{"utilization":29.4, "resets_at":"2026-09-20T18:50:00Z"}, "seven_day":{"utilization":61.2, "resets_at":"2026-09-26T06:00:00Z"}, "seven_day_breakdown":{"rows":[{"key":"claude_code","percent":100}, …]}}}

The response is stored verbatim. It ships buckets that are null today under names like tangelo, cedar_ember and nimbus_quill — unshipped features. A writer that whitelisted the four documented windows would drop every one of them silently on the day it went live.

What it cannot tell you

  • The percentages are integers. A hundred steps across a seven-day window is roughly 1% per 101 minutes at uniform full burn. Sampling faster than hourly cannot resolve more than the source reports.
  • Statusline records lag. Claude Code refreshes its own usage cache far less often than it renders — measured at ~25 minutes between changes, with 37 of 39 samples identical. A src: statusline record means by this time it had reached X, not that it became X then. Monotone lower bounds, useful as corroboration, wrong as a timeline.
  • Windows are account-wide; this machine is not. claude.ai, mobile and a second laptop burn the same windows and leave nothing here. seven_day_breakdown is what reveals whether that is happening.
  • The token belongs to Claude Code. The poller reads it from the login keychain and cannot renew it. Leave Claude Code closed long enough and polling fails 401 until you start it again — written to poll-errors.log, never swallowed.
  • No backfill. History begins at install. Earlier burn can be reconstructed from transcripts only as a cost proxy, and only for windows whose percentages are already gone.

And it refuses one thing on purpose: it will not tell you whether you were at the keyboard during a quiet stretch. Separating "asleep" from "working but rationing" needs an idle sensor this tool deliberately does not have.

Cracking it open

Two writers, one append-only log, and a rule that keeps them from cancelling each other out. The constraint that shapes it: the value is exposed in exactly two places, and the cheap one is stale.

Why the boundary gets its own trigger

Undersampling a cumulative counter costs timing precision, never magnitude — burn 6% between two polls and the next poll still shows all 6%. The exception is the reset, where the counter zeroes and unsampled burn is genuinely lost. So rather than raise the base rate everywhere, the poller aims at the edge: every response carries resets_at, so it always knows where the next boundary is and takes one extra sample just before it.

Why nothing here trusts a key name

Codex's own history proves the hazard. On 2026-07-12 the primary slot silently changed meaning — it had been the 5-hour window, it became the 7-day window, and secondary vanished. Keyed on the slot name, 2,068 of 2,419 records would be misread as five-hour data. Window identity comes from window_minutes, and normalisation happens at read time, where it can be re-run when a vendor moves something again.

The failure mode it is built to survive

Capture is fail-silent on every path, because a recorder that breaks a statusline is worse than no recorder. Bad JSON, a missing rate_limits, an unreadable log — each one falls straight through to the render. The only thing usage-history will interrupt is its own logging.
