↓  WHY IT EXISTS

The failure it saves you from

You download a Google Meet recording and ask for a transcript. The obvious move is to run speech recognition over it — and it works, and it takes minutes, and the output is a wall of text with no idea who said what. Meanwhile the file you handed over already contained a caption track that Google wrote during the call, with speaker names in it. The skill's first act is to look before it listens.

The whole workflow

# 1 — probe: is there anything to extract at all?
ffprobe -v quiet -print_format json -show_streams -select_streams s "$FILE"
   → index, codec_name (webvtt / subrip / ass / mov_text),
     tags.language, tags.title

# 2 — one stream: use it. more than one: show them and ask.
   Found 2 subtitle streams:
     Stream 0: webvtt (English)
     Stream 1: subrip (Spanish)      default: 0

# 3 — extract, WebVTT first
ffmpeg -i "$FILE" -map 0:s:$N -c:s webvtt "$OUT" -y

Output lands next to the input with the extension swapped — recording.mp4 → recording.vtt — unless you say otherwise. Then it reports the path, the format, the file size, and a preview of the first few entries, because a subtitle file that extracted cleanly and a subtitle file that came out as garbage look identical from a byte count.

WebVTT first, SRT only as a fallback

The preference isn't stylistic. WebVTT carries <v Speaker> voice tags and SRT does not. Google Meet captions are WebVTT internally, so extracting one to WebVTT keeps the speaker attribution intact; converting down to SRT throws it away. SRT is what you get when the source codec can't be converted to WebVTT at all.

No subtitle track is not a dead end

If ffprobe comes back empty, there's nothing embedded to extract — but the file is already local, so the skill hands off to transcribe-media and generates the captions from the speech instead.

skills/transcribe-media/transcribe.sh "$FILE" --format vtt   # or srt

Same .vtt or .srt on the other end, just derived from audio rather than lifted from a container. The one case where that's the wrong route: a Meet recording that's still sitting in the Drive player and hasn't been downloaded. There, extract-gdrive-transcript wins, because it reuses Google's own speaker-attributed captions rather than re-recognising anything.

Hardcoded subtitles are out of scope, permanently. Some files have the text painted into the video frames rather than carried as a stream. There is no stream to map, so FFmpeg cannot extract them at any quality setting — recovering that text is OCR, which is a different problem and not what this skill is.

When the output looks wrong

Garbled or empty results usually mean the track is in a format FFmpeg can't convert, not one it can't read. Re-extract with -c:s copy to get the raw bytes untouched and see what the format actually is before blaming the file.

What it needs

  • FFmpeg installed — brew install ffmpeg, or apt install ffmpeg on Linux. No FFmpeg, no skill.
  • A local file. Video or audio, MP4 / MKV / WebM, anything FFmpeg opens. Nothing is uploaded and nothing is downloaded — it reads the file where it sits.
  • A path. If you don't give one, it asks for one rather than guessing.
