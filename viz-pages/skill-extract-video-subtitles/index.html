↓  WHY IT EXISTS

The failure it saves you from

You download a Google Meet recording and ask for a transcript. The obvious move is to run speech recognition over it — and it works, and it takes minutes, and the output is a wall of text with no idea who said what. Meanwhile the file you handed over already contained a caption track that Google wrote during the call, with speaker names in it. The skill's first act is to look before it listens.

Handing it a file

It fires on the thing you were going to say anyway — "get the subtitles out of this", "extract the captions", "rip the subs" — and on the specific case it was built for: a Meet recording already sitting on disk. The only input is a path.

# the skill takes $ARGUMENTS as the file path
extract the subtitles from ~/Downloads/"Weekly sync (2026-02-11).mp4"

No path given, it asks for one rather than guessing — there is no default file and no directory scan. Everything after that is decided from what ffprobe finds in the container, except the one question it puts to you: which stream, when there is more than one.

When the output looks wrong

Garbled or empty results usually mean the track is in a format FFmpeg can't convert, not one it can't read. Re-extract with -c:s copy to get the raw bytes untouched and see what the format actually is before blaming the file.

Hardcoded subtitles are out of scope, permanently. Some files have the text painted into the video frames rather than carried as a stream. There is no stream to map, so FFmpeg cannot extract them at any quality setting — recovering that text is OCR, which is a different problem and not what this skill is.
  • It never re-recognises speech itself. When there is no track, it hands the file to a sibling skill rather than growing an ASR engine of its own.
  • It doesn't fix a bad caption track. Auto-generated captions that were wrong during the call are extracted faithfully wrong. Extraction is a copy, not a judgement.
  • Timing is whatever the container says. A track with drifted cue times comes out with drifted cue times; nothing here re-aligns to the audio.
  • One track per run. Multiple languages means multiple extractions, and you pick each time.

What it needs

Requiresffmpeg — and ffprobe, which ships with it. brew install ffmpeg, or apt install ffmpeg on Linux. That is the entire dependency list; no FFmpeg, no skill.
TakesA local file. Video or audio, MP4 / MKV / WebM, anything FFmpeg opens. Nothing is uploaded and nothing is downloaded — it reads the file where it sits.
IntegratesNothing. The manifest declares no integrates at all: no MCP server, no browser, no API, no network. Two subprocess calls to binaries already on your machine.
Hands off totranscribe-media when the container has no subtitle stream, and points at extract-gdrive-transcript when the recording is still in the Drive player rather than on disk. It calls the first and merely names the second.
Its stateNone. The manifest says state: false and there is nothing to qualify it with — no cache, no index, no run log, nothing under ~/.agents/. It keeps nothing between runs, so run two never knows run one happened.
What it writesExactly one file, where you can see it: the .vtt or .srt beside the input with the extension swapped. That is the output you asked for, not state. The source video is opened read-only and never modified.
Safe to deleteEverything it produced, freely. Re-running costs a second of ffmpeg.

The whole workflow

One file path, from the probe to the preview. There is no script here — the skill is this sequence, and the branch in the middle is the whole design.

← → arrow keys

Step 1 — probe, and probe for subtitles only

ffprobe -v quiet -print_format json -show_streams -select_streams s "$FILE"

-select_streams s is what makes this cheap and unambiguous: it returns the subtitle streams and nothing else, so an empty array is a definite answer rather than something to be inferred from a wall of video and audio metadata. Each stream comes back with index, codec_name (webvtt, subrip, ass, mov_text), and whatever is in tags.language and tags.title.

Step 2 — one stream is automatic, more than one is a question

A single track is used without asking. Several, and the codec and language tags from the probe are printed back so the choice is informed rather than a number in the dark, with stream 0 as the default:

Found 2 subtitle streams:
  Stream 0: webvtt (English)
  Stream 1: subrip (Spanish)      default: 0

Step 3 — extract, WebVTT first and SRT only as a fallback

The preference isn't stylistic. WebVTT carries <v Speaker> voice tags and SRT does not. Google Meet captions are WebVTT internally, so extracting one to WebVTT keeps the speaker attribution intact; converting down to SRT throws it away permanently. SRT is what you get when the source codec can't be converted to WebVTT at all.

# try WebVTT to a pipe first — cheap, and it either works or it doesn't
ffmpeg -i "$FILE" -map 0:s:$N -c:s webvtt -f webvtt pipe:1 2>/dev/null

# same map, different target codec, only if that failed
ffmpeg -i "$FILE" -map 0:s:$N -c:s srt   -f srt   pipe:1 2>/dev/null

# then write it for real, next to the input
ffmpeg -i "$FILE" -map 0:s:$N -c:s webvtt "$OUT" -y 2>/dev/null

-map 0:s:$N is the N-th subtitle stream of input 0, not absolute stream index $N — which is why the number shown in step 2 is the one that works here. The trial runs to pipe:1 rather than a file so a failed conversion leaves nothing on disk to clean up or mistake for a result.

Step 4 — the branch that makes the skill worth having

An empty probe is not a failure. The file is already local, so the skill hands off to transcribe-media and generates the captions from the speech instead:

skills/transcribe-media/transcribe.sh "$FILE" --format vtt   # or srt

Same .vtt or .srt on the other end, just derived from audio rather than lifted from a container — and, notably, without the speaker names, which is the cost of having had no track. The one case where that's the wrong route: a Meet recording that's still sitting in the Drive player and hasn't been downloaded. There, extract-gdrive-transcript wins, because it reuses Google's own speaker-attributed captions rather than re-recognising anything.

Step 5 — report the preview, not the byte count

Output lands next to the input with the extension swapped — recording.mp4 → recording.vtt — unless you say otherwise. Then it reports the path, the format, the file size, and a preview of the first few entries. That last part is the only real verification in the whole sequence: a subtitle file that extracted cleanly and one that came out as mojibake are indistinguishable by size, exit code or extension. Only the cues tell you.
