Not a browser and not a security boundary. Anything local can drive your Chrome while it runs.

agent-browser took your screen every time it opened a tab

Attached straight to your Chrome over CDP, agent-browser 0.41–0.43 pulls Chrome to the front and hides the tab you are on whenever it opens a tab. It calls Target.createTarget without background: true, and sends Page.bringToFront when it switches tabs. Measured on 2026-11-13: Chrome came to the front about 6 s into a run, and your tab stayed hidden for 14–17 s. Through the relay, nothing moved.

Upstream issue #1247 has been open since April 2026 with no maintainer reply, and the fix PRs (#1880, #2292, #1427) are unmerged. Every new attach also costs an "allow remote debugging" click, which an unattended run cannot give.

So the fix lives outside agent-browser: a small local relay that rewrites those calls on the way to Chrome.

Point agent-browser at the relay

agent-browser --cdp ws://127.0.0.1:9333/devtools/browser/relay --session mine tab new --label work https://example.com
  • Open your own tab and close it when done. Use tab new and tab close. close ends the agent-browser session, not the tab (the relay keeps Chrome open either way).
  • The browser skill picks it for you when browse is down and the job needs your signed-in Chrome.
  • Check it is up: curl -s 127.0.0.1:9333/stats returns the counters (createTarget, swallowed, focusEmu, upstreamConnects, clients) and "upstream":true once it holds a connection to Chrome.
  • Test it: cd tools/cdp-relay && npm test runs the real relay against a fake Chrome (a ws server) and checks each rewrite.

What it won't do

  • No lock on your Chrome. While it runs, anything local can drive your signed-in Chrome with no prompt. It binds 127.0.0.1 only. That is the accepted price of one Allow click.
  • Discarded tabs stay asleep. agent-browser revives a Memory Saver tab with Target.activateTarget, which the relay swallows. Open your own tab instead.
  • Chrome needs remote debugging on (chrome://inspect/#remote-debugging, Chrome 144+). With it off, the relay waits and retries.
  • Headless agent-browser does not need it. The relay changes nothing there.
  • macOS only as shipped: launchd and Chrome's DevToolsActivePort path.

Where it lives

Integrates with launchd: com.rascaltwo.cdp-relay, always on. agent-browser: --cdp ws://127.0.0.1:9333/devtools/browser/relay.
Requires node, npm and agent-browser.
Installed copy launchd may not read scripts under ~/Desktop (TCC), where the repo lives, so the plist runs a copy of cdp-relay.js and its node_modules in the state folder. Re-run the install after changing the script.
Its state ~/.agents/state/cdp-relay/: the installed copy and relay.log.
Safe to delete? Yes, deletion-policy: delete. It only holds the installed copy and its log; reinstall to restore.
Platform macOS (launchd, Chrome's DevToolsActivePort path).

One tab, end to end

One Node file, cdp-relay.js (178 lines, one dependency: ws). It runs two WebSocket sides and a table that remaps ids.

  1. Hold the one connection. At start, and every 5 s after (RETRY_MS), keepUp() reads DevToolsActivePort (port on line 1, path on line 2), probes the port with net.connect, and calls connectUp(): one ws socket to Chrome. That is where Chrome asks you to Allow. Under launchd, TCC denies reading Chrome's Application Support folder, so upstreamUrl() falls back to ws://127.0.0.1:9222/devtools/browser (CHROME_PORT overrides 9222).
  2. Accept a client. agent-browser connects to ws://127.0.0.1:9333/devtools/browser/relay. The relay waits for the upstream connection first, and closes the client with 1011 if Chrome is unreachable.
  3. Swallow three calls. Page.bringToFront, Target.activateTarget and Browser.close are answered at once with { id, result: {} } and never reach Chrome. swallowed counts them.
  4. Rewrite Target.createTarget. The relay sets params.background = true, so the new tab opens behind your work. When Chrome answers, the new targetId goes into the ours set.
  5. Remap the id. Every other command gets a fresh upstream id from a counter that starts at 1,000,000, stored in pending with its client and original id. Two clients that both send id: 1 cannot collide.
  6. Own the session. On Target.attachToTarget, the answer's sessionId is recorded in sessionOwner against that client. If the target is in ours, the relay also sends Emulation.setFocusEmulationEnabled to that session, so a hidden tab still takes clicks. Child sessions that arrive in Target.attachedToTarget inherit the owner and get the same treatment.
  7. Route answers and events. A response goes back to its client with the original id restored. An event with a sessionId goes only to that session's owner. An event without one (browser-level) goes to every client.
  8. Clean up. When a client leaves, its sessions and pending entries are dropped. When Chrome's socket closes, the relay clears all tables and closes every client with 1011; keepUp() reconnects when Chrome is back.

launchd (com.rascaltwo.cdp-relay, RunAtLoad and KeepAlive) starts the installed copy in ~/.agents/state/cdp-relay/ and sends stderr to relay.log.
