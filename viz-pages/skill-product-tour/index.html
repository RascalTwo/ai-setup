↓  WHY IT EXISTS

A tour should follow the user, not the Next button

Every project eventually needs a tour: onboarding in a real app, or a walkthrough an agent gives Joseph over finished work. On 2026-10-23 three options were tried on one test app: driver.js, Shepherd.js, and a hand-rolled guide. driver.js won. Shepherd.js is AGPL-3.0, or paid for revenue-earning companies since 14.0.1, it blocked clicks behind it, and it jumped between targets. A hand-rolled guide meant owning positioning and scrolling forever.

When to fire it

Any time a web app or page needs a tour, onboarding, guided walkthrough or spotlight steps, in a real app or injected into a build for a demo.

  • Steps are data: { id, say, target, done? }. say is HTML, target a selector (none means a centred bubble).
  • done is the user action: { sel, value }, { sel, text } or { sel } (the element appears).
  • In a walkthrough, say names where to look, never what is right.

What it doesn't do

  • It has no component bindings. It is plain driver.js, so it works in any framework but offers no React or Next.js wrappers.
  • It does not float on a loose version. Pinned to 1.10.2; bump on purpose only.
  • It leans on two driver internals. The overlay path stroke and the pointer-events override are marked UPGRADE CHECK in theme.css and can break on a release without saying so.
  • Watching is polling. Each done is checked every 300 ms; there is no event hook.

Why a watcher

driver.js only offers advanceOnClick on the highlighted element. That misses picking a select option or typing into an input, which are the actions a walkthrough cares about. So tour.js polls each step's done every 300 ms and calls moveNext() when it holds. A "skip ›" link is always there, so a step the user cannot or will not do never traps them.

Upgrade check: after any driver.js bump, look at the two rules marked UPGRADE CHECK in theme.css. The amber edge must still glide between targets, and clicks outside the target must still reach the app.
