↓  WHY IT EXISTS

GitHub forgets what you already read

A careful reviewer reads a pull request one commit at a time, because that is how the author built it and how it makes sense. GitHub does not help with that in three specific ways.

  • The files come in an order that has nothing to do with the story. The commit that changes the API and the commit that calls it are read in whatever order the page lists files.
  • There is no way to approve one hunk. You can leave a comment on a line, but you cannot say this piece is fine and move on.
  • A force-push wipes the reviewer's place. The author rewrites the branch to address comments. Now every commit has a new SHA, and you cannot tell which hunks you already approved, or which of your comments the new version answered.

There is a fourth problem, specific to talking to an agent by speech-to-text: a hunk's name has to be something the reviewer can say out loud and have heard correctly. A SHA, a line number, or src/cart.ts:42 will not survive dictation. “Amber falcon” will.

Using it

The skill fires when the user asks to review a branch, a PR or a commit range commit by commit, or says “hunk review”, “review viz” or “let me review the commits”, or right after pr-shape reshapes a branch they are about to read. The agent runs six steps; the reviewer's part is step 3.

1 · open review.ts open <name> --repo <path> --range base...head. Several --repo pairs make one review across repos. It prints the page's URL.
2 · order The agent writes order.json: for each commit, a one-line “why read this now” and the files in the order it would explain them.
3 · read The reviewer marks hunks and files, then presses Send review. Or just says it in the terminal: “amber falcon: rename it”.
4 · status review.ts status <name> lists every flag, question, addressed and changed item by ID, with notes and replies.
5 · reply review.ts reply <name> <id> <text> answers on the hunk. The agent fixes, rewrites and force-pushes as the work needs.
6 · refresh review.ts refresh <name>. The page reloads where the reviewer was. Back to step 3.

The keys on the page:

j / k Next and previous hunk. Past the last hunk of a commit, on to the next commit.
a Approve the focused hunk, and step to the next one. Pressing it again clears it.
c / q Mark “change this” or “question”, and put the cursor in the note field.
J / K Next and previous file.
n / p, g / G Next and previous commit; first and last hunk of the commit.
A Approve every hunk in the focused hunk's file.
o / O Fold the hunk, or the whole file down to its hunk bars.
[ / ] More lines above the hunk, or after the file's last hunk.
v On a changed hunk: only what changed since you saw it, or the whole hunk.
i, r, s, ? Edit the note; refresh from git; send the review; list every key.
Alt-click, 🎙 Comment on anything through the viz feedback widget. It lands in .viz-data/feedback.jsonl anchored to the hunk or file ID.

Each file also has ✓ all, which approves every hunk in it, and its own ✓ ✎ ? for a mark on the file as a whole. Every hunk, file, commit and the whole review shows its lines added, changed and removed. Only approved hunks and fully approved files start folded; a folded file still lists its hunks' bars. A hunk that changed since you marked it shows only what changed since you saw it, with the agent's reply under the first change; v switches to the whole hunk.

What it does not do

  • Local only. The review is a viz page served from 127.0.0.1. Nobody else can open it, and it is created with viz:posture “local”.
  • No GitHub sync. Nothing is posted to the pull request. Marks, notes and replies live in this page's folder and nowhere else.
  • It does not watch. A range is followed by branch name and re-read when you press ↻ Refresh or the agent runs refresh. Push, and nothing happens until one of those.
  • Editing a hunk's changed lines makes it a different hunk. Even for a one-character change. You get a re-review, not a silent pass. That is the point, and it costs a second look at tiny edits.
  • Context-only changes do not reset a tick. If only the unchanged lines around a hunk move or change, your approval stands. The fingerprint never sees them.
  • A mark can end up with nowhere to go. If its content is gone and no unmarked hunk in its file shares a changed line with it, it becomes an orphan, which status and the page list. Raise it with the reviewer; it is not dropped. If a hunk moves to a different path, its mark still looks for a home only at the old path, so it becomes an orphan.
  • A carried mark needs one shared line. A gone mark moves only to an unmarked hunk that shares at least one changed line with it, the most similar one. A hunk rewritten from scratch therefore comes back as an orphan plus a fresh unreviewed hunk. A carried mark always arrives as changed or addressed, never as a plain tick, so you re-read it.
  • Merge commits are not shown (the range is read with --no-merges).
  • pr-viz's own review mode has not been switched over to it yet.

Where it lives

The skill skills/hunk-review-viz/: SKILL.md; lib/review.ts (git, parsing, fingerprints, ordering, marks); lib/words.ts (the IDs); scripts/review.ts (the CLI); template/ (index.html, app.ts, api.ts, contract.ts, review.css), the page each review is made from.
Declared kind: skill, state: true, requires.skills: [viz, pr-viz] and commands: [git, node]. No integrates block and no deletion-policy.
Requires viz: every review is a viz page, made with viz create --from the template, served on 127.0.0.1:5180, with the feedback widget for Send. pr-viz: lib/review.ts imports its kindOf to tell code from tests, docs, lockfiles and binaries. git reads the commits. node runs everything.
Its state ~/.agents/state/hunk-review-viz/reviews.json: review name to page folder and URL, and nothing else. The marks are not here.
Per review A page folder called hunk-review-<name>, in the viz library (review.ts dir <name> prints it): review.json (repos and ranges, written by open), order.json (the agent's), .viz-data/state.json (marks and replies), .viz-data/feedback.jsonl (Send and spoken comments), refreshed.txt.
Safe to delete? The index, yes: it is only names. Delete it and the marks survive in their folders, but the name no longer resolves, and open would ask viz to create a page that still exists. A page's state.json, no. That is every mark the reviewer made and nothing else holds a copy.

What applyMarks does with a mark

similarity = changed lines both hunks share ÷ changed lines in either, whitespace trimmed, 0 to 1

kept The mark's fingerprint is still in the review. It applies as it was (✓ approve, ✎ change this, ? question; a replied question shows as answered). It can now sit in a different commit.
changed Fingerprint gone, it was ✓. Moves to the most similar unmarked hunk in the same repo and path that shares at least one changed line. Shown as changed since you approved, with what you approved underneath.
addressed Fingerprint gone, it was ✎ or ?. Same move. Shown as addressed: re-review, with your note, the agent's reply and what you marked.
orphan Fingerprint gone and no unmarked hunk left in that file. Reported by status as content gone, with nowhere to carry it.

Why the fingerprint hashes only the changed lines

A rebase renumbers every line, and a force-push gives every commit a new SHA, so neither can be part of the identity. What survives a rewrite is what the hunk adds and removes in a given file. So the fingerprint is sha256(repo, path, the + and − lines). The @@ header, the context lines and the commit are left out. That is why moving a hunk to another commit keeps its mark, and why a context-only change does not reset a tick.

Why the ID is a function of the fingerprint

words() takes the first eight hex digits of the fingerprint and maps them onto 126 adjectives and 120 nouns, so the same content always has the same two words: about 15,000 pairs, all common words that speech-to-text spells right. If two different fingerprints in one review land on the same pair, the second gets a third word in front. What you say is normalised the same way (normalizeId: lowercase, anything that is not a letter becomes a space), so “Amber-Falcon” and “amber falcon” are the same ID. reply even answers an ID whose hunk has since been rewritten away, because the old mark still knows it.

Where the page gets its data

The page folder holds a thin api.ts that imports the skill's lib/review.ts by the path open wrote into review.json. Two routes: GET /review returns buildReview(dir) (git is read fresh on every call), and POST /mark calls setMark. state.json is written to a .tmp file and renamed, so a reader never sees half a file, and the page sends ✓ all one mark at a time because each mark reads, changes and rewrites the whole file.
