↓  WHY IT EXISTS

A viz about an app lived somewhere else

A viz could explain a running app only from a browser tab or the app-panel: a screenshot with boxes drawn on it, true until the window moved, the app scrolled or the screenshot aged. big-arrow could point at one thing on the real screen, but a tour, five labels at once, or a diagram laid over a toolbar needed a whole page, and nothing hosted one there.

viz-overlay hosts any viz page over the real screen and keeps it aligned to the thing it is about. The page draws; the host finds the target, follows it and reports where it is.

Find the target, show the page

# what can it lock onto? labelled elements with their screen rects
viz-overlay elements --app Finder --match back

# show a viz over it (a viz id, URL or file)
viz-overlay show finder-overlay-tour --target Finder --element Back

# talk to the page while it runs: overlay.on("data") gets it
viz-overlay update 4182 '{"step": 2}'

# see and end what is running
viz-overlay list
viz-overlay stop --all

The skill fires when you ask an agent to annotate, tour or explain a running app in place, or to point at one thing or several at once. show raises the target once, fails fast with exit 3 when it is not there, and returns once the page is up. One rule decides when the viz-overlay shows:

target
while the target is on screen and no other app's window covers it (the default with --target)
pane
while Ghostty is frontmost and this session's herdr pane is focused (the default without one)
always
always

What it will not do

  • macOS only. The host is a Swift binary (helper/build once, with the Xcode command line tools). The page contract itself has nothing macOS-specific in it.
  • Element targets need Accessibility for the terminal app, and only reach what the app exposes. Chrome exposes page content for some tabs and not others; then measure the element in the browser and pass --rect.
  • A rect rides on its window, not the page. Scrolling inside a web page does not move a --rect; measure again.
  • It never takes the app away from you. Clicks pass through except over the page's [data-overlay-hit] elements, and the app you are in stays frontmost. A text field in the overlay borrows the keyboard until you click elsewhere.
  • Messages need herdr. Outside a herdr pane, what the page sends only reaches the log.
  • Slow full listings. A whole-app elements walk can take about 6 s on a busy app (Finder's desktop). A target stops at its first exact match and then re-reads only that element.

Where it lives

The skill skills/viz-overlay/: SKILL.md, reference/contract.md (the page API), page/standalone.js, helper/ (the Swift host and bridge.js), test/, THIRD_PARTY_NOTICES.md (code ported from bigarrow, MIT).
Integrates viz: a viz id or URL is the page; the page contract lets it target real windows. herdr: what the page sends is typed into the session's pane, and --when pane follows the pane's focus. ghostty: --when pane shows only while Ghostty is frontmost.
Its state ~/.agents/state/viz-overlay/logs/<id>.jsonl: one JSON event per line per overlay (shown, hidden and why, target changes, sends, page errors, closed). deletion-policy: delete: logs only, safe to remove. Running overlays are listed in $TMPDIR/viz-overlay/.
Requires herdr. macOS plus the Xcode command line tools to build the host. Accessibility for the terminal app, for element targets, window titles and raising.

One page, two homes

Every overlay page must also render without the host. show --save-snapshot FILE records everything the page was given (rects, track states, elements() answers); page/standalone.js's fromSnapshot replays it in a browser, so viz verify and a reviewer see the page as it looked over the app.

Why not part of app-panel

Both put a web page in a native panel and type messages into the pane, so one host could serve both. They stay apart for now (ADR 2026-11-11-keep-viz-overlay-beside-app-panel): app-panel is deleted once Claude Code renders MCP Apps itself, and viz-overlay should not be tied to it before either has had real use.
