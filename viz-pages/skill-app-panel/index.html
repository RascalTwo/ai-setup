↓  WHY IT EXISTS

The agent can run a tool, but not show you its screen

MCP tools can ship an interactive view (a ui:// page: a chart, a form, a QR code). Claude Code runs the tool and drops the view. Separately, a task that takes twenty minutes is a terminal that says nothing, and anything visual an agent wants to show you has nowhere to go.

app-panel is one MCP server that fills the gap until Claude Code renders MCP Apps itself, at which point this skill is deleted. It puts all of it in one floating panel beside the terminal, and what you press there is typed back into the session.

Show it, track it, or proxy a server

Two tools of its own. show puts HTML the agent writes (any library or site may load) or a page by URL in the panel; in that HTML, panel.send(text) messages the agent. progress shows a long task as one view updated in place: stages, a real count or a bar filling toward an estimate, then green or red. The host's instructions tell every session to use one of them for work over a minute.

From a shell, the app-panel-progress command posts to the same function. Given -- <command> it wraps the command and finishes the bar by its exit code, in the foreground or the background. Try the bar below: it is the same idea, driven by a timer instead of a command.

Servers with views go in ~/.config/app-panel/servers.json, not claude mcp add, because a server Claude Code connects to directly loses its views. The host offers their tools as <server>__<tool> and opens a tool's view in the same panel.

What it will not do

  • macOS only for the floating panel. It needs the helper binary (helper/build once, with the Xcode command line tools). Without it, or elsewhere, views open in a browser tab.
  • It hides itself. The panel shows only while Ghostty is frontmost and the session's herdr pane is focused. A view for a pane you are not looking at waits, hidden.
  • Replies need herdr. Outside herdr there is no pane to type into, so a view's message has nowhere to go and the view gets an error back. While a permission prompt is open herdr refuses to type, so the host retries every 2 s for up to 10 minutes.
  • A show by URL is framed at a fixed 640 px height, and panel.send is not available inside it: that page is another origin, so it can be neither measured nor scripted.
  • Not yet bridged: view permissions (camera, mic), file downloads, display modes other than inline, and app-provided tools. A view opened again from the list starts fresh.
  • Registered by hand. Server changes reach new sessions; a running one needs /mcp reconnect. Some ext-apps example servers need uv run --with 'mcp<2' ….

Where it lives

The skill skills/app-panel/: SKILL.md, host.ts (the MCP server), lib.ts, progress.ts (the command), page/ (the panel's relay and progress pages), helper/Panel.swift, reference/research.md.
Integrates herdr: the panel follows its pane, hidden while another pane is focused. ghostty: the panel sits at the terminal window's corner.
Its state ~/.agents/state/app-panel/sessions/<pane>.json: one file per herdr pane, how the app-panel-progress command finds its session's host. deletion-policy: retain, so it is kept. Your servers live in ~/.config/app-panel/servers.json.
Requires bun. For the floating panel, macOS plus the Xcode command line tools to run helper/build once. herdr, for a view's messages to reach the session.

One panel per session, newest on top

Every view goes in the one panel, and earlier ones stay in its list. A finished task given the same title again starts a new view; a successful one folds the panel 5 s after it ends. The panel page is only a relay: view, sandbox frame, page, WebSocket, then the AppBridge in host.ts, running against the real server.

Why herdr typing

Claude Code channels were the first delivery route, but their dev flag stops every launch at a warning screen. Typing into the pane replaced them; the switch back waits for channels to accept a custom server without the flag. The reasoning for MCP Apps over other specs is in reference/research.md.
