The description is written last, by the person who needs it least

By the time a branch is ready you have lived in it for days. The PR body gets written from memory of the diff, for the one reader who doesn't need it. Then a reviewer spends their first minute on it to decide how to read everything else, and gets one of two things: "Fixes the thing", or four screens of fluent prose that restates the diff.

Agents made it worse in a particular way. They write the body fast, and they post it. The first human to read it is a reviewer, notified, on a public thread. Then every new push either leaves the body stale, or an agent rewrites the whole description and takes with it the sentence you tightened and the Evidence section a reviewer asked for.

And one more, upstream of both: the PR that describes a change that isn't ready. It claims a behavior no test pins, and the body reads confidently anyway. r2-pr's job is the description. It won't write one for something it can't back.

Say "open a PR", then read what it hands you

There is no slash command. The skill fires when you ask to open, draft or update a PR or its description. Its first step looks for an existing PR on the branch (gh pr view <branch>) and that alone decides which of the two flows you are in. The skill asks you for exactly four things:

A ruling If the readiness check finds a gap, it stops and lists it with what would fix each. You fix it, ask r2-pr to, or say go ahead as it is. That last answer puts the gap in the body.
The yes It hands you the draft's path, a rendered preview and the title. Your approval of that draft is the one gate.
A force-push Asked every time. A plain push is not.
Ready The PR goes up as a draft. You flip it, unless you said otherwise up front.

It describes. It does not fix, watch or merge.

  • It fixes nothing in your branch. Step 3 pushes back ("no test pins that clients without gzip get plain JSON: add one?") and waits. A go-ahead is allowed, but then the gap goes into the body under Not proven yet, in public.
  • It does not watch CI, answer reviews or merge. Its remit is the body, its layout, getting it onto GitHub, and refreshing it after new commits.
  • Once posted, written sections are people's. When one is stale after a push, it says so and proposes the edit; it applies it only on a yes. Only its two marked sections are refreshed unattended.
  • It cannot add a marker to an old PR. sync throws when the live body lacks a section it was asked to refresh. A PR opened before r2-pr:look existed gets it added by hand, once, under Why, with a yes from you.
  • The local preview is not GitHub. It is Bun's markdown renderer plus two shims (alert boxes and #123 links). --github renders exactly, but sends your draft to GitHub, so it only runs when you ask. Even the local page loads three open-source libraries from a CDN (stylesheet, highlighter, mermaid); none of the draft leaves the machine.
  • It cannot see the video play. Its final check opens the PR page, and Chrome won't load video in a background tab. The skill says so, and calls that not GitHub's fault.
  • The repo's own PR template wins. Its headings are the written sections, in its order. r2-pr's layout fills in around it.

Where it lives, and what it leaves behind

The skill skills/r2-pr/SKILL.md (eight steps), reference/body.md (the body's layout and the GitHub facts behind it), scripts/body.ts (104 lines, the mechanical parts).
Declared kind: skill, state: true, deletion-policy: retain.
Its state ~/.agents/state/r2-pr/<owner>-<repo>/<branch>/: the draft pr.md and its rendered preview pr.html beside it. Retain. The update path rebuilds from pr.md, so this is the PR's working copy, not scratch to sweep.
Integrates GitHub through gh: push, pr create/pr edit, and GitHub's markdown renderer (gh api markdown, the opt-in --github path).
Requires gh, git, bun. Bun is load-bearing: the local preview calls Bun.markdown.html directly.
Borrows from pr-split (is it one change?), pr-viz (the walkthrough and the Where-to-look lines), github-attach-media (hosting the video and image), unslop on every sentence it writes, and r2-sdlc's understood.md when that ran on the branch.

Eight steps, and one border they cross

Everything left of the yes happens on your disk. Step 7 is the only place bytes leave it, and step 8 is the same trip again with a smaller payload.

Amber is the gate. The dashed edge is the other entrance: step 1 finds a PR already there and goes straight to update.

Two of those steps are verdicts rather than work. Step 3 compares the branch with what the PR is about to claim (every claimed behavior has a test, touched tests pass, nothing uncommitted, merges cleanly, no doc left stale), then runs pr-split on every PR whatever its size. If the answer is "pieces", this run ends there and each piece's branch re-enters at step 1. Step 6 is the only approval, and an edit sends you back through redraft and re-preview.

The only code moves words. It never writes them.

scripts/body.ts opens with its own rule: "The words are the agent's; this only moves them." Three verbs, each a branch of one if chain: 

# 1. render the draft here, open pr.html beside pr.md (body.ts:41)
bun "$R2PR/scripts/body.ts" preview pr.md <owner/repo>

# 2. swap local media paths for uploaded URLs (body.ts:79), body to stdout
bun "$R2PR/scripts/body.ts" finalize pr.md video=<url> image=<url> > final.md

# 3. replace ONLY r2-pr's marked sections on a live PR (body.ts:88)
bun "$R2PR/scripts/body.ts" sync final.md <owner/repo> <number>

The draft names its media by local path, one per line: r2-pr:video <path> and r2-pr:image <path>. One regex (MEDIA, line 19) finds them, and each verb reads them differently. preview (rendered by Bun.markdown.html, line 50) parks each as a marker the markdown renderer passes through, then drops in a local <video> or <img> (and prints missing video: path in bold if the file isn't there). finalize turns the video into a bare attachment URL on its own line, which is how GitHub embeds a player, and the image into an <img width="1400">. It throws if you forgot a URL.

A regex decides who owns a sentence

Every section r2-pr is allowed to refresh sits between <!-- r2-pr:<name> --> and its closing twin. That is the whole ownership model, and it is one regular expression (line 20): 

const SECTION = /<!-- r2-pr:([\w-]+) -->[\s\S]*?<!-- \/r2-pr:\1 -->/g;

A rebase doesn't even reach sync. The body names no commit anywhere a reader sees it, because a commit ID is stale on the next push for nothing. So step 8 compares git diff <old-range> with git diff <new-range>. Same patch means a rebase: it re-pins pr-viz's plan to the new head and stops. Nothing a reader sees has changed, so nothing is rewritten.

The body has a minute line

The layout in reference/body.md is two altitudes. Above the divider is what a reviewer reads before choosing how to review; below it is everything else, opened by the film. 

section links, then:
[Why] · [Where to look] · [In depth] · [How] · [Evidence] · [Rollout] · [Not in this PR]

## Why              two or three sentences, from the reader's side
<!-- r2-pr:look -->
## Where to look    start here · skim or skip · not sure about · feedback wanted
Size: 22 files, 515 lines to read (132 code, 383 tests)   ← classify.ts, verbatim
<!-- /r2-pr:look -->
**Proven**: before → after, one line, then each acceptance criterion and what proves it

---  In depth
<!-- r2-pr:walkthrough --> video · note · image · changes <!-- /r2-pr:walkthrough -->
## How · ## Evidence · ## Rollout · ## Not in this PR

Where to look is not prose r2-pr invents each time. Its four lines are pr-viz's plan.json lookHere, word for word, and the size line is classify.ts's output verbatim: a computed fact with no verdict attached. Evidence carries the strictest rule in the skill: every item is re-runnable, with its exact input, command and printed output under a collapsed Re-run, and the command was run by r2-pr before it went in. Anything that would need a throwaway test to prove is really a missing test, and gets caught back at step 3.

Why the body is shaped around GitHub's quirks

Each of these is in reference/body.md as a checked fact, and each explains a layout choice that would otherwise look strange:

  • PR-body headings get no anchors, so #why goes nowhere. An explicit <a id="why"> survives as user-content-why, and the section links point there.
  • A link can't open a collapsed <details>, so the section links skip the walkthrough; it sits right below them anyway.
  • GitHub strips a video's poster attribute but shows its first frame, so pr-viz paints the hero onto frame one.
  • A code fence has one language: syntax colours or diff colours, never both. So the changes walkthrough shows added-only hunks in their language and changed hunks as diff.
