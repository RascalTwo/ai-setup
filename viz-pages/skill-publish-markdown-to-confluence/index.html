↓  WHY IT EXISTS

The problem

Your doc lives in markdown. Confluence stores its pages as ADF — Atlassian Document Format, a JSON tree. Nothing bridges those two by hand, so "publish it to the wiki" degenerates into pasting into the editor and watching tables, links and headings come out wrong. Every republish, again.

The turn

One command converts markdown → ADF and replaces the page body. The doc stays the source of truth on disk; Confluence becomes a render target. Say "publish this to Confluence", "push this markdown to the wiki", "sync this doc to that page" — then give it three things:

  • The source file — the markdown to publish.
  • The target page — a full URL (…/wiki/spaces/FOO/pages/12345/My+Page) or a raw numeric page ID. From a URL it takes the ID out of /pages/{id}/ and the hostname as the cloudId; from a bare ID it has to ask which site.
  • Rows to drop, optionally — --drop-row "Source" for field-table rows that only make sense locally.

If you don't name a page, it asks. It does not guess, and a 404 on the fetch stops the run rather than quietly picking a different page.

The limits

The converter is deliberately narrow. No bullet or numbered lists, no fenced code blocks, no multi-paragraph blockquotes, no nested tables. Hit one of those and you extend md-to-adf.py — you do not hand-edit the ADF output. (A - bullet does survive as a paragraph with a literal leading dash, so a short list publishes legibly, just not as a real ADF list.)
  • Needs python3, a standalone Atlassian MCP registration, and edit access to the target page.
  • It replaces the whole body. There is no partial update and no diff — for surgical edits to a page a human owns, that's confluence-editor, which leaves its work unpublished for review.
  • A claude.ai-managed connector cannot publish, however well its tools work in-session. That's a dead end rather than a misconfiguration, and the skill says so with the diagnosis attached.
  • It's content-agnostic on purpose. Domain conventions (a journal format with provenance rows) belong in a thin caller that supplies the right --drop-row flags and target page — not in this skill.

One publish, markdown to live page

Five steps, three scripts, and one rule that decides the shape of the last two: the body never travels through the model's output.

← → arrow keys

What survives the conversion

  • Headings #…######, pipe tables (first row is the header, separator discarded), links, **bold** and _italic_, single-line > blockquotes, --- rules. YAML frontmatter is stripped.
  • Date pills. A bare YYYY-MM-DD inside a table cell becomes a real ADF date node — a native Confluence pill. Dates in narrative paragraphs stay plain text, which is what you actually want.
  • Row-dropping. --drop-row "NAME" strips field-table rows that only make sense locally — provenance, debug metadata — before anything is published.
  • Confluence-native elements you added in the UI. A fresh ADF body would wipe ToC macros, info panels, Smart Links and Jira embeds — markdown can't express them, so the converter can't regenerate them. preserve-extensions.py lifts them off the current page, anchors each to its nearest preceding heading, and re-splices them into the new body.

That preserve set is a named list — extension, bodiedExtension, inlineCard, blockCard, embedCard. A macro type outside it gets dropped on the next republish, and the fix is to extend PRESERVE_TYPES.

The receipt

Fetch the current page (and keep it — the preserve step needs it), convert, splice, push:

# 1. getConfluencePage with contentFormat:"adf" → save to /tmp/current-page.json
# 2. convert + preserve
python3 <skill-dir>/md-to-adf.py <source> --drop-row "Source" > /tmp/adf-full-raw.json
python3 <skill-dir>/preserve-extensions.py /tmp/current-page.json /tmp/adf-full-raw.json > /tmp/adf-full.json

# 3. push from disk — never inline the body
python3 <skill-dir>/mcp-http-call.py updateConfluencePage /tmp/update-args.json

The push goes through a direct Atlassian MCP HTTP client: it reads the bearer token from the keychain, runs the MCP initialize + notifications/initialized handshake, then POSTs a tools/call whose arguments it loads from a file. Inline tool-call args flow through the model's output tokens — fragile above a few KB, where character-level corruption, escaping bugs and hard size limits all live. The disk path is tested at ≥600KB of args.

Why the managed connector is a dead end

Having working mcp__*Atlassian*__* tools in your session does not mean this can publish. Atlassian access arrives from one of two places and only one of them carries a token this script can use:

                        standalone server      claude.ai-managed connector
serverUrl in keychain   mcp.atlassian.com/…    api.anthropic.com/v2/ccr-sessions/…
accessToken             the real bearer        empty string
in-session tool calls   yes                    yes
mcp-http-call.py        yes                    no

The managed connector is proxied through api.anthropic.com and authenticates with the claudeAiOauth session token rather than a per-server one, so its mcpOAuth entry exists with an empty accessToken. Substituting the session token doesn't rescue it: the handshake succeeds, a session id comes back, and then every tools/call returns -32003 "MCP tool call requires approval" — the proxy gates each call behind an interactive channel an out-of-band HTTP client cannot satisfy.

Diagnose before believing it. Dump the mcpOAuth rows and read the serverUrl and whether accessToken is set. If the only Atlassian rows are EMPTY against api.anthropic.com, register the standalone server and re-check the keychain — the token is shared, so it becomes usable immediately, and handing the job to another session is usually unnecessary.

Where the keychain path doesn't exist at all — a different OS, no Claude Code — the documented fallback is a Confluence REST PUT to /wiki/api/v2/pages/<id> with a personal API token, sending the same ADF as atlas_doc_format.
