The problem

You're three commands deep into something real and an aws call dies. Not because the work is wrong — because a one-hour token quietly ran out. Now the task is on hold while you go find a browser tab, expand an account tile, and copy-paste export lines. The interruption costs more than the credentials do.

The turn

Hand the whole errand to the agent. It reaches the portal in Chrome, verifies it opened the right account, copies the credential block, and writes it to ~/.agents/state/aws-sso-creds/<portal>-<account>.env at mode 600. It prints the path, the account ID from sts get-caller-identity, and the expiry — never the secrets.

"Why not just set SSO up properly?"

Because that's work, and this is lazy — the good kind. Doing it the official way means an ~/.aws/config sso-session plus a named profile for every account you ever touch, configured up front and maintained forever. That's a chore you pay before you get to do the thing you actually wanted to do.

And it only pays off for tools that know how to resolve an AWS profile. This drops temporary credentials into environment variables — the one credential path that works with everything: the CLI, Terraform, boto3, an SDK, a one-off script that never heard of a profile. Nothing to configure per account, nothing to maintain, and the creds expire on their own in about an hour, so the lazy path is also the one that leaves nothing lying around.

The trigger

It doesn't wait to be asked. Any of these in an aws call's output is enough:

  • ExpiredToken · InvalidClientTokenId
  • UnrecognizedClientException · Unable to locate credentials

That's the selling point. The failure is the invocation — the thing that used to interrupt you now just fixes itself and the task keeps moving.

Consuming the result is one line, because the Bash tool doesn't persist env between calls:

set -a && source ~/.agents/state/aws-sso-creds/<portal>-<account>.env && set +a && aws sts get-caller-identity

The scope

  • Never types a password. A password prompt means the session died — that's the human's job, and it stops.
  • Never guesses an account. Ambiguous request, or a name that isn't listed → it asks. It also verifies the account ID after the fact rather than trusting the tile it clicked.
  • Read-only by default. These creds often carry write permissions; it won't run mutating commands unless that was the ask.
  • Doesn't recover a dead session. Tab died, portal shows signed-out → restart from the portal URL. There is no reconnect path.
  • One account per run. The dotenv holds one account's keys. A second account is a second run and a second file.

The run, end to end

One invocation, from an empty Chrome tab to an aws call that answers with the account you asked for.

← → arrow keys

The portal is a website, so it gets driven as one

There is no device-authorization API call here and no aws sso login. Step 0 loads six Chrome tools in one batched ToolSearch — tabs_context_mcp, tabs_create_mcp, navigate, javascript_tool, find, computer — and everything after that is clicking. Landing on login.microsoftonline.com or an Okta page is an SSO redirect, so completing it is in scope: find the row for the user's account and click it. Landing on a password field is not: that means the browser session expired, and the skill stops and hands it back.

Verifying the account is a regex, and the regex has a scar

Account rows collapse by default and the expand chevron is a small target, so it clicks the account name instead. Then, before anything is copied, javascript_tool walks every [role="dialog"] and reads the account out of the modal's own text:

d.textContent.match(/Create access for the account\s+(.+?)\s*\((\d+)\)/)

That (.+?) used to be \S+?, which matches a single non-space token. Account names contain spaces — "Example Corp Dev" — so the old pattern silently failed on every multi-word account and reported NO_CRED_DIALOG against a perfectly valid modal.

NO_CRED_DIALOG means "no modal found", not "wrong account". It is never a pass. If it comes back while a credentials modal is plainly open, the selector or the regex has drifted from the portal's markup — confirm the account from a screenshot before copying anything, and fix the snippet. Portals also render several modals at once, so a stale one can still be in the DOM.

Copy, don't read

It finds the copy button for Option 1: Set AWS environment variables and clicks it. The three export lines go onto the system clipboard and from there straight to disk, so the secrets never enter the transcript. Extracting the values with javascript_tool and pasting them into a bash command would round-trip live credentials through chat — so the skill forbids it outright.

The receipt

The write carries two scars — both real, both bite:

# 1. the portal's code block is CRLF; a stray \r corrupts the
#    Authorization header -> "Invalid header value"
# 2. the block has NO trailing newline, so AWS_REGION lands on the
#    end of AWS_SESSION_TOKEN -> InvalidClientTokenId
mkdir -p ~/.agents/state/aws-sso-creds && chmod 700 ~/.agents/state/aws-sso-creds
umask 077
{ pbpaste | tr -d '\r' | sed -E 's/^export //; s/"//g'; echo; echo "AWS_REGION=us-east-1"; } > "$OUT"
chmod 600 "$OUT"

The bare echo between the two is the entire fix for bug #2. On Linux, pbpaste becomes xclip -o -selection clipboard or wl-paste.

Debug by length, never by value

When something looks wrong, the file is inspected without printing any of it:

awk -F= 'NF{printf "%s len=%d\n", $1, length($0)-length($1)-1}' "$OUT"
# expect: AWS_ACCESS_KEY_ID len=20, AWS_SECRET_ACCESS_KEY len=40,
#         AWS_SESSION_TOKEN len~1000, AWS_REGION len=9

A session token ending in -east-1 means bug #2 bit you. And the last thing the run does before reporting success is source the file and compare sts get-caller-identity against the account ID recorded in portals.md — a mismatch prints WRONG ACCOUNT and exits non-zero, because the tile it clicked is a guess and the caller identity is not.
