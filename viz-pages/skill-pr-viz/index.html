The diff is alphabetical. The change is a story.

"Files changed" lists files by path. The change happened in a different order, for a reason, and the reason lives somewhere else: in the description (what the author meant), in a linked issue (why anyone cared), in a review thread from last week (why that line is odd), in a test (what is actually pinned). The diff is the evidence. It was never the case.

So a careful reviewer's first hour is not reviewing, it is research: open each file at head, read the whole function and its callers, work out what proves each behaviour. And that research falls on the one person who did not write the code. The tempting alternative is to skim and trust the description, which is a review of the author's summary.

pr-viz moves the research to the front. Its research step is to read like the reviewer who has to defend the change, and the answer is written down in the order a person understands a change: Why, What, Where to look, How, Proof, Risk and rollout, Check these. Every changed line of production code appears in the How. Every behaviour the PR promises is traced to what proves it, or marked untested or partial in plain words. The film is self-contained: it covers all seven chapters as if the viewer had read none of the PR body.

Say "pr viz". Get a film, a page, and a picture.

Triggers: explain this PR, demo this PR, turn it into a video, pr viz, review video, PR film. It also fires without being asked: r2-pr step 4 runs it through the hand-over on every PR, unless you said to skip it. One plan renders four ways, picked by the URL hash:

Reading What it is
film The default. A narrated walkthrough with a chapter bar; How includes a tour of every changed line. viz render makes it an mp4.
#{"cut":"short"} The short cut: a fifth of the length, for a stranger who will not watch the full one. Why, the headline What, Where to look. Reuses the full film's scenes and clips; nothing new is written or spoken.
#{"mode":"review"} The same scenes as a page, with the transcript, the full diff, the acceptance criteria and a reviewed box per file in story order. "▶ watch" plays that scene in place.
#{"mode":"poster"} Only the pictures, every scene finished, the diff tour as the film shows it. One tall image for anyone who will not play the film.

Plus a hero: the one scene, named in plan.json, that alone tells a stranger what the PR does, as a 1080p still. What you are handed at the end: the mp4, the short cut with its .vtt, the hero, the poster, the changes walkthrough as markdown, a chapters list for a video description, and the live URL.

It enforces coverage. It cannot enforce that the narration is true.

What the gate counts. build.ts compares hunk ids: every production hunk must appear in some tour entry. It cannot read the say line attached to one. A sentence can claim anything about a hunk it covers. What keeps the claims honest is the research step and a person reading every full-size chapter frame, which are habits, not code.
  • "Every line" means every production line. Files are classed by path (classify.ts): a plan.json override first, then binaries, lockfiles, tests, docs, and everything else is production. Tests, lockfiles, docs and binaries need no tour entry, and a binary's hunks are emptied outright. A manifest bump like package.json is production, and gets narrated.
  • It stops at the hand-over. It makes the files. Putting them on a PR is r2-pr's job, and uploading the media is another skill's.
  • It is local by default. The template ships viz:posture = local, unlisted, and says why: a review film of someone's PR is not for the open web unless you decide it is.
  • The add-ons are narrow. The call graph is Python only, standard-library ast, resolving calls by name inside a package root: dynamic dispatch, aliasing and getattr are invisible to it. The fixtures add-on reads PDFs. A saved diff has no checkout to walk, so both are skipped there.
  • A tick is yours alone. Reviewed-ticks live in the browser's localStorage, per PR. They are not shared with the next reviewer.
  • It cites only what the audience can see. Tests, CI, real runs, public docs. Never a local skill or an internal review bot: they cannot check it, so it proves nothing.
  • It is not quick. Voice for every line, verify twice, then two renders as background jobs, then stills. 3D is only for a PR where depth means something; 3D views that said what 2D already said were cut.
  • The markdown walkthrough leaves out import-only hunks. They are listed at the end with links. The film still walks them: that is its promise.

What it leaves behind, and where

The skill skills/pr-viz/: SKILL.md; scripts/ (build.ts, classify.ts, review-order.ts, stills.ts); template/ (index.html, pr-viz.ts at 941 lines, pr-viz.css); reference/ (plan, scenes, style, research, 3d); addons/ (callgraph.py, python_callgraph.py, pdf_fixtures.py).
Declared kind: skill, state: true, requires: [viz, bun, ffmpeg]. No integrates block and no deletion-policy.
Its state Real, but not in a folder of its own: there is no ~/.agents/state/pr-viz/. A run leaves (1) a viz in the viz library, ~/.agents/state/viz/pr-<n>-<slug>/, holding plan.json beside the files derived from it, plus .verify/ and .tts/ caches; (2) the outputs on the Desktop (~/Desktop/pr-<n>.mp4, .short.mp4, .hero.png, .poster.png, the default of stills.ts); (3) the reviewer's ticks, in their browser.
Deleting it The manifest declares no deletion-policy, so this is a reading of the source: hunks.json, narration.json, callgraph.json and fixtures.json regenerate from build.ts, and the mp4s from a render. plan.json, and the research behind it, do not.
Requires viz (the page, its server and kit, verify, render; stills.ts borrows its puppeteer and Chrome lookup), bun, ffmpeg (the hero frame, the stacked poster). Only when a change calls for them: python3 for the call graph, uv with pypdf and pillow, and pdftoppm, for PDF fixtures.
Called from r2-pr, step 4, on every PR. Its sibling pr-split imports classify.ts from here to tell production code from tests, lockfiles and docs.

    From a say line to a beat
    
      
    
        Every say line is one beat, numbered across the whole film; a tour entry is a
        beat too. build.ts writes narration.json from them, so there is
        one copy of the script. What the voice is given strips the markup (l.81 to 86): pointer
        marks [words](target) keep the words, {{c:id|words}} glossary
        hovers keep the words, **strong** and backticks lose their marks.
      
    
      
    say  : "The sync job now wraps its fetch in [retrying](L2)."
cue  : { "at": "beat:2", "say": "The sync job now wraps its fetch in retrying." }
    
      
    
        (L2) is the pointer: from the moment retrying is spoken, line 2 of that
        tour step is outlined, until the next mark or the end of the line. When it is spoken is
        known because verify's second pass compiled the voice's word timestamps into
        .tts/manifest.json. This is also why a render matters to timing: the short cut
        keeps the full film's beat numbers, so it reuses the full film's compiled clips and records
        nothing new.
      
    

      
    A tick that knows what it was ticked against
    
      
    
        On the review page every file has a "reviewed" box, in the order the tour reaches it. The
        problem a push poses is old: which of the files I already read have changed since? pr-viz
        stores, with each tick, a SHA-1 of the file's changed lines only: for each hunk, the
        sign and text of every added or removed line (pr-viz.ts l.870 to 877). Line
        numbers and context are not in it. A tick holds when that fingerprint is unchanged; when it
        differs, the tick is gone and the file comes back marked changed since you looked.
      
    
      
    
        This is the real rule, running in your browser with crypto.subtle. Tick some
        files, then push at them.

        Which way the rule errs. Anything that changes an added or removed line, or moves a

    Three small hacks around GitHub
    
      
      
        
    • 
          The hero is painted onto the video's first frame. GitHub's player drops a
          poster attribute but shows a video's first frame as its thumbnail, so
          stills.ts overlays the hero on frame 0 only with
          ffmpeg overlay=enable='eq(n,0)', copying audio, subtitles and chapters
          untouched (l.55 to 66). A re-render replaces the mp4, so run stills again after.
        
      • 
        
    • 
          The poster is shot in 4,000-pixel bands and stacked. A Chrome screenshot tops out
          at 16,384 device pixels and repeats the page past it, so at 2x the page is clipped in
          bands and joined with vstack. GitHub refuses images over 10 MB, so a poster
          that big is re-shot at 1.5x (l.75 to 90).
        
      • 
        
    • 
          Links go to the exact lines in Files changed. review-order.ts builds
          each block's anchor as #diff-<sha256 of the path>R<line>, which
          is GitHub's own scheme, and falls back to the compare view before the PR exists so a local
          draft links correctly. An added-only hunk is fenced in the file's language for syntax
          colour; anything with a removed line is fenced as diff, because red and green
          are the point.
