↓  WHY IT EXISTS

A picture explains a change quicker than a giant diff.

A PR body is text, and "Files changed" lists files by path. The idea behind the change, what it makes possible or prevents, is the one thing neither shows at a glance. pr-viz draws it: one picture of the idea, in a frame every PR shares.

It used to do far more. pr-viz was a narrated film: a tour of every changed line, a review page, a poster and a hero still, all from one plan.json. A full run for one small PR took a 12-minute agent session and 172 tool calls before anything rendered, and the user had not watched one of the films in a long time. The story it told was also being told a second time, because the page the user actually reviews code in, the hunk review, carried only a line per commit and per file.

So the skill kept its name and its original point, and gave the other jobs to the tool that serves each reader. What is left is small enough to run on every PR, which is the design: a hero nobody has to ask for.

Say "pr viz". Get a still and a GIF.

Triggers: hero for this PR, pr viz, picture of this change. It also fires without being asked: r2-pr step 5 makes the hunk review, the walkthrough and the hero on every PR, hand-opened or Kelpie's. Every hero shares one frame, and only the drawing changes:

Part What it is
the frame Fixed: the title top-left, one subtitle line under it, a repo#PR badge top-right, and a large drawing area below (1760×770 CSS px on a 1920×1080 stage). Never edited per PR.
hero.png The still: the page's last frame, with no controls, at 1920×1080.
hero.gif 4 s of the drawing building up, then a 2 s hold on the finished picture; it loops; 960 px wide, under 5 MB, no sound. Its last frame is the still.

It draws the idea. It cannot check the idea is true.

What verify can and cannot see. viz verify passes a drawing that lints, formats and renders without a console error. It cannot tell that the picture says something true, or that a reader can follow it. That is a person reading chapters.png and the full-size PNG, which is a habit, not code.
  • It makes only the picture. There is no narration, no review page and no plan.json any more. The code tour is hunk-review-viz's and the PR text is r2-pr's.
  • It stops at the hand-over. Putting the GIF on a PR is r2-pr's job, and uploading the media is github-attach-media's.
  • The drawing must be a pure function of t. The page is seeked, not played, so timers, CSS transitions and requestAnimationFrame do not render.
  • The GIF halves everything. It is 960 px wide, so no text under 14 px at 1920, and 22 px and up for any label a reader needs. One idea, not every detail.
  • The GIF has a ceiling. Over 5 MB it retries with fewer frames, then fewer colours, and fails naming the size: simplify the drawing, with fewer gradients and less motion.
  • It is local by default. The template ships viz:posture = local, unlisted: a hero of someone's PR is not for the open web unless you decide it is.
  • It costs a render on every PR. That was accepted, in the ADR, over making it only on request. The ADR says to revisit if the hero on every PR proves to be work nobody looks at, which is what ended the film.

What it leaves behind, and where

The skill skills/pr-viz/: SKILL.md; scripts/hero.ts; and template/ with index.html, frame.ts, ramp.ts, hero.json and drawing.ts, about 250 lines in all.
Declared kind: skill, state: true, requires.skills: [viz] and commands: [node, ffmpeg]. No integrates block and no deletion-policy.
Its state Real, but not in a folder of its own. A run leaves (1) a viz in the viz library, ~/.agents/state/viz/pr-<n>-<slug>/, holding hero.json and drawing.ts beside a .verify/ cache; and (2) the two files at --out, by default ~/Desktop/pr-<n>.hero.png and .hero.gif. r2-pr passes --out <state dir>/pr, so a PR's pair lands beside its draft.
Deleting it The manifest declares no deletion-policy, so this is a reading of the source: the PNG and GIF regenerate from hero.ts. hero.json and drawing.ts, which are the picture, do not.
Requires viz (the page's server and kit, verify, render, and the puppeteer and Chrome lookup hero.ts borrows), node and ffmpeg (the palette-optimised GIF).
Called from r2-pr, step 5, on every PR. Its sibling pr-shape no longer imports anything from here: its production-versus-test check is now classify.ts, which lives in hunk-review-viz.

    Small hacks around GitHub
    
      
      
        
    • 
          It is a GIF, not a video. A GIF plays without a click and an mp4 needs one. The GIF
          ends on the still, so the body shows the GIF alone: showing both would say the same thing
          twice.
        
      • 
        
    • 
          The GIF is shrunk by a ladder. hero.ts tries 20 fps with 256 colours,
          then 10 fps with 256, 128 and 64 colours, and stops at the first that is at most 5 MB
          (l.21 to 23). Only 10 and 20 fps are tried because they give whole-centisecond GIF frame
          delays. GitHub refuses images over 10 MB, so 5 MB leaves room.
        
      • 
        
    • 
          The still hides the controls first. Before the screenshot,
          hero.ts injects display: none for the frame's play and scrub
          bar, so the PNG is the drawing and nothing else (l.46).
        
      • 
        
    • 
          The title is the PR's title. code spans in it render mono. If the
          title changes after the hero was made, edit hero.json, run
          hero.ts again, and upload the new GIF.
