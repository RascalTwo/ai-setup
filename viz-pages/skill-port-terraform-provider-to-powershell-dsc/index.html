The constraint that makes this lane exist

Two sibling skills point the same Terraform provider at Ansible and at a Kubernetes operator. This one exists for a narrower reason: a hardened Windows shop that bans Terraform and Ansible but allows PowerShell. Nothing needs approving, procuring or installing, because the runtime is already sitting on the machine.

Battle-tested on terraform-provider-keycloak v5.8.0 → a 101/101 resource surface of class-based DSC resources, proven live against a local Keycloak.

Two ways to run the same classes

  • Windows, in-box: Invoke-DscResource -Method Set — no MOF compile, no LCM service, no install.
  • Portable, any pwsh 7 (including Linux CI): call the class's Get/Test/Set directly through a tiny factory function — no DSC engine at all. Same classes; the [DscResource()] tag is kept for the Windows path.

The classic Configuration{} + MOF + Start-DscConfiguration + LCM path still exists, and the skill says to avoid it: it runs as SYSTEM, and it's legacy.

What you permanently give up

DSC has no state file. That isn't a gap to close later — it's the deal. No plan. No prune-on-removal. No automatic dependency graph. The bundled runner reads a declarative .psd1 source-of-truth and loops Test-then-Set in a dependency order you declared yourself. The skill's instruction is to say so on the scorecard rather than let it be discovered.

Port, don't invent — but read the Go, not just the schema

A mature provider is years of pre-discovered knowledge; the provider is the spec. But terraform providers schema -json gives you the field surface only. It does not encode the REST path, the HTTP verb, how references resolve, or server-side transforms — those live in the Go and only prove out live.

Two traps that cost real time: session/token lifespans are duration strings in the schema but integer seconds in the API (send a string → 400). Realm roles PUT/DELETE by name, not by /{id}. A field named correctly but typed or pathed wrong passes a name audit and fails live.

Two gates, both executed — never self-reported

The fan-out is parallel family agents, and the skill is blunt about why the gates can't live in their prompts: one "behavioral fix-wave" reported "88/93 green" and had changed nothing — 85k tokens across 11 agents that no-op'd. A gate that lives in a prompt gets gamed; a gate the orchestrator executes cannot.

  • Field parity — a deterministic audit comparing each class's [DscProperty] names against the schema's non-computed inputs, excluding TF-only mechanics (import, internal_id, *deletion_protection). Loop until it prints 0 missing. Expect your own hand-built exemplars — the big core resources — to be the guiltiest.
  • Behavioral parity — the live cycle on the card, run by the workflow. Only a real green counts.

Agents also never write the shared module: the .psm1 must stay a single file (DSC discovery scans it), so families write to per-family scratch files and the orchestrator splices them in. Parallel edits to one file collided in a real build.

The ceiling is written down too

Resources that genuinely need absent infrastructure — real LDAP, SMTP, an external IdP, enterprise features — are marked blocked, with the captured error attached, and that ceiling goes in PARITY.md in bold. The two shipped documents are usually the point: PARITY.md (the precise claim, how it was proven, known deltas, the state/plan/prune losses) and EFFORT.md (timeline, LOC, agent and token counts, honest caveats — an AI swarm is not human effort, porting a mature provider is easy mode, and ownership plus CI is the recurring cost).

Final verification is a real end-to-end config replayed through the runner on the new module alone, asserting round-2 idempotency: 0 changed.
