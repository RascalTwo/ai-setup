The screenshot that looks hosted and isn't

You want a screenshot, or a short screen recording, at the top of a PR. Every path that looks like it should work fails, and most fail silently: the Markdown is valid, the PR saves, and you only find out when a reviewer sees a broken image icon. A private repo makes it worse, because the one URL you can construct yourself is exactly the one GitHub's image proxy cannot fetch.

Every door but one is shut

  • There is no attachment API. The only way to get a renderable, access-controlled image URL is GitHub's own uploader, which is a browser drag-drop onto a classic Markdown editor. gh can't do it.
  • raw.githubusercontent.com from a private repo does not render. GitHub serves images through camo, and camo can't authenticate. Dead end.
  • The file_upload MCP tool currently rejects host paths. The skill marks it regressed and tells you not to rely on it.
  • A synthetic cmd+v paste of an image on the clipboard is unreliable: the key event never delivers image bytes to GitHub's paste handler.

So the skill stops trying to host the image and makes GitHub's real uploader run. What it returns is a https://github.com/user-attachments/assets/<uuid> URL you can put in any PR, issue, comment or Projects card body.

Say "put this screenshot in the PR"

The skill's description says when it fires: you have an image, screenshot or video and a PR or issue body, comment or Projects card needs a hosted copy. Six steps, clipboard to URL to body: 

# 1. file onto the clipboard as base64 TEXT (macOS; note the -i)
base64 -i /path/to/image.png | tr -d '\n' | pbcopy

# 2. open a CLASSIC editor in Chrome and prove it is one: both must be true
#    https://github.com/<owner>/<repo>/wiki/_new
({ hasFileAttachment: !!document.querySelector('file-attachment'),
   hasBody: !!document.querySelector('#gollum-editor-body') })

# 3. click into the editor body (the computer tool) so the tab has OS focus
# 4. hand scripts/drop-and-harvest.js whole to javascript_tool
#    → { url, imgTag, bytes }

# 5. spend the URL
gh pr edit <N> --body-file body.md   # <img width="1200" src="$URL" />

# 6. clear the body, null onbeforeunload, navigate away. Never save.

A video is the same run with one line set first in the page: window.__upload = { name: "pr-1187.mp4", type: "video/mp4" }. mp4, mov and webm upload the same way. Linux swaps step 1 for base64 -w0 image.png | xclip -selection clipboard; everything after it is identical, because the mechanism is the browser's.

What it won't do, and what it leans on

  • It won't work without Chrome. The mechanism is a real browser driving a real uploader; chrome is a declared requirement and there is no fallback.
  • One file per run. For several, repeat steps 1, 3 and 4 per file. The snippet empties the editor before each drop, so the one URL it then finds is always that upload's; a second drop into a full editor can land above the first URL, not after it.
  • It needs a classic editor. The <file-attachment> element exists only on GitHub's classic Markdown editors, not the React /issues/new one. The reliable instance is a wiki new-page, so some repo with its wiki enabled has to exist. Disabled wikis redirect /wiki/_new to the repo home.
  • It leans on page internals. file-attachment and #gollum-editor-body are GitHub's markup, not an interface. If they move, the snippet returns an error naming the missing element instead of dropping into a page with no uploader on it.
  • It can't un-upload. The asset is permanent and independent of the wiki page, and the skill documents no way to remove one. Treat an upload as one-way.
  • The URL is not public. A user-attachments asset is visible only to people who can see the repo it was uploaded through.
Scope is the gotcha: upload through the same repo as the PR, or one your audience can also see. Then open the PR and actually look at it. A broken image means wrong repo scope or a bad URL, and that eyeball check is part of the skill.

Where it lives

The snippet skills/github-attach-media/scripts/drop-and-harvest.js, 47 lines and the only code in the skill. It is not a module you run; it is text you hand to Chrome MCP's javascript_tool whole.
Integrates GitHub, through the user-attachments upload behind the wiki editor (an undocumented path, used because it is the only one), and Chrome, for the drag-drop automation through Chrome MCP.
Requires gh, to spend the URL on a PR, issue, comment or Projects card, and chrome with Chrome MCP connected.
Which repo's wiki Load-bearing, not incidental. Prefer the same repo as the PR, so the asset's visibility matches the audience's. If its /wiki/_new redirects to the repo home, use another repo your audience can also see, for example another repo in the same org.
Its state None. The manifest says state: false, so there is no deletion policy either: no upload log, no URL cache, no record of what went where, nothing under ~/.agents/.
What persists The asset on GitHub's CDN, which is GitHub's, permanent, and independent of the wiki page. And the base64 text left on your clipboard until you copy something else.
What does not The wiki page. It is never saved: step 6 clears the body, drops the unsaved-changes guard and navigates away. Nothing is written to the repo.
Safe to delete Locally there is nothing to delete. The CDN asset is out of this skill's hands, so treat the upload as one-way.

The turn: run GitHub's own uploader

One file, from the shell to a URL in a PR body. The bytes travel through the OS clipboard as text, so a 400 KB screenshot never passes through the agent's context, and the page reconstructs the file and hands it to the uploader as if a person had dragged it in.

← → arrow keys

The bytes travel as text, on purpose

base64 -i image.png | tr -d '\n' | pbcopy puts the file on the OS clipboard as one line of text. The obvious consequence is that the bytes never enter the agent's context. The less obvious one is that text is what navigator.clipboard.readText() returns to a page, which is why the skill routes around the synthetic-paste dead end instead of fixing it. Step 3, clicking into the editor body with the computer tool, is not decoration: it gives the tab the OS focus that the clipboard read needs.

The classic editor is the whole constraint

GitHub's uploader is bound to a <file-attachment> custom element, and that element only exists on the classic Markdown editors. The precondition is checked rather than assumed, and both halves must be true: 

({ hasFileAttachment: !!document.querySelector('file-attachment'),
   hasBody: !!document.querySelector('#gollum-editor-body') })

The snippet repeats the same test itself (drop-and-harvest.js lines 17 to 21) and refuses with "no <file-attachment>/#gollum-editor-body — not a classic editor (use the wiki _new page, NOT /issues/new)".

Reconstructing a File nobody dragged

Lines 23 to 35 are the trick. Empty the editor, read the clipboard, and refuse anything that isn't /^[A-Za-z0-9+/=]+$/ (a stale clipboard stops here with "clipboard is not base64 text — re-run the pbcopy step"). Then decode atob(b64) into a Uint8Array, build a DataTransfer, add new File([u8], name, { type }) with image.png and image/png as defaults, and dispatch dragenter, dragover and drop at the <file-attachment>, each a real DragEvent with bubbles, cancelable and that dataTransfer. That is the sequence a human drag produces, so GitHub's own uploader takes it from there.

Harvesting, because the upload is asynchronous

The drop returns at once; the URL does not. The snippet polls the editor body for /https:\/\/github\.com\/user-attachments\/assets\/[0-9a-f-]+/, 180 attempts 500 ms apart (lines 38 to 44), because a video takes longer than an image. A match returns { url, imgTag, bytes }; bytes should equal the file's size. A timeout returns { error, body } with the current body included, so you can see what GitHub actually inserted instead of guessing.

Pass the snippet as-is. Do not wrap it in an async IIFE. javascript_tool returns the last expression's value and supports top-level await, but it does not await a Promise you hand back, so (async () => {…})() serializes to {}. The file's last line is the bare out for exactly this reason. If you do get {}, the drop still ran: read the URL back out of the body with document.querySelector('#gollum-editor-body').value.match(/user-attachments\/assets\/[0-9a-f-]+/)?.[0].

Spend it, then walk away without saving

The URL is plain text in a plain Markdown body, so gh takes it from there: gh pr edit, gh issue edit, or gh project item-edit --id <DI_…> --body. Build the whole body in a file and pass --body-file to avoid escaping pain. <img width="1200" height="630" src="…"> pins a stable render size for a 1200×630 card; ![alt](url) is fine otherwise.

Cleanup has an ordering requirement: clear the body, fire a bubbling input event so the editor notices, null window.onbeforeunload, then navigate. Navigate first and Chrome throws a "Leave site?" dialog. 

const b = document.querySelector('#gollum-editor-body');
b.value = ''; b.dispatchEvent(new Event('input', {bubbles:true}));
window.onbeforeunload = null; true;

Verify by hash, not by spinner

bytes in the result equals the local file size. For proof GitHub serves exactly your file, fetch its signed URL without a browser and hash it: 

U=$(gh api markdown -f mode=gfm -f context=<owner/repo> -f text='![x](<url>)' \
    | grep -o 'https://private-user-images[^"]*' | head -1 | sed 's/&/\&/g')
curl -s "$U" | shasum -a256   # compare with shasum -a256 on the local file

Then open the PR and look. A video should show a player, but Chrome loads no video in a background tab and a fresh upload can take a minute to serve, so a spinner is not a failed upload. The hash settles it.
