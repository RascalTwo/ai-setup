Counting blockers lies to you

A backlog column sorted by "how many things block this" looks reasonable and ranks the wrong work first. An issue blocked by three independent root-level items is one layer from being pickable. An issue blocked by one thing that is itself blocked by five things is further away than that — but the count scores it as the safer bet. The count says the first item is worse; the shape of the graph says it's nearly ready.

So this skill ranks by depth instead: the longest path from any root node — an issue with zero blockers — to this issue, following blocking relationships. A root is depth 0. An issue blocked only by roots is depth 1. And so on. It captures transitive distance, which is the thing you actually care about when you're deciding what to start on Monday.

Within a depth, items are sorted alphabetically by title. That's the whole ordering rule: (depth ascending, title alphabetical). The payoff is a "pick up from the top" column — the top is always the most actionable work, and deeply blocked items sink to the bottom.

What you have to tell it

  • --org and --project are required — the owner, and the project number from the URL. It prompts if you leave either out.
  • --repo is required too, as owner/name: it is the repository the blocking relationships are read from. The skill's job is to work it out for you — if every issue on the board comes from one repo it takes that one, and if the board is mixed it asks rather than guessing.
  • --column defaults to "Parking Lot".
  • --dry-run computes and prints the proposed order with depth numbers and writes nothing. Worth doing first on a board you care about.
python3 SKILL_DIR/scripts/reorder.py \
  --org <org> --project <number> \
  --column "Parking Lot" --repo "<owner/repo>" [--dry-run]

The skill carries disable-model-invocation: true, so it does not fire on its own — it runs when you ask for it by name or by description ("sort the board by dependency depth", "put the most blocked items at the bottom").

Where it stops

  • One column, in place. It reorders within a single column and does not move items between columns. It is a sorter, not a triager.
  • Blocking and blocked-by only. Sub-issue and tracked-by relationships are ignored — a parent/child hierarchy will not show up as depth.
  • One repo's relationships. --repo is singular, and a blocker that isn't an issue on this board is dropped from the graph entirely rather than deepening anything. Cross-repo boards get an answer that is right about the part of the graph it can see.
  • Draft issues are skipped. They have no number, so they have no dependencies and no place in the ordering.
  • A dependency cycle doesn't crash it, but it doesn't resolve it either — the loop is broken by treating a revisited node as depth 0, which is a decision to keep going, not a correct answer about a graph that has no correct answer.
  • It needs gh, authenticated with the project scope.
  • It runs at roughly 3 API calls a second on purpose, to stay inside GitHub's rate limits. A large column takes as long as it takes.

What actually happens

One board column, from --org to a reordered column — every API call it makes, in order.

Resolving the board, and paging it

get_project_node_id() turns organization(login:) { projectV2(number:) { id } } into the opaque node ID every later call needs, and prints the project title so you can see you hit the right board. fetch_project_items() then pages items(first: 100, after:) until pageInfo.hasNextPage goes false, pulling four things per node: the project item ID (which is what gets moved, and is not the issue's ID), the issue number and title from the ... on Issue fragment, and the column name out of fieldValueByName(name: "Status"). A node whose content has no number is a draft issue and is skipped.

Blockers are fetched for the whole board, not the column

This is the non-obvious part of the run and it is a correctness requirement: fetch_blockers_for_all() is handed every issue number on the board, not just the ones in the target column, because an item's blocker frequently sits in another column. Filter first and the depths come out shallow and wrong.

The fetch uses GraphQL's blockedBy field directly, aliased ten issues to a query to stay under the complexity limit:

repository(owner: "…", name: "…") {
  issue_41: issue(number: 41) { number blockedBy(first: 50) { nodes { number } } }
  issue_42: issue(number: 42) { number blockedBy(first: 50) { nodes { number } } }
  …                                        # 10 per query, then sleep(0.5)
}
The SKILL.md's step list is out of date here. It describes a two-call REST route — issue_dependencies_summary for blocker counts, then the issue timeline for the actual numbers. reorder.py does neither: it reads blockedBy in one batched GraphQL query. Same answer, one round trip instead of two, and the aliased-batch shape is why the progress output counts in tens.

Blockers are filtered to b["number"] in issue_numbers on the way in — a blocker that isn't on this board contributes nothing rather than becoming a phantom node.

Longest path, memoized, with the cycle handled

compute_depths() is a depth-first search with two sets doing the work. cache memoizes, so each issue's depth is computed once no matter how many paths reach it. in_progress catches cycles: a node revisited while still on the stack returns 0, which breaks the loop rather than recursing until Python's stack limit. The recurrence itself is one line — 1 + max(max_depth(d) for d in deps), with deps intersected against the board's own numbers, and no dependencies meaning depth 0.

Longest path, not shortest, and that is the whole thesis of the skill: an item is only as ready as its deepest chain, so taking the max is what makes "blocked by one thing that's blocked by five" outrank "blocked by three roots".

Applying it: afterId chaining, one item at a time

There is no bulk reorder mutation, so the order is laid down as a chain. The first item's updateProjectV2ItemPosition is sent with projectId and itemId and no afterId, which means "move to the top". Every subsequent call passes afterId: <the previous item's ID>, so each lands directly behind the one before it and the chain builds the column top-down. time.sleep(0.2) between mutations is the rate limiting.

mutation {
  updateProjectV2ItemPosition(input: {
    projectId: "PVT_…", itemId: "PVTI_…",
    afterId: "PVTI_…"          # omitted on the first item → goes to the top
  }) { clientMutationId }
}

Then it prints the final order as Depth NN | #123 | Title, one line per item, which is both the receipt and the explanation — you can see exactly why each item sits where it does. --dry-run prints the same table and stops before the first mutation.
