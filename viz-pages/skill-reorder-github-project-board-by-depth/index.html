Counting blockers lies to you

A backlog column sorted by "how many things block this" looks reasonable and ranks the wrong work first. An issue blocked by three independent root-level items is one layer from being pickable. An issue blocked by one thing that is itself blocked by five things is further away than that — but the count scores it as the safer bet. The count says the first item is worse; the shape of the graph says it's nearly ready.

So this skill ranks by depth instead: the longest path from any root node — an issue with zero blockers — to this issue, following blocking relationships. A root is depth 0. An issue blocked only by roots is depth 1. And so on. It captures transitive distance, which is the thing you actually care about when you're deciding what to start on Monday.

Within a depth, items are sorted alphabetically by title. That's the whole ordering rule: (depth ascending, title alphabetical). The payoff is a "pick up from the top" column — the top is always the most actionable work, and deeply blocked items sink to the bottom.

What you have to tell it

  • org and project are required — the owner, and the project number from the URL. It prompts if you leave either out.
  • column defaults to "Parking Lot". view defaults to 1 and is rarely needed.
  • repo auto-detects: if every issue in the column comes from one repo, it takes that one from the first issue. If the column is mixed, it stops and asks rather than guessing.

What actually happens

The skill doesn't hand-roll the graph in conversation — it shells out to scripts/reorder.py, which does the whole run and prints a summary table of the final order with the depth numbers attached. The steps, for transparency:

1  gh api graphql   → the project's node ID
2  fetch every project item: status, issue #, title, item ID
3  keep only the items in the target column
4  REST issue_dependencies_summary → blocker COUNTS
5  for anything with blockers → the issue timeline gives the
   actual blocking issue numbers
6  build the graph, compute longest-path depth (memoized DFS)
7  sort by (depth ↑, title A→Z)
8  apply it: updateProjectV2ItemPosition mutations,
   afterId-chained so each item lands behind the last
9  report the final order

Steps 4 and 5 are deliberately two calls: the summary endpoint gives how many blockers an issue has, and only the issues that have any get their timeline walked for the actual blocking issue numbers.

If it hits an auth error, the fix is one line and the skill will tell you to run it: gh auth refresh -s project.

Where it stops

  • One column, in place. It reorders within a single column and does not move items between columns. It is a sorter, not a triager.
  • Blocking and blocked-by only. Sub-issue and tracked-by relationships are ignored — a parent/child hierarchy will not show up as depth.
  • It needs gh, authenticated with the project scope.
  • It runs at roughly 3 API calls a second on purpose, to stay inside GitHub's rate limits. A large column takes as long as it takes.
