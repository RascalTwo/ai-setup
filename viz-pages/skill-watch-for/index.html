↓  WHY IT EXISTS

Looking, again and again, to see if it's done

Before this, waiting on a screen meant a loop: take a screenshot, Read it, decide it isn't ready, sleep, repeat. Every glance parks ~1–2k vision tokens in context, and they accumulate. A ten-minute deploy watched every 20 seconds is thirty images spent on "not yet".

watch-for moves the looking out of Claude. A small local model on Ollama judges each frame; Claude runs the watcher in the background and is told when it exits.

When the skill fires

When Claude would otherwise screenshot repeatedly to wait on a UI (a dialog, a banner, a page finished loading, a spinner gone), or has to find the moments a recording shows something. The skill tells Claude to:

  • phrase each condition as something visible, and wait for success or failure in one expression so a failure ends the wait early;
  • narrow the source (--in window:<App>, a region) because a smaller frame is faster and more legible;
  • run it with Bash run_in_background: true and a sized --timeout, then read the exit code and JSON line when notified;
  • Read the saved frame once before any irreversible action.

What it won't do

  • Small text is weakest. d1 is a 2B model. A small target can take a few frames to trigger; a region makes it bigger and faster.
  • It answers "is X visible", never "what does it say". Reading values is read-image-locally.
  • Ollama serializes requests. Another loaded model, yours or another session's, stalls every check; a check stuck behind it ends as exit 2 after 300 s.
  • macOS only for screen and window sources (screencapture and osascript). Videos, folders and stdin paths do not care.
  • At most 1 frame per second. Something on screen for less than a second can be missed.
Waiting, not proof. d1 is ~93% right per frame and confirms over 2 frames. Before an irreversible action, Read the saved frame once yourself.

How it actually works

One watch-for invocation, from the expression to an exit code.

← → arrow keys

The expression is parsed, not evaluated

ast.parse(expr, mode="eval") reads the condition, and a walker allows only strings, and/or/not, "x" in <region>, box() and px(). Anything else is refused with exit 2 before a single frame is captured. Regions are fractions of the frame (box(x,y,w,h)) or exact pixels (px(x,y,w,h)).

Getting frames

# live screen: one capture per loop, three rotating temp files
screencapture -x -t png [-D N] frame.png
# window:<App>: bounds from System Events, then a rectangle capture
osascript -e 'tell application "System Events" to tell (first process whose name is "App") to get {position, size} of front window'
screencapture -x -t png -R x,y,w,h frame.png
# video file, stream URL or camera: decoded once, one frame per second
ffmpeg -nostdin -i SOURCE -vf fps=1 %08d.png

A live source takes the next frame as soon as the last answer is in, but never more often than once per second. For a live stream ffmpeg skips to the newest frame; a file is judged frame by frame.

One call per region, conditions batched

judge() groups conditions by region and makes one d1 call per distinct region, putting every condition for that region in the same request to /v1/systemone as separate questions. Measured on 40 screenshots, 4 questions per call gave 98.8–100% the same verdicts as asking them singly and was ~3.5× faster.

Frames go at native resolution: 1536 px was ~native accuracy (768 px scored 90.0%, 1536 px 93.8%), and a real 3456×2234 screen costs 2.4–3.0 s per call.

Skipping work, then deciding

Each frame is reduced to grayscale at 512 px and compared with the last judged frame. If no pixel moved by more than 24/255, the previous verdict is repeated without asking the model. Each probability is turned into true at p ≥ 0.5, the boolean tree is evaluated, and a match needs 2 consecutive true frames. --gone inverts the result to wait for something to disappear.

Time, output and exit codes

Each d1 call is handed only the time remaining of --timeout, so the deadline holds even while Ollama is busy. On a match it copies the frame to the tool's own folder in ~/.agents/state/ and prints one JSON line: 

{"matched": true, "t": 312.0, "frame": "(saved frame, path in the JSON line)", "p": {"Saved @ frac[0.5, 0.5, 0.5, 0.5]": 0.91}}

Exit 0 on a match, 1 on timeout or end of stream (it prints {"matched": false, …} with the last probabilities), 2 on any error.
