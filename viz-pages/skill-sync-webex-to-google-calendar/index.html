Your work day is on the calendar you aren't looking at

Work meetings arrive through Outlook and show up in the Webex desktop app's calendar, the Zoom and Google Meet ones included. The calendar you actually plan your day in is Google. Two calendars means that a free slot on one is a meeting on the other, and the only thing reconciling them is you, squinting.

People paper over it by copying events across by hand, which is how the same meeting ends up on both sides under slightly different titles. The skill's config even has an excludeTitles list for events the user copied into Webex from Google, so that a hand-made copy in one direction does not bounce back as a duplicate in the other.

Say it, then keep your hands off the keyboard

Triggers: sync Webex to Google Calendar, mirror my Webex meetings, update my work calendar. The extract takes about 70 to 100 seconds and it takes Webex's focus, so the agent tells you to leave the mouse and keyboard alone. When it finishes it brings back whatever app you were in.

It then shows one table: action, title, start, reason. Nothing is written until you approve it. Say "dry run", or just do not approve, and the table is the end of it. Everything is optional config in ~/.config/sync-webex-to-google-calendar/config.json:

excludeTitles Exact titles never mirrored. Default: none.
timeZone IANA zone for reads and writes. Default: the system zone.
titlePrefix Prefix on every mirror's title. Default: [Webex].
colorId Google event colour for mirrors. Default: "6".
days Window length. Default 30, because Webex's list reaches about a month ahead.

One direction, one window, one kind of event it may delete

  • Read-only on Webex. It clicks an event row and reads the side panel. No window is opened, nothing is created, nothing is accepted or declined.
  • It touches only what it wrote. On Google, an update or a delete requires the event's description to start with MIRRORED-FROM-WEBEX. Your own events are never modified.
  • It reads a fixed set of fields. Title, times, organizer, rooms, invitee count, link, description. The panel's password, host key, meeting number and dial-in blocks are never selected, and pwd= values inside links are replaced with pwd=REDACTED before the extract is even written.
  • The Webex description does not go to Google. It can hold passwords. A mirror carries the organizer and rooms, and the join link as its location.
  • It emails nobody. No attendees on a mirror, and every write carries notificationLevel: NONE.
  • It will not act on a partial read. Unless the extract has zero errors and at least one event, it stops with no Google writes, because a partial read would delete live mirrors.
  • Absence past the edge of the list is not a cancellation. A mirror dated on or after the list's last day stays, since the list may simply end there.
  • Banner rows are skipped. All-day entries are not meetings.
  • macOS only, and it needs Accessibility. The terminal must be trusted for the accessibility API, Webex must be running, and it is not a two-way sync. Ambiguous matches are marked ? in the plan for you to decide.

What it plugs into, and what it leaves lying around

The skill skills/sync-webex-to-google-calendar/SKILL.md is the judgement half. The deterministic half is scripts/run.sh and scripts/wx.swift.
Declared kind: skill, state: false, integrates webex and google-calendar, requires: [webex, swiftc, google-calendar-mcp].
Integrates Webex, read through the macOS accessibility API, and Google Calendar, written through its MCP server.
Requires The Webex desktop app, swiftc (it compiles wx.swift on first run), and the Google Calendar MCP. Plus a macOS Accessibility grant for the terminal, which lives in System Settings, not in this repo.
Its state Nothing worth keeping. It leaves scratch under ~/.local/share/webex-calendar/: the compiled wx binary and out/week.json, week.ndjson, progress.log. The directory is mode 700 because the extract holds your meeting titles in plain text. The mirrors themselves live on Google, each carrying its own identity in its description.
Safe to delete? Yes, all of it. The binary recompiles from wx.swift and the extract is rebuilt on every run. Deleting a mirror on Google just makes the next run create it again.

It reads Webex the way a screen reader does

The skill takes the route that needs nothing from Webex, no export and no API: it does what assistive software does, asks macOS for the app's accessibility tree and reads the text of the controls. wx.swift drives the Webex window into its calendar List view, clicks each event row, and reads the side panel that opens. A shell wrapper brings Webex to the front and, no matter how the run ends, puts your previous app back. Then the judgement half takes over: gate the extract, read Google, classify, show a plan, and write on approval.

Deletion is the dangerous verb, so every guard is about absence

Creating a wrong event is a nuisance. Deleting a right one is a loss. So most of the classifier's care goes into one question: when may the absence of a Webex event be read as "it was cancelled"? The mirror carries its own key. The first line of a mirror's description is MIRRORED-FROM-WEBEX | <link> | <start ISO>. That one line is both the ownership tag (the only events it may update or delete) and the identity Webex never gave it (link plus start). There is no database of "what I mirrored", so there is nothing to drift out of step with Google. The calendar is the record.

Two honest ceilings. The accessibility tree is Webex's UI, not a contract, so a Webex update that renames a button can break the baseline step; it fails loudly with exit code 2 or 3 and an ERROR line rather than guessing. And every row costs a scroll, a click and a wait for the panel to show the right meeting, with fixed sleeps in between, which is why a month takes a minute or two.
