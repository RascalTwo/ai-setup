pr-split doesn't count lines. It finds the seams where a branch holds more than one idea, proposes a finest and a balanced cut, and on a yes makes one local branch per piece, but only if the pieces sum back to the original exactly.

No size threshold. "One PR is right" is a full answer.

↓  WHY IT EXISTS

One branch, four ideas, one review

You start a retry fix. By Thursday the branch also renames a helper you tripped over, bumps a dependency (and its lockfile), points a second job at the new retry, and corrects a sentence in the docs. Git has no objection. The pull request you open is "one change" only because one branch produced it.

The reviewer gets one list of files. Nothing in it says which lines are the idea and which are furniture, so they read the top carefully, skim the middle, and trust the rest. A reviewer takes in one idea at a time, and the branch handed them four.

Splitting it afterwards by hand is worse than it sounds. git add -p and a few cherry-picks leave you with branches that nothing ever checks against the one you wrote: a hunk can end up in two pieces, in none, or in a piece that cannot build without another. You find out on piece three's CI, or you don't.

pr-split bets that the unit is the idea, not the line count. A 900-line rename is one idea; a 60-line PR that also reformats a file is two. "One PR is right" is a full answer, given in one line. Where it does find a seam, the cut it proposes is checked by a script: the pieces, applied in order, must rebuild the original branch's tree exactly, or no branch is made.

The seams come from people who have thought about this: Google's small-CL guidance (refactorings in their own change), Palantir's review practices (interfaces first, implementations second), Beck's Tidy First? (a rename is its own atom). Where the evidence runs out the skill says so: it backs "smaller and focused", not "as many PRs as possible", and whether stacked PRs beat separate ones is contested. So the default is the finest cut, you merge pieces back together, and pieces stack only where one needs another.

Say it, or let r2-pr say it every time

Typed triggers: split this PR, is this too big, break this branch up. The path that actually fires most is the other one: r2-pr step 3 runs pr-split on every branch before it opens a PR, "whatever its size", once the readiness checks have passed. "One PR is right" and r2-pr carries on. Pieces, and that r2-pr run ends there; each piece's branch then goes through r2-pr from step 1, readiness check included.

What you see is a conversation, then a command. It reads every hunk and the diff itself, names the atoms, and shows two cuts as tables (piece, one-line purpose, files, lines, what it stacks on, any shared file and where it put it) and asks which, and which pieces to merge further. Here is that table for a real run, a nine-hunk branch I built in a scratch repo to check my own reading of the script:

Piece (finest) Purpose Files Lines Stacks on
tidy Rename timeoutMs 1 +1 −1 merge-base
core Retry with jittered backoff: the loop, the delay function, its test, the new dependency, and bun.lock (shared file: goes with the manifest change that moved it) 5 +29 −2 merge-base
sync The sync job adopts the retry 1 +2 −2 core
docs One sentence about it 1 +2 core

Balanced would be two PRs: tidy, and retry (core, sync and docs, 7 files, +33 −4), because sync and docs are footnotes a reviewer reads alongside core anyway. The decision is yours; pr-split does not pick for you, it only refuses to cut until you have.

It can prove the pieces add up. It cannot prove any piece works.

I ran this. On the same branch I left "after" off the sync piece, so it would be built straight on the merge-base. The script printed ✓ the 4 pieces sum back to retry-backoff exactly and made all four branches. That piece calls retrying(), which exists only in core: on its own branch it does not compile. Sum-back found nothing wrong because nothing was lost. This is the gap SKILL.md step 5 exists for: run each piece's tests and linters in a worktree of its own, and if one fails, delete the branches and cut again.
  • It cannot cut inside a hunk. Pieces claim whole files or whole hunks by id, and hunks are whatever git diff -U3 hands over, so two edits a few lines apart are one hunk. Put an added import two lines from an unrelated rename and git gives you one hunk holding both; there is no half to give each piece. The skill reads that as a finding ("a hunk that touches two atoms' code is a sign they are one atom"), not a bug to work around.
  • It does not decide what an atom is. That is judgement, and judgement is the model's (steps 1 to 3). The script keeps the books. A cut can pass every check and still be a bad cut.
  • It has no size threshold and no quota. A 900-line rename stays one PR. It will not tell you how many pieces is "enough", and it does not claim stacked PRs beat separate ones; stacking is used only where one piece needs another.
  • It does not push, open a PR, or touch your checkout. The original branch and your working tree stay exactly where they were. What you get is local branches; opening them is r2-pr's job, one at a time.
  • It does not carry your commit history. Each piece is one commit titled with the piece's title (l.122). The original commits live on, on the original branch.
  • It diffs from the merge-base (l.51, l.60). Whatever the base branch did after you branched is not part of the picture, and not part of any piece.

Where it lives

The skill skills/pr-split/SKILL.md (six steps, each with a "done when") and scripts/split.ts, 140 lines, two subcommands: hunks and cut.
Declared kind: skill, state: false, requires.skills: [pr-viz] (its classifier is imported from there) and commands: [git, bun]. No integrates block and no deletion-policy.
Its state None. It keeps nothing between runs. cut.json lives wherever you write it; the only things a run creates are the piece branches (yours) and throwaway worktrees in the OS temp dir, which it removes itself, even on failure. Deleting the skill leaves nothing behind but those branches, and git branch -D deletes them.
Requires git (worktrees, apply, rev-parse) and bun (it runs the TypeScript). One more that the manifest does not declare: split.ts line 21 imports kindOf from ../../pr-viz/scripts/classify.ts, to label each file prod, test, lock, binary or docs. The script only works with pr-viz's folder beside it.
Called from r2-pr, step 3, on every branch before a PR is opened, and by hand ("split this PR"). Each piece it makes then re-enters r2-pr at step 1. Its sibling pr-viz explains the PR that survives the cut.

Atoms first, branches second

There are two halves and they never swap jobs. SKILL.md's steps 1 to 3, 5 and 6 are the model's judgement; steps 1 and 4 call split.ts, which makes no judgement at all. The judgement is a set of seams, each one borrowed from a source the skill links:

  • A separate mechanism or module. Two modules that each gain a feature are two atoms.
  • Interface apart from implementation. The API as interfaces and docs first, the implementations second.
  • Refactor apart from behaviour. A rename, a move or a reformat is an atom; the behaviour that builds on it stacks on top.
  • Tests travel with the code they test, inside that code's atom.
  • A shared file belongs to no atom. A lockfile, a shared config, a generated file goes with the first atom that needs it, and every later atom that needs it stacks on that one.

On the demo branch that gives the four pieces in the table above. The rename (client.ts#2) is its own atom and stacks on nothing. The retry loop, the delay function, the test and the dependency are one mechanism, so the lockfile rides with the manifest change inside it. The sync job is a second module adopting the first, so it stacks.

An atom is "the smallest set of hunks that stands alone: it builds, its tests pass, and its PR description would be one sentence". Step 2 is done when every hunk is in exactly one atom and every dependency between atoms has a name. That sentence is what the script is built to check the first half of.
