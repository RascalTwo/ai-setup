A role, not a process

You are the CEO. The manager exists so you can ask one session what ten are doing instead of walking to ten panes — but nothing it does may assume it is the only one talking to a session. You can and will walk to a pane whenever you want.

The failure this is built against is not "I don't know what my sessions are doing". It is polling: a manager that looks only when spoken to cannot tell you a session finished, because by the time it looks you have already walked to the pane and found out. Every invocation therefore arms a watch, unasked.

Any session, five steps, every time

There is no daemon to start. Say "which sessions need me" — or "fleet", "manage my sessions", "who is blocked" — in any session, and that session becomes the manager. It keeps no memory of what sessions are doing; every invocation it looks:

  1. Run ~/.claude/skills/fleet/fleet — JSON, one object per pane.
  2. Read ~/.agents/state/fleet/ledger.md.
  3. Reconcile. An In progress row whose session has vanished from the snapshot gets surfaced, not resolved — a pane can die without the work being finished, so it asks you.
  4. Report: counts first, then one entry per pane that is not plain idle.
  5. Arm the watch, every time, unasked.
# Monitor, persistent: true
while true; do sleep 5; ~/.claude/skills/fleet/watch-tick; done

That is the whole arm command, and step 5 is not optional — a quiet fleet is only news if something is actually looking.

Not a task manager, and the watch dies with the session

  • The watch lives in the session that armed it. Clear or close that session and the watch disarms silently — the fleet looks calm precisely because nobody is looking. This is accepted, not engineered around: the recovery is to run /fleet again, which re-arms at step 5. So it never reports a quiet fleet as quiet unless a watch is actually running.
  • It is deliberately not a task manager. Backlog and parking-lot columns were considered and cut. Two sections, In progress and Done, and if you want more that is a separate tool and a separate conversation.
  • It never promotes a task. herdr's done ("a turn finished") and the ledger's Done ("the work is finished") are different claims. Only you move a row between them.
  • It never renames a tab on its own initiative, never writes to a focused pane, and never targets itself.
  • It never pastes a session's output back wholesale. You asked so you would not have to read the pane. One sentence, one action, and you choose whether to go read it.

Cracking it open

One session finishing, from the hook firing to you hearing about it. Nothing in this path screen-scrapes a terminal to find out what a Claude session is doing — the session says so itself.

One file per session per event, and therefore no lock

hooks/session-state.sh writes ~/.agents/state/fleet/state/<session_id>.<hook_event_name>.json, the raw hook payload. Because the event name is part of the filename, two events can never touch the same file: no read-modify-write, no locking, and ten concurrent sessions cannot race each other.

Stop fires many times per session, so the hook is bash builtins plus one redirect — zero forks after the first run. It exits immediately if $HERDR_PANE_ID is unset (not in a herdr pane means not in the fleet), and both the session id and the event name are character-checked before they become part of a path. macOS ships bash 3.2, which treats quotes inside an inline =~ pattern as literal, so the two regexes live in variables.

Two sources, and the disagreement is information

So the rule is asymmetric: if signal says attention and herdr_status says idle, believe signal. And if neither fires for days across the whole fleet, suspect herdr's detection rules broke rather than believing everyone is calm — herdr agent explain <pane> names the rule that matched.

done and idle are the same underlying state, before and after you have looked at it. Reading a pane from the CLI does not mark it seen, so the manager cannot accidentally clear a done out from under you. The field that separates just finished from idle since breakfast is reported_age_s, and it is a file mtime — the hook payloads carry no timestamp and the hook is deliberately zero-fork, so stat -f %m (BSD, falling back to -c %Y for GNU) is the only clock there is.

Label, not pane id — and when they lie

The label is what your sidebar shows, so it is the only name you can act on. The title tracks what the session is doing now; the label only changes when something renames the tab. When they disagree, the report says so — a tab labelled fleet running the orchestrator redesign, or one labelled 6, sends you to the wrong pane or to no pane at all. It offers herdr tab rename; it never renames on its own initiative. If label is null it falls back to the pane id and tells you that is what it is doing.

It also can't assume which pane it is: the manager session is not the tab labelled fleet unless it happens to be. It checks. (The sibling that keeps those labels honest automatically is herdr-autolabel.)

400 characters, then a subagent

last_message is truncated to 400 characters — enough to say what a session is asking, not enough to answer a real question about its work. For anything deeper it dispatches a subagent to read that session's transcript and report back in two sentences. Never a transcript into the manager's own context; they run to megabytes and it is holding ten of them. The untruncated text, if genuinely needed, is at ~/.agents/state/fleet/state/<session>.Stop.json.

Spawning and talking

A new session is always its own tab and never steals focus — and the recipe is longer than it looks, because two of its steps report success before they are true:

pane=$(herdr tab create --no-focus --cwd <dir> --label <slug> \
       | jq -r '.result.root_pane.pane_id')

# A fresh tab is not yet a shell, and nothing announces when it becomes one.
for i in $(seq 1 12); do
  out=$(herdr agent start <name> --kind claude --pane "$pane" \
          -- --dangerously-skip-permissions 2>&1)
  case "$out" in *agent_pane_busy*) sleep 1 ;; *) break ;; esac
done
sleep 5
herdr agent prompt "$pane" "<the task>"
sleep 5
herdr pane read "$pane" | tail -12   # REQUIRED: did the prompt actually land?

agent start returns interactive_ready: true as soon as the process exists, and agent prompt returns agent_prompted once herdr has typed — neither means the agent received anything. Prompt too early and the keystrokes vanish with every call reporting success, leaving a session sitting at an empty prompt while the manager reports it as working. pane read is the only honest confirmation; a pane showing 0/1.0M (0%) context and the default Claude Code title has never had a turn. If agent start never takes, close the tab you created — otherwise fleet reports an empty labelled tab as a real pane forever.

--kind also takes codex, gemini and others — this is not Claude-only. Talking to a session already running is the same prompt call and needs no wait; the race is only against startup. Target by pane id, not by agent name: names are ambiguous across tabs and easily reused, and the pane id is what the two hard rules are checked against. Fanning out is just several prompt calls — no special mechanism.

Every session runs --dangerously-skip-permissions. A prompt sent to the wrong pane gets executed without anyone asking. Hence the two hard rules: never write to a pane whose focused is true — that is two writers on one stdin with no lock — and never target yourself. fleet already excludes $HERDR_PANE_ID; do not route around it.

The loop lives outside the script, on purpose

The watch is a poll of the state directory, and the while true is in the Monitor command rather than in watch-tick. That split is load-bearing: a loop is read into the shell's memory once, so a script containing its own loop is frozen until the monitor is restarted. watch-tick does one pass and exits, so it is re-executed every tick, edits land on the next tick with no restart, and it picks up changes to fleet immediately. The second payoff is that a one-pass script can be run by hand — seed a fake label into its PREV file and watch [GONE] fire exactly once.

Being a fresh process each tick means nothing can live in a shell variable between ticks, so both pieces of memory are files in $TMPDIR: fleet-watch.seen (episode keys already announced, never truncated — truncating makes every arm re-announce the whole backlog) and fleet-watch.labels (last tick's label set). The label-set diff through comm -23 is what catches a vanished pane: a session that dies writes no state, so a change-only watch would be silent in exactly the case that matters.

The select is the volume control — only signal, done and blocked get through, because ten sessions past an unfiltered watch is a firehose and the harness stops firehoses automatically. And the interval sets latency, not cost: a tick is ~60ms of shell and wakes nobody, so 5s is a fine floor and fswatch would be optimising the wrong thing.

The ledger tracks tasks, not sessions

A session's status is never written into the ledger. Status is read live and joined at display time, so the ledger cannot go stale about anything herdr already knows. Done rows older than 7 days get swept at the top of an invocation; that is the only pruning, and there is no scheduled job.

Two channels out, and the spoken one goes first

The fleet console reads the manager's turns aloud on a phone, and prose written for a screen is punishing as speech — nobody follows a table by ear. So say-aloud takes one or two spoken sentences on stdin and writes speech/<session>.json through jq -Rs, because hand-authored JSON breaks on the first apostrophe and fails silently.

Order matters, and it is counter-intuitive. The Stop hook captures the manager's last assistant message. A turn that ends with "spoken version sent" hands the console that acknowledgement instead of the report, and the written channel silently goes blank. Call say-aloud first, then write the report as the final thing you say.

Disposable on purpose

No session state in the manager's head, ledger on disk — so /clear costs nothing and beats letting the context compact. When a round of work is finished and the ledger is written, it tells you it is safe to clear. At task boundaries, never at a token threshold: a threshold fires mid-thought and costs you the thread.

herdr's own conventions — pane geometry, naming, targeting, lifecycle — are deliberately not duplicated here. herdr --skill ships with the binary and changes when herdr changes.
