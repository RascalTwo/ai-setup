↓  WHY IT EXISTS

The queue ran dry, and the lessons evaporated

Kelpie builds what you sign off and refines what you hand over. When both queues are empty it simply stops, and the project sits idle until you think of the next thing yourself. Meanwhile the material for that next thing is lying around: the round of Changes requested that showed a build missed the point, the stall that happened twice, the workaround nobody came back to, the run that went so smoothly it deserves a sequel.

plus-ultra already knows how to judge "what would make this better", but it only sees the session it runs in. Dredge gives it a memory: everything since the last dredge, read as lessons, so the proposals come from what actually happened rather than a cold brainstorm.

Point it at a thing, or let Kelpie

Type /dredge and name the target: a repo, a directory, a skill, a tool, a process. The manifest carries disable-model-invocation: true, so an agent never reaches for it on its own; only you, or Kelpie's briefing, start it.

Inside Kelpie it fires by itself. When a project has nothing to build, refine or answer, the tick opens a 💡 dredge tab in the project's herdr space, at most once a day and only after a commit has landed since the last one. The proposals arrive in that pane; answer there.

What it won't do

  • It writes no code and changes nothing in the target. Its only writes are its own ledger and, on your word, the tasks you file.
  • It never files a proposal on its own judgment. Proposals land nowhere by default: they live in the conversation until you say "file 2 for an agent".
  • It has no cap, but it isn't allowed filler. A thousand proposals that each cite a lesson or carry a price are welcome. "Nothing new" is still a valid answer.
  • It forgets what its ledger forgets. Delete the state and a rejected idea can come back as if you'd never seen it.
  • Kelpie's "something new" test is commits. A project with no repos has nothing to compare, so an idle one dredges once a day.

Where it lives

The skill skills/dredge/SKILL.md: the target and its ledger, gathering lessons, judging with plus-ultra, presenting, taking verdicts.
Declared kind: skill, state: true, deletion-policy: retain, plus disable-model-invocation: true. Integrates plus-ultra (read by path, since it is user-invoked too), timeline-studio-tasks (filing) and recall (finding past sessions).
Its state ~/.agents/state/dredge/<slug>/: watermark (when the last dredge began) and ledger.md (every proposal and your verdict). Keep it: deleting it makes the next dredge look over all history and forget every rejection.
In Kelpie tools/kelpie/dredge.md is the run's briefing; the tick's step 4 in dispatcher.ts starts it, with the run folder ~/.agents/state/kelpie/dredge/<project>/ and its .started stamp.

How Kelpie decides to dredge

Every five minutes the tick checks each project, in this order, after it has filled the build and refine slots:

  • No work. No task to build or refine, none waiting on you, none signed off and closing, and none just handed over (a task without noQueue reads ready only on the next tick).
  • Not already dredging. No herdr agent whose working directory is the project's dredge folder.
  • A day since the last. The .started stamp is at least 24 hours old.
  • Something new. quiet() runs git log -1 --since=<stamp> on each repo's base; with no commit anywhere, it waits.
  • Not paused, and the usage gate is open, the same gate builds and refines use.

Then dredge() writes the briefing to .prompt.md, spawns the 💡 tab on Opus, and only then writes .started, so a failed spawn retries on the next tick. One new dredge per tick, like every other kind of run.
