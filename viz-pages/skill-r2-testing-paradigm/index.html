Bad tests drive out good

The easiest test to write mocks everything, so it proliferates — and the suite ends up green and lying. A mock returning { ok: true } passes whatever the code sends. A test that passes with the code broken is theatre, and nothing in a green run tells you which tests those are.

WHAT A TEST RESULT MEANS · columns: the code · rows: the test

A test only earns its keep in the bottom-right cell. If nobody has ever seen it land there, you can't tell it apart from the theatre cell — which is why this skill makes you put it there on purpose, every time.

Reminders don't hold that back; the skill's answer is mechanical. Choose the most real stand-in, prove each test can fail, measure the three things coverage can't see, and make the lazy path blocked rather than discouraged.

Any test work — loaded in slices

It fires on anything test-shaped: writing, reviewing or fixing tests, a flaky or slow test, a coverage gate, a mutation sweep, a screenshot baseline, choosing a stand-in. SKILL.md is short — what every test task needs — and a routing table sends each task to the one reference file it reaches for.

What it doesn't do

  • It doesn't ban unit tests. Function scope is for logic with many input combinations — date math, parsers, pricing, state machines. Call the real function, check outputs, exhaustively.
  • It won't narrow scope for convenience. Journey is the default; a narrower scope needs a narrower subject, not a test that was quicker to write.
  • It hasn't adopted step helpers or Gherkin. given()/when()/then() are fine where the stack already has them; adding them is unproven, and a trial (viz-gwt-as-code) is deciding. Until then, comments carry the clause.
  • It doesn't pick horizontal. Tests come one vertical slice at a time — unless you ask for them up front. That choice is yours.
  • No retries, no quarantine, no "slow" bucket. There is no tolerated class of flaky or slow test to file things under.
  • The reviewer doesn't run the sweep or edit tests. test-reviewer reads the mutation report and reports findings; it changes nothing.
  • It installs nothing. Stryker, MSW, LocalStack and the rest are examples of a rung, not requirements.

Two axes: scope, then stand-in

Black box first: test as a user of the thing and assert on what that user can observe — and the user changes with the scope. Test hardest where a failure would be silent (a wrong number, a dropped record); a crash is loud on its own. Pick the row from what the test is about; then, for every dependency it doesn't own, take the leftmost column you can get.

A test must be able to fail

One test at a time, the loop has five steps, and the fourth is the one most suites skip: break the code on purpose and watch the test notice. When the whole change looks done, a mutation sweep does the same thing across everything it touched.

THE LOOP, THEN THE SWEEP · step through it

← → arrow keys

Every test reads as GIVEN / WHEN / THEN, verbs in capitals, one clause each. A second clause repeats the verb; AND never joins them. In code, the comment carries the whole clause, never the bare verb. Expected values come from somewhere independent of the code — a literal, a worked example, the spec.

// GIVEN a user with no session
// WHEN they request the dashboard
// THEN they are redirected to /login
// THEN a login-required event is logged     ✓ verb repeated
// GIVEN                                     ✗ bare verb — the clause is missing

Three coverage signals, three questions

No signal answers another's question. Line coverage says a test ran a line, not that anything checked it — so a suite of do-nothing mocks can hit 100%. Flip between two suites of the same code:

THE SAME CODE, TWO SUITES · pick one · numbers illustrative

The gate has rules of its own. Aim for 100% of lines and branches; hold a floor that only rises — lowering it is a deliberate, reviewable edit; test the gate both ways, since one never seen failing may not be wired up. And an exclusion carries its reason on the exclusion itself:

✓ passes the gate — the reason sits on the exclusion
/* c8 ignore next -- only runs in browsers without a built-in QR decoder */
✗ bare — fails the gate
/* c8 ignore next */

Flaky and slow tests are bugs

In the test or in the code — never a property of the suite. A fixed sleep is both at once: too long on a fast run, too short on a loaded one.

Retries and quarantine would have hidden a real defect. Force the rare condition until it fails every run, then fix what that exposes. Make tests independent so they run concurrently, test the end state with motion off, and leave artifacts — video, DOM snapshot, network log, console, an error naming what was expected — so nobody needs a re-run "with logging on".

A person approves every baseline

SCREENSHOT TESTS · mask what isn't under test, then a person decides

A new picture never becomes the baseline by itself. The clock, today's date, a random id — anything that changes on its own — gets a solid box in both pictures, or the test fails every run for nothing. Keep baselines few, clipped to the element that matters.

Gates, not willpower

Gresham's law is why the skill enforces instead of exhorting: if the lazy test is merely discouraged, it still wins on effort. So the lazy shape is made unrepresentable or blocked.

TWO SHAPES THAT DO THE ENFORCING

A journey test is a file in the journey folder with the journey suffix — there's no in-between folder where a half-mocked journey can hide. Before adding a new kind of test, see if an existing artifact can do the job: one story, three jobs, one place for bad tests to grow instead of three. Every escape hatch — an exclusion, a mock where a fake would do, a gate opt-out — carries a written reason, checked mechanically.

The same file covers tooling. Test every gate both ways — see it fail on a violation and pass without one. Write down each tool's blind spots and cover them elsewhere: Cypress doesn't enforce CORS like a real browser on the real domain, so a curl check against the deployed origin does. And prefer portable tooling: a macOS-only decoder was swapped for ZXing/WASM so the same tests run in Linux CI.

What the reviewer checks, and where each rule lives

test-reviewer asks three things of each test — who is the user, would it catch the bug, is there a more real version — then runs twenty-one checks. Each one points back to the file that explains it, and the finding cites it: severity (blocker / suggestion / fyi), file:line, the rule, a concrete fix.
