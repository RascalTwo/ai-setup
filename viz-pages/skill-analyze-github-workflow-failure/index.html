It never reads
the whole log.

A failed Actions run is mostly green. The first pass pulls only the failed steps — one gh command — and usually that is the answer. The full log zip opens only when that came back truncated or ambiguous, and even then nothing is read end to end: five error-typed greps, each with a hard line cap.

It names the broken step and the cause.
It writes no fix and re-runs nothing.

The failure is four lines. The log is not.

The thing you actually want out of a red CI run — which job, which step, what it said — is a handful of lines buried in megabytes of successful setup, cache restores and dependency chatter. Handing all of that to a model is how you spend a fortune to read something you didn't need.

So the skill is built around one refusal: never download the whole log until you have a reason to. Two passes, and the second one has named conditions instead of a judgement call.

"Latest" is narrower than it sounds

You can hand it a run ID, or say latest. But "latest" resolves through a one-element list — it takes the single most recent run and then checks whether it failed:

gh run list --limit 1 --json databaseId,conclusion \
  -q '.[] | select(.conclusion=="failure") | .databaseId'

So it means "the latest run, if that run failed" — not "the most recent failure". If something has since gone green, or a run is still in flight, the selector matches nothing and you get an empty string rather than an older failure. Fine for the real use case (you just watched it go red), worth knowing before you hunt a phantom bug in the skill.

It stops at the diagnosis

Both passes end at the same four-part report, and the shape is the deliverable: which job and step failed, the exact error message, the likely root cause, the suggested fix or next step. Suggested. Nothing is patched, nothing is re-run, nothing is pushed — the fix is a sentence handed back to you, and applying it is a separate decision you make.

  • It never re-runs anything. No gh run rerun, no dispatch. Triggering is a different skill's job.
  • It reads one run. No comparison against the last green run, no history, no flake detection.
  • Every probe is bounded by head. That caps the cost and it also means a failure whose evidence sits past the cut is simply not seen.

When the answer isn't in the log at all

This skill is a reader. It works on the assumption that the run already printed the truth somewhere and the job is to find it. When a provider swallowed the real error and emitted an opaque "unknown error" instead, no grep will recover it — that's diagnose-terraform-unknown-error, which adds temporary debug logging, triggers a fresh run, and extracts the actual HTTP exchange. Different tool, because it's a different problem: this one reads evidence, that one has to go create some.

Where it lives

IntegratesGitHub Actions run logs, via the gh CLI — two endpoints and nothing else: gh run view --log-failed for the cheap pass, and the REST route repos/<owner>/<repo>/actions/runs/<id>/logs for the zip.
Requiresgh, already authenticated against the repo. Plus unzip, grep and head — every probe in the deep pass is those three.
Where it reads fromThe repo you are standing in. It does not take an owner/repo argument for the cheap pass; gh resolves that from the git remote.
Its stateNone. It keeps nothing between runs — no cache, no index, no history. The one file it creates is /tmp/run-logs.zip, overwritten by the next invocation and owned by the OS's temp cleanup, not by the skill. Nothing under ~/.agents/state/.
Its other halfTwo files in the skill directory, not one prompt: quick-analysis.md and deep-analysis.md. SKILL.md is a router that says which to read and when.

Two passes, and what fires the second

From a run ID to a root cause, tracing the one path the skill actually takes.

← → arrow keys

Pass one asks GitHub to do the filtering

gh run view <run-id> --log-failed 2>&1   # every failed step, one shot, no zip

Then it scans that output for the four things that usually carry the answer: the job and step name, the error message / exit code / exception, any HTTP status code in the 4xx–5xx range, and provider-specific error summaries. Most runs end here. The skill calls this pass "lightweight and token-efficient" and means it as the reason to try it first, not as a disclaimer.

The escalation has named conditions

Pass two is not "be thorough anyway". It fires on exactly three states, and they're all properties of the pass-one output, not of the failure: the output was truncated, the error was unclear, or more context is needed. Only then does it pull the whole run:

gh api repos/<owner>/<repo>/actions/runs/<run-id>/logs > /tmp/run-logs.zip

And having paid for the zip, it still doesn't read it. It picks a probe by what the error looks like and greps for that signature alone — the Terraform box-drawing block (grep -a "│" minus the rule characters), a Go panic (panic|goroutine|SIGSEGV), an HTTP status line, a Www-Authenticate header or insufficient_scope. Every one is piped through head, so the worst case is bounded before it starts.

# the catch-all, for when you can't type the error yet
unzip -p /tmp/run-logs.zip \
  | grep -a -E "(Error:|error|panic|failed|Fatal)" \
  | grep -v "azure\|microsoft\|github\.com\|blob\|management\|login\|storage" \
  | head -40

unzip -p is doing real work there: it streams the archive members to stdout without ever unpacking them to disk, so a multi-hundred-megabyte log costs one pipe and no extraction. -a is on every probe for the matching reason — that concatenated stream contains control bytes, and without -a grep decides it is binary and stops printing matching lines.

The denylist cuts both ways

It filters on substrings, not on sources. That second grep -v exists because "error" matches a thousand innocent Azure and GitHub URLs — but a genuine failure whose message contains management, storage, login or blob is thrown out with the noise. It is a noise filter tuned against one shop's pipelines, not a general one. If the catch-all comes back empty, that is the first thing to suspect — not evidence that the run is clean.
