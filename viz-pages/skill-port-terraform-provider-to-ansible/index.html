Port, don't invent

A mature Terraform provider is years of pre-discovered knowledge: every schema field, every API quirk, every server-side normalization is already encoded in its Go source. The provider is the spec — read it, don't rediscover it. Providers are also the ecosystem's shared source of truth (Pulumi bridges them, Crossplane upjet-generates from them), so porting one ports the industry's best knowledge of that API.

The workflow is battle-tested on one port: terraform-provider-keycloak → 131/131 surface parity (109 resources + 22 data sources), every module live-acceptance-tested, in roughly two hours of orchestrated agent time.

You invoke it. It never invokes itself.

The manifest carries disable-model-invocation: true, so nothing about a conversation makes this fire — it starts when you name it: "port the provider", "build an Ansible collection for X", "Ansible can't manage X natively". That gate is deliberate. This is a multi-hour orchestration that clones a repo, writes a collection and fans agents out in parallel; it is not something that should happen because someone mentioned Ansible.

It handles a partial port too — resuming a collection that already covers half the surface — and Phase 0 ends by confirming scope with you: full parity or a subset, where the repo lives, what the collection namespace is.

The limits, stated out loud

The test target is a local container, full stop — a script in the repo owns start, healthcheck, bootstrap credentials and env file. Pointing the suite at a deployed instance was measured at roughly 5× slower per run (WAN+TLS on every call), and the suite dies when that instance does. The only exception is a service that genuinely cannot be containerised, and then that limitation goes in PARITY.md in bold.

The per-module lifecycle is about one fifth of a mature provider's permutation depth — providers accrete per-field update cases over years. Closing that gap means porting the provider's own resource_*_test.go files scenario by scenario, which costs about as much as the module port itself and multiplies suite runtime. Measured-PoC: lifecycle tests suffice and the depth gap is stated honestly. Owned product: port the suite.

  • Terraform plan and state mechanics do not port. import, write-only *_wo attributes and regenerate-triggers have no Ansible meaning; each non-port is documented in the module docs rather than faked.
  • Untestable is allowed, unevidenced is not. A resource that can't run on this server is acceptable only with the captured server error attached — a feature gate, a server-side file, a removed feature.
  • The port is a derivative. It carries the provider's licence (usually Apache or MPL) plus a NOTICE crediting it. That is a Phase 0 decision, not a shipping afterthought.
The deliverables are usually the point. EFFORT.md and PARITY.md carry the caveats the numbers don't: AI-minutes are not human-months, porting a mature provider is easy mode because the quirks were pre-discovered, and ownership — CI, releases, API drift — is a recurring cost the build does nothing to reduce.

The shape Ansible forces on it

Resources become modules; data sources become *_info modules — read-only, plain AnsibleModule plus the API client, changed=False, supports_check_mode=True. The trap is the miss case: port each data source's miss semantics from its Go read path. Some return empty state on a 404, some hard-error with specific messages. Get it per-resource; there is no convention to guess. Secrets get stripped from returns even where the provider exposes them as Sensitive attributes.

Everything a plan/state engine would have handled is hand-built once, in a shared layer written by hand before any fan-out — 318 lines in the reference port, across three files:

  • plugins/module_utils/<service>_api.py — the provider's client, ported: its auth grants, re-login-once-and-retry on 401 (providers do this, and long runs need it), JSON verbs relative to the API base, created-id capture, safe error extraction. Built on ansible.module_utils.urls.open_url, because a collection must not require requests.
  • plugins/module_utils/resource.py — a present/absent engine taking read() / desired() / create() / update() / delete() hooks, so check-mode and --diff are implemented once for every module. Declared-fields-only comparison, SET_FIELDS for order-insensitive lists, sanitize() for secrets.
  • plugins/doc_fragments/<service>.py — the auth options, so every module's docs inherit them instead of repeating them.
Register every module name before writing any of them. The whole action_groups block in meta/runtime.yml is generated from the resource file list up front. Playbooks then set auth once via module_defaults: group/<ns>.<name>.<group>, and no fan-out agent ever edits a shared file — with 16 parallel writers, merge collisions are otherwise guaranteed.

What actually makes a module flap

Idempotency fails in specific, boring, expensive ways — each one a day a from-scratch team loses:

  • Quoted booleans. Component-style configs store booleans as the strings "true"/"false"; Python's str(True) is "True" → permanent flapping until explicitly mapped.
  • Masked secrets. Servers echo ********** back, so a secret-only change is undetectable. The provider has the same limitation (DiffSuppress) — keep secrets out of the comparison and inject them at write.
  • Server-added fields you never sent → compare declared fields only, and send existing-merged-with-desired on update.
  • Order-nonpreserving multivalued config → compare order-insensitively, or flap forever.
  • Durations the provider exposes as strings become integer seconds, because seconds are the API's native unit and the string is a Terraform-side convenience.

The rule the fan-out agents get: server normalizations are normalized in the module. Never weaken the idempotency test to make it pass. The oracle mirrors how providers test themselves — apply twice, and the second run must report changed=false — extended into a full cycle: create → identical re-run → check-mode update with the diff asserted and no server mutation → real update → absent → absent re-run not-changed.

Two Ansible-only paper cuts

Neither exists in the provider, both bite in the port. Ansible's no_log heuristic fires on any option name containing password or secret — reset_password_allowed and password_policy trip the warning and need no_log=False set explicitly. And a return key literally named keys collides with dict.keys() in Jinja, forcing result['keys'] bracket access in every playbook; pick a different key name.

Prove parity, don't claim it

The preferred oracle isn't the Go source, it's Terraform itself: terraform providers schema -json dumps every resource's and data source's final composed schema, and scripts/field-parity-audit.py --schema-json diffs the collection against it. The module side is read with Python's ast — argument_spec keys pulled straight out of the syntax tree, unioned with the options: keys in the module's DOCUMENTATION block — so the audit compares what the module declares, not what it documents.

Three exclusion lists keep it honest rather than noisy: EQUIV maps renamed fields (realm_id → realm), IGNORE_GO drops the Terraform-only mechanics (import, client_secret_wo, client_secret_wo_version, client_secret_regenerate_when_changed), and DS_ARTIFACTS records, per data source and with the Go line number that proves it, fields declared optional that the read path never actually reads. Computed-only fields are excluded outright: they are outputs, and they land in end_state rather than in options.

Expect to discover legacy alias registrations in the provider's resource map — serve those as plugin_routing redirects, not duplicate modules. If the registry release lags the HEAD you ported, the dump misses the HEAD-only resources; the fallback is --provider-src, a static Go parse whose composed schemas come back NEEDS-MANUAL for a small agent wave to resolve with evidence. And when the audit finds real gaps, expect your own hand-built exemplars to be the guilty ones — they were written before the patterns were known.
