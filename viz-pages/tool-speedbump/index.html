Every session thought it had the whole machine

Sessions can't see each other, so each sizes its work as if it were alone. On 2026-10-16 two sessions ran the same viz verify side by side, each with a headless Chrome at 12x concurrency, and the Mac crawled. A per-tool lock only covers tools already known to be heavy.

speedbump checks the machine itself before every Bash call, so it covers anything, and tells the agent who is already hogging it.

You don't invoke it

  • It is always on once install.ts has merged the hook into your Claude Code settings. Nothing to type.
  • When it fires the agent sees "Speed bump, not a wall", the reason, the three busiest processes and the instruction to run the exact same command again.
  • To tune it read ~/.agents/state/speedbump/log: blocks while the Mac felt fine mean the thresholds are too low.
  • To turn it off remove the entry from settings/claude-code/settings.json. Test: sh tools/speedbump/speedbump.test.sh.

What it won't do

  • It never blocks twice. Once a session has been warned, every command it runs for the next 10 minutes passes, whatever the command.
  • It doesn't stop or throttle anything. It only advises; the agent decides.
  • Memory warning is ignored, only critical counts. Swap used, disk I/O and thermal state are left out on purpose.
  • macOS only. It reads kern.memorystatus_vm_pressure_level.
  • A failed disk reading counts as fine, so a broken df never blocks every command.

Where it lives

Integrates with Claude Code hooks: a PreToolUse hook on Bash, entry in settings/claude-code/settings.json, timeout 5 s, run after rtk hook claude.
Requires sh and jq. Platform: macOS.
Its state ~/.agents/state/speedbump/: sessions/<session_id> (mtime is the "warned" mark; files older than 60 minutes are pruned) and log (one line per block).
Safe to delete? No, deletion-policy: retain: the log is your tuning record. Deleting the session marks only means each session is warned once more.

One Bash command, end to end

Claude Code is about to run bun test. It pipes {"session_id", "tool_input":{"command"}} to tools/speedbump/speedbump.sh on stdin. Exit 0 lets the command run; exit 2 blocks it and feeds stderr to the agent.

  1. Read the machine. sysctl -n hw.ncpu kern.memorystatus_vm_pressure_level vm.loadavg plus df -k "$HOME" free KB. SPEEDBUMP_SIGNALS fakes this in tests.
  2. Decide. An awk pass flags: pressure level >= 4 (critical); 1-minute load > 1.5 x cores while the 5-minute load > cores; free disk < 10485760 KB (10 GB). None true: print nothing, exit 0.
  3. Check the mark. jq pulls session_id; if ~/.agents/state/speedbump/sessions/<id> was touched in the last 10 minutes (find -mmin -10), exit 0.
  4. Otherwise bump. touch the mark, prune marks older than 60 minutes, append date session cores pressure load free-kb cmd (command cut to 120 chars) to log.
  5. Name the culprits. Disk-only trouble gets a short "free up space" message. Otherwise ps -Ao is sorted by RSS (memory) or CPU, top 3 each walked up its parent chain to a claude process and tagged "(this session)" or "(another Claude session, pid N)".
  6. Exit 2. The message on stderr says to run the exact same command again. The agent does; step 3 now finds a fresh mark and the command runs.
