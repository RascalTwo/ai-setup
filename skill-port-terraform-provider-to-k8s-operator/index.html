The provider is already the spec

A Terraform provider is a machine-readable description of a service's manageable surface: docs/resources/ enumerates every resource, the Go schemas define the fields, and the acceptance tests encode years of API edge-case knowledge. Phase 0 is three gh api calls — the resource list, the release tag you'll pin your parity claim against, the test-suite size. Those three numbers become the denominators for every claim you make later.

And the operator gets one capability no Terraform provider has: continuous drift correction. An out-of-band change is reverted in seconds rather than detected at the next plan — which is why the target of the port is an operator and not another CLI.

Then the question that decides everything: does a typed SDK for the target API exist in your implementation language? If yes, the port is mostly reconcile-wiring. If no, budget a client-wrapper layer first and say so in the ledger — it's the difference between hours and days, and the honest headline of any measurement.

You invoke it. It never invokes itself.

The manifest carries disable-model-invocation: true. Nothing about a conversation triggers this; you name it — "an operator for X", "CRDs for <service>", "operator parity with the <X> provider" — and it also resumes a port that is already half done.

Five inputs get established before any code, and it asks only about the genuinely undecidable ones: the provider repo, the target API and auth (a local dockerized instance, always), the language and runtime (Java 21 + Quarkus + JOSDK/QOSDK by default — an explicit Go/kubebuilder ask is honored, but the reference chassis is Java-shaped), the scope, and the repo home and naming rules.

Proven end to end on one build: 11 CRDs covering an IdP provider's core surface in about 79 minutes wall-clock, 9 parallel agents, 0 integration defects. Those calibration numbers come from that run; nothing in the skill is specific to that provider.

The PoC boundary, named on purpose

  • No admission webhooks, metrics, CRD versioning or HA tuning unless you ask for them — but the skill makes you list them as the production tax, so the effort number is never quoted naked.
  • You cannot run the provider's acceptance tests. Its test engine shells out to the terraform binary. You port every behavior instead, and track it in docs/TEST-PARITY.md so "mirrored" is a checklist rather than a vibe.
  • A CRD count is not a coverage number. Full parity lands at roughly a third to a half of the provider's resource count, because families collapse. "11 CRDs" says nothing without docs/CAPABILITY-MATRIX.md beside it, and the skill's rule is blunt: never claim parity without that file.
  • No dual-path remote-target logic. The target is URL plus credentials in env vars, so pointing elsewhere is already a zero-code override. Building flags for it is explicitly forbidden.
  • The generated CRDs have no required: blocks. The CRD generator ignores @JsonProperty(required=true); a missing field surfaces as a reconcile error carried in status, not as a rejected apply — acceptable for a PoC, and a thing to state rather than discover.

One lever, decided once

The chassis is a single generic reconcile path every resource reuses — and you build it inline yourself; never delegate it. Specs carry typed fields for the common knobs plus a free-form additionalConfig overlay deep-merged over the representation, so full API reach doesn't require a typed field for everything.

serialize desired (NON_NULL)  # from the CR spec
overlay additionalConfig      # the escape hatch, merged on top
fetch live
  absent  → create, re-fetch for the id
  present → subset-diff (every desired field must match live)
            → merge-update on drift

Subclasses implement exactly two methods — sync (make the API match the spec, return the remote id) and remove. Everything else is inherited: delete is finalizer-backed through the framework's Cleaner with deletePolicy: delete|orphan, status carries ready, message, resourceId, lastSync and observedGeneration, and @MaxReconciliationInterval(interval=30, SECONDS) is not a tuning knob — that 30-second resync is the drift-heal mechanism.

The escape hatch has a shape requirement that costs an afternoon to discover: additionalConfig must be a JsonNode, not a Map<String,Object>. The map form still emits additionalProperties: {type: object} into the generated CRD, and scalar values get rejected at apply time. And @PreserveUnknownFields lives in io.fabric8:generator-annotations, not in the crd-generator-api artifact you would guess.

A continuous loop turns small bugs into infinite ones. Fields owned by a different endpoint — list-attachment fields settable only at create — silently no-op on update. Set them on create, then strip them from the drift compare, or you get an eternal 30-second PUT loop. Same for masked secrets: servers echo **********, so a secret left in the subset comparison never matches. Exclude those keys and re-set them only on real writes. Same again for a representation constructor that defaults a deprecated field — null it before building the desired subset, or every resync is a PUT.

Then one or two exemplar resources go end-to-end green before any fan-out — the exemplar exists to eat the chassis bugs once. In the reference build both chassis defects surfaced in the first exemplar's e2e run, and nine parallel implementations inherited the fixes for free.

CRDs are not one-to-one with resources

Providers explode variants into separate resources — N *_protocol_mapper types, M vendor-flavored *_identity_provider wrappers. One CRD with a type field covers a whole family. Component- or plugin-style APIs collapse the same way: where a provider exposes LDAP federation, its mappers, realm keystores and key providers through one generic endpoint keyed by providerType + providerId with a free-form config map, the family becomes one CRD and the same lever fits.

Waves are sorted by business value, not alphabet. Same-shape mechanical resources parallelize cheaply; a domain that needs new chassis ground gets its own exemplar-first hour before its wave fans out. One agent per resource, an isolated git worktree each, docs/PATTERN.md as the contract, and compile-only inside the worktree — the integration e2e runs once after merge, by you. After each wave: merge, rebuild, run the full suite, update the capability matrix, commit.

You can't run their tests. You can port every behavior.

The acceptance tests are the highest-value artifact in the provider repo: each *_test.go is a behavioral spec whose fixtures translate roughly 1:1 to CR YAML and whose check functions read as assertion checklists. You cannot execute them — the test engine shells out to the terraform binary — so you port the behaviors instead, into verify/verify.d/NN-<resource>.sh scripts run in order by verify/verify.sh against the real API with no mocks anywhere.

Each script is self-contained and builds its own prerequisites through raw API calls, never through other CRDs — so a broken CRD fails one script instead of cascading through the suite. Four beats every time: create → update via CR patch → out-of-band drift-heal → delete and assert gone. The third beat is the one no Terraform provider can be asked to pass.
