The problem

Documentation costs as much as code to write and maintain, and gets a fraction of the scrutiny. Nothing compiles it, nothing tests it, nothing goes red when it drifts — it just misleads quietly until someone acts on it. The ten rules are the missing scrutiny. They come from documandments.com (Austin Grey Lovelace, 2026); the skill is the enforcement.

Rule I is a gate, not advice

Before a single line, four questions get answered out loud: what is this accomplishing, who is the audience, how will they know it exists — the critical path, the file or review or error message they are already looking at — and who keeps it true.

Fail any one and the doc doesn't get written. Not written badly, not written with a TODO — not written. The output is a sentence instead: "I'm not adding a doc for X because nobody would find it and nothing keeps it true." This is the most important rule; the other nine only matter for docs that clear it.

Then the ladder

Docs that pass the gate still don't go straight to a docs/ page. Confusion you can delete beats confusion you can explain, and truth baked into a contract is enforced rather than remembered — never write "may be null" when you could make it nullable, never document a valid-values list you could have made an enum. Prose is rung four. A standalone document is rung five.

And placement outranks quality: if it sits somewhere the reader must first think to look, assume they never will.

What survives in the prose

  • Only the why. The code shows what, the tests show how. Write what they can't: the trade-off, the constraint, why the obvious approach was rejected, what breaks if someone "simplifies" it.
  • Less detail, not more. The seven-step walkthrough becomes a lie the moment the process grows an eighth step, and it always does. Deciding what to leave out is the valuable part.
  • One home per fact. Copies drift, disagree, and teach the reader to trust neither. Link instead — and prefer a source that can't drift, generated from the code or authoritative over it.
  • Flat, tagged, linked. A folder tree taxes you twice: once guessing the branch to file under, again guessing it to find.
  • Diagrams in the repo, in text. Mermaid first. Never a screenshot, never a link into a tool that demands an account — those are diagrams that will never be updated.
Especially when the prose is AI-generated — which means yours. The default failure mode is verbose, over-structured, faintly corporate text with three sentences where one would do. The rule is to reread your own draft as an editor and cut it before it enters the codebase.

Rule X: distrust what's already there

Treat every doc you read as an unversioned script running in production with no coverage — verify it against the code before relying on it. When you change code, grep for the prose that describes it and fix or delete whatever your change just falsified. Stale docs are a defect your change introduced. Deleting a stale doc is a legitimate fix and often the best one.

The review pass

The same ten rules run backwards over a diff. It reports only what fails — no clean bill, no restating what's fine — as rule number, file:line, what's wrong, and the fix.

# the fix is almost always one of three words
III  api/client.ts:88   comment restates the line below  → cut it
IV   docs/setup.md:12   duplicates the vendor's install  → link it
II   README.md:40       lists the 5 valid modes in prose → make it a type

Where judgment overrides

The rules serve the reader, not themselves. A generated API reference is "detailed" and that's fine. A legally required runbook exists whether or not it survives entropy. A newcomer tutorial is step-by-step on purpose. When a rule and the reader conflict, the reader wins — but the skill has to say which rule it's setting aside and why, so it's a decision instead of a slip.

The skill file ends by pointing rule X at itself: this too will eventually be outdated.
